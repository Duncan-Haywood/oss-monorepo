    Common questions

    Why does my Stripe webhook signature verification fail?

    The usual cause is that the body being hashed is not the exact bytes Stripe sent. Frameworks that parse JSON first and then re-serialise it change whitespace and key order, which changes the HMAC. Verify against the raw request body. The second most common cause is the wrong whsec_ secret: each endpoint has its own, and stripe listen prints a different one than the dashboard.

    What exactly is signed for each provider?

    Stripe signs the timestamp, a dot, then the raw body, using HMAC-SHA256 with the secret and hex output. GitHub signs the raw body (sha256= prefix, hex). Shopify signs the raw body and base64-encodes the result. Slack signs v0:timestamp:body (hex, v0= prefix). Standard Webhooks (Svix, Clerk, Resend and others) sign id.timestamp.body, base64-encode the result, and use the base64-decoded part of the whsec_ secret as the key.

    Does this tool upload my webhook secret or payload?

    No. Everything is computed in this page with the browser's Web Crypto API. Nothing is sent anywhere and the page makes no network calls. Even so, prefer a test-mode or already-rotated secret when debugging, and rotate any live secret you paste into a shared screen or ticket.

    Why does a valid signature still get rejected by my server?

    Stripe, Slack and Standard Webhooks libraries also reject requests whose timestamp is more than about five minutes from your server clock. A correct signature on an old request fails that check, which is the replay protection working. Check server time (NTP) if live requests fail this way.

    No. It checks one request against one secret and suggests likely causes. It does not review your endpoint's other defences and is not security advice. No warranty.
