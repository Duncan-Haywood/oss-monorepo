The audit pass, and how much of it a template can decide

Study · 2026-08-24 · portfolio/research/a11y-evidence-record/README.md

Built and measured 2026-08-20. Re-runnable:

cd portfolio/research/a11y-evidence-record
python3 -m unittest discover                          # 186 tests, no dependencies
python3 measure_themes.py --recompute-from results-2026-08-20.json   # offline, pre-contrast
python3 measure_themes.py --recompute-from results-2026-08-21-contrast.json  # offline, with 1.4.3
python3 audit.py <path> --record --scope "<subject>"  # produce a record
python3 audit.py <path> --stylesheet theme.css --record --scope "<subject>"  # + contrast (1.4.3)

Why this was built

portfolio/pipeline/candidates/eaa-remediation-pipeline.md is the pipeline's highest-composite candidate (7.25), carries a build-now verdict, and is the only build-now candidate with nothing built for it. Its first experiment opens:

"Build the audit-and-fix pass against three real shop themes; measure how many blocking issues the generated fixes actually close under AT verification."

The second half needs a contractor with a screen reader and cannot be done by an unattended session. The first half can be, and had not been. Two candidates depend on it — shopify-a11y-evidence sells the same audit through a different channel.

This directory is that pass, plus the write-up's deliverable 4 — "a dated file listing what was tested, with what tool or AT, what changed, what remains open and why" — as a function rather than a promise.

Amendment, 2026-08-21 — the coverage boundary had a hole, and it is closed

Finding 1 below is the right design and it was not fully implemented. The boundary it assembles is only honest if every criterion the engine reasons about lands in one of the record's two lists. Two did not.

Run for the first time against this portfolio's other WCAG engine (pipeline/probes/eaa-wcag-triage/), audit.py was found to check neither 1.2.2 Captions nor the aria-hidden-on-a-focusable-control case of 4.1.2, and to list neither in NOT_TESTED — so a record said nothing at all about them, which a reader can only read as "checked and passed." On the hand-labeled fixture set that gave audit.py recall 0.857 against the sibling engine's 1.0.

Both checks are now implemented, and CoverageBoundaryIsComplete in test_audit.py asserts the invariant that would have caught it: no criterion is both checked and declared untested, and every statically reachable criterion appears in one list or the other. Suite is 61 → 75 tests.

Consequence for the numbers below: the headline counts (286 findings, 63.2% undecidable across twelve npm storefront themes) were produced before these two checks existed, so the finding count is a lower bound by an unknown margin. Re-deriving it needs measure_themes.py to re-fetch the twelve tarballs; --recompute-from cannot do it, because the saved rows hold per-package results rather than the markup. The measurement and the full reasoning are in ../a11y-engine-agreement/.

Finding 1 — the record cannot be published without its own coverage boundary

This is a design result rather than a measurement, and it is the part that matters most for liability. The candidate's rule is:

Never sell an overlay, and never sell "compliance." … Deliverables state what was tested and when — a record, not a warranty.

A disclaimer in a template is not that rule; it is a sentence someone can delete. So the list of success criteria the tool cannot test is assembled inside evidence_record(), in the same structure and the same function as the findings. A caller cannot emit findings without also emitting the seventeen criteria — contrast, reflow, focus visibility, keyboard operation, alt-text quality, and whether a real screen-reader user can complete checkout — that static analysis does not reach. test_record_carries_its_coverage_boundary_even_with_no_findings pins it for the case where it is most tempting to omit: a subject with nothing found. example-record-2026-08-20.md is exactly that case, and it is 52 lines of which 24 are the coverage boundary.

The third answer is the other half of it. A template that emits alt="{{ image.alt }}" has an alt attribute whose value is unknown until render. Calling that a pass overstates coverage; calling it a failure invents a defect against a customer's markup. It is counted as undecidable and reported as an open item. Every template-expression test in test_audit.py asserts an empty findings list, not merely a non-empty undecidable list.

That third answer turned out to be the measurement.

The candidate's write-up cites, from secondary sources, that "automated tools catch roughly a quarter to a third of WCAG issues" — a claim about rendered pages, and the reason the write-up scores autonomous ops: 6 and prices a contractor into every job. A remediation vendor does not edit rendered pages. It edits templates, and at that stage a second gap opens underneath the first one: most of what the audit can see is a variable.

The important part is which gap it is. The undecidable class is not contractor work. Rendering the shop's own pages with the shop's own data closes almost all of it — it is a build step, not a hire. So this finding argues that the pipeline needs a render stage before the audit stage, and that a template-only audit sold as a deliverable would be reporting on about a third of what it appears to cover. It does not argue that autonomous ops: 6 is overstated; if anything the automatable fraction is larger than scored, once the render step exists.

Finding 5 — the port was built, not just scoped; on templates it is mostly undecidable, and the reachability study said why before the port existed to measure it

../a11y-engine-agreement/README.md named porting #523's colour-contrast resolver here — against unrendered templates rather than the rendered pages it measured at 98.76% decidable — "an open question rather than a port." A concurrent session answered half of that question first, without building the port: the amendment below this one (now superseded, kept for the record) measured reachability — measure_stylesheet_reachability.py scanned the same 22-package, pinned-version corpus as results-2026-08-20.json for stylesheet files and expression-built classes, found 9 of 22 packages ship any literal .css at all (the rest is Sass/Less source, or nothing), and concluded a resolver "is not proposed here." contrast_pass.py is that resolver anyway, built independently in a session that had not yet seen that conclusion when it started, and then re-run — after the collision surfaced — against the same pinned corpus for a like-for-like comparison rather than reconciling by narrative alone.

The reachability study's central number holds under an independent build: 9 of 22 packages, exactly. That is strong cross-validation of two different scanning methods (a bespoke reachability scan and this module's own css_from_tarball) landing on the same figure. Where the two accounts differ is the conclusion, not the count. The reachability study treated "most packages have no reachable stylesheet" as a reason not to build a resolver for the ones that do; measuring what the resolver actually does with those 9 says that reasoning proves too much — the sibling engine does not decide 100% of rendered-page contrast either (98.76%, not 100%), and this codebase's standing principle is to resolve what is decidable and name what is not, not to decline a whole criterion because it cannot cover everything. contrast_pass.py's guard against expression-built classes — the reachability study's other named concern, measured there at 1.6% of class attributes corpus-wide — is real defensive value in the resolver regardless of how it is scored, since a falsely-resolved class is the failure mode this whole tool exists to avoid.

no-declared-color — the honest "nothing here says what colour this is" answer, identical to what a page with no stylesheet supplied gets — is 1,099 of 1,312 undecidables (84%) across the whole corpus, which is the reachability study's finding wearing a different name: most of the corpus has no stylesheet to resolve against, so most elements are undecidable for exactly the reason that study measured. CSS volume does not predict decidability: @zalify/theme-templates ships 119 .css files — the most literal CSS in the corpus — and resolves none of its 47 contrast-bearing elements, because its markup is the one this pass guards against (class-is-template-expression and style-is-template-expression account for 22 of @zalify's 47 undecidables; see the per-package rows in results-2026-08-21-contrast.json for the rest). The undecidable reasons among these 9 packages are no longer one reason wearing every case — no-declared-color still leads (507 of 680), but no-opaque-background (46), class-is-template-expression (44, corpus-wide — the guard, firing on real dynamically-classed wrappers, not hypothetically) and unresolvable-color (39) all contribute a real share. unresolvable-font-size is 22, entirely from one package (gatsby-shopify-theme), consistent with a CSS-in-JS build this reader — by design, plain-CSS only — cannot see.

What this changes and does not change. It does not roll back the sibling engine's finding: a rendered page's contrast is 98.76% decidable, and that number is untouched. It does not roll back the reachability study's measurement either — 9 of 22, confirmed independently. What it changes is the conclusion drawn from that measurement: 1.4.3 moves from NOT_TESTED to CHECKS in this engine too (matching the sibling engine's manual → partial move in #523), because a criterion this pass can decide some of, honestly, is not the same as a criterion it cannot test at all — the same distinction the coverage-boundary amendment above draws for every other check in this file. For a remediation vendor running this candidate's audit-and-fix pass against a theme's source, 1.4.3 is real but modest automatable coverage (5.7–10.5% depending on whether the package ships CSS at all), not the sibling engine's 98.76%. The honest path to that number is upstream of this module: render the theme and hand the rendered page to the sibling engine — named as its own follow-up in "What could not be measured here" below, since it is a real piece of work and was not attempted here.

Amendment, 2026-08-21 (superseded by finding 5 above) — the 1.4.3 contrast port is not generally buildable, measured

Landed on main by a concurrent session while this directory's finding 5 was being built, and kept here rather than deleted, on the same principle ../a11y-engine-agreement/README.md states for its own superseded amendments: a declared, dated divergence is not the failure mode this repository's re-derivation problem is about, and rewriting history to hide that two sessions reached different conclusions from the same premise would be worse than showing the correction in place.

The measurement in this amendment is not wrong and is not superseded: finding 5 independently re-derives its central number (9 of 22 packages ship a literal .css file) by a different method and gets the same answer. What is superseded is the conclusion — "not proposed here" — which finding 5 revisits by actually building the resolver this amendment declined to, on the same premise that most of this codebase already uses everywhere else: decide what is decidable, name what is not, rather than declining a whole criterion because it cannot cover everything. See finding 5 for the numbers and the reasoning against this amendment's original conclusion; the original text below is preserved, with a small number of inline notes -- in parentheses, or struck through -- marking exactly where finding 5 speaks to a specific claim made here.

#523 ported colour-contrast decidability into eaa-wcag-triage/ (the sibling engine over built HTML output) and named porting the same resolver into this engine's audit.py as a follow-up — flagged there as "non-trivial … an open question rather than a port," because this engine reads source theme packages, not a rendered page with one linked, compiled stylesheet. That question is now measured rather than assumed, with measure_stylesheet_reachability.py run against the exact 22-package corpus measure_themes.py audited (pinned to the same names and versions, so both measurements describe the same population). Raw rows in results-stylesheet-reachability-2026-08-21.json.

The answer splits into two separate blockers, of unequal size:

Blocker 1 — for 7 of 22 packages, the stylesheet is not in the package at all. @nuskin/ns-shop-elements (469 class attributes across 50 markup files), @vue-storefront/nuxt-theme (399 classes, 45 files) and pinelab-storefront (183 classes, 19 files) are representative: these are component kits meant to be styled by a downstream consumer project, so there is no CSS to resolve against — not undecidable, absent. No resolver design closes this; the stylesheet genuinely is not there to read.

Blocker 2 — of the 15 packages that do ship stylesheets, 469 files are .scss against 161 .css, and only 9 packages ship any literal, unprocessed .css at all. fassbender-shopify-theme (the package #523's own template port worked from) is representative of the majority case: 74 .scss files against 3 .css files, and its _variables.scss opens with @import '../../node_modules/bootstrap/scss/variables' and a map-merge — real Sass control flow, not a file css.py's selector-and-value parser could read a colour out of without first running a Sass compiler. That is a different kind of change than the port asked for: eaa-wcag-triage/css.py is deliberately standard-library-only, no install step, per this portfolio's research-tooling norm; adding Sass compilation means either a third-party dependency or a per-package npm install + build step, which the corpus's own node_modules-relative imports show would need the package's own node_modules to resolve correctly — fragile in a way the current zero-dependency, read-only design is not. (This part of the finding stands: contrast_pass.py also does not compile Sass, and packages whose only stylesheet is .scss source are indistinguishable, in finding 5's numbers, from packages with no stylesheet at all — both report no-declared-color.)

What is not blocked. The class-attribute side of #523's concern — "class names are often built from expressions" — measures as the small problem: 138 of 8,591 class attributes (1.6%) carry a template expression across the whole corpus. audit.py's existing is_expr/refs_can_match machinery already handles exactly this case for other attributes, so if a resolvable stylesheet is ever available (say, a future stage that runs after ../a11y-render-recovery/'s theme-rendering step, where the render already implies a Sass build happened), matching a class attribute to a selector is the easy half. The stylesheet not being literal CSS in the source package is the actual blocker, and it is concentrated rather than evenly spread: of the 158 literal .css files in the whole corpus, 147 (93%) sit in just two packages — @zalify/theme-templates (117, and the only package with zero .scss at all) and @ecomplus/storefront-twbs (30, a compiled-Bootstrap bundle shipped alongside its own 204 .scss source files). The other seven packages with any literal CSS have one to three files each — plausibly a vendored reset or a single component stylesheet rather than the theme's own styling, not checked further here. A resolver built against this corpus would have real, non-trivial coverage on two packages out of twenty-two and near nothing on the rest. (Finding 5's per-package table above tests this prediction directly: @zalify/theme-templates in fact resolves 0% despite its 119 CSS files, for the reason -- heavily expression-built classes -- named two paragraphs up in this same amendment; @ecomplus/storefront-twbs resolves 100%, matching the prediction. The "near nothing on the rest" half of the prediction undershoots what the built resolver found: @pradip1995/create-storefront-app, with a single CSS file, resolves 69.4%.)

Consequence. ~~1.4.3 and 1.4.11 stay in NOT_TESTED for this engine, and should — the reason given there ("needs rendered colours; stylesheets, theme settings and images all participate") already covers this finding without needing to be rewritten.~~ Superseded by finding 5: 1.4.3 moved to CHECKS on 2026-08-21, in the same commit that built contrast_pass.py. 1.4.11 stays in NOT_TESTED, for the reason finding 5's own change to that list gives (it needs rendered geometry, not just a declared colour, so a stylesheet would not have resolved it regardless). The distinction from eaa-wcag-triage/ is not a gap in this engine; it is the two engines auditing different artifacts (source template packages vs. one project's built output) where only one of those artifacts ships a stylesheet a standard-library parser can read, and read completely — see finding 5 for what a resolver actually recovers from the fraction it can reach. Closing the rest of the gap for template packages generally would need a Sass/Less build stage, which remains a different, larger decision than a port and is still not proposed here.

What could not be measured here

  • No AT verification, so the candidate's actual kill criterion is untested. "Kill it if … AT verification finds that generated fixes close less than half of blocking issues" needs a contractor with a screen reader. Nothing here moves that.
  • ~~No generated fixes.~~ Closed 2026-08-24 for two classes, still true of every class that needs a name or a colour invented. The audit half of "audit-and-fix" has been here since this directory was built. The first defect finding 2 of the theme-resolution pass recovered by hand -- a theme that prefixes the control id and forgets the matching <label for> -- is two strings, and the pairing is unique when exactly one control in the file has that literal as its trailing text after a separator. The CLI now prints those edits in the record as proposed, not applied, with the same "not a conformance claim" framing the findings already carry, and it never writes the customer's files. Inventing alt text, a visible name, or a contrast colour is still not attempted: those are not determined by the markup.
