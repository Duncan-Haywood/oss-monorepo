# edge-api: the site's counter, feedback form and support inbox on Lambda

The AWS home of [`platform/edge`](../../../edge/README.md): the same handler the
Cloudflare Worker runs, on Lambda behind the site's CloudFront distribution,
with its data in DynamoDB. The Worker keeps serving until cutover.

Account: **apps** (beside SES, so inbound mail is one account; found from the org stack's `account_ids`). Region: **us-east-1**. Nothing here has been
applied; there is no AWS account yet.

## What it creates

| Resource | Why |
|---|---|
| Lambda `edge-api` (Node 22, arm64, 256 MB, reserved concurrency 10) | `platform/edge/aws/lambda.mjs` wrapping `worker.mjs`; zip built by `archive_file` from the repository's files, no build step and no dependencies |
| Function URL (auth `NONE`) + two invoke permissions | the CloudFront origin; every request without the `x-origin-verify` secret gets a 403 |
| DynamoDB `edge-api` (on demand, PITR, KMS, deletion protection, TTL `expires_at`) | counts, feedback, inbox, rate-limit windows (`platform/edge/aws/dynamo-store.mjs` has the key design) |
| S3 inbox bucket (private, SSE-KMS, TLS-only, 1-day expiry) | SES writes inbound support mail here (email stack); the function copies a capped 256 KB version into the table |
| Secrets `edge-api/origin-verify`, `edge-api/inbox-token` | generated by `random_password`; never typed by a person, never in the tree |
| KMS key `alias/edge-api` (rotation on) | table, bucket, logs, secrets, Lambda environment, DLQ |
| SQS `edge-api-dlq` | inbound mail the function failed on twice |
| Alarms: errors, throttles, dead letters | to `alarm_topic_arn` (the spend-guards stack's topic) once set |

### Same limits as the Worker

| Limit | Worker | Lambda |
|---|---|---|
| Feedback per sender | 3 a minute (Cloudflare rate-limit binding) | 3 a minute (a DynamoDB counter keyed by an HMAC of the viewer address; the window expires in two minutes; no address stored) |
| Feedback site-wide | `FEEDBACK_DAILY_CAP` 50 | same variable, same code path |
| Per count key | `MAX_PER_SLUG_PER_DAY` 20,000 | same |
| Inbox | 256 KB per message, 200 a day, 90 days | same; plus SES spam/virus verdicts drop mail before storage |
| Spend | free-plan daily limits | reserved concurrency 10 + the site WAF's rate rule; on-demand DynamoDB |

## What the site stack needs from here (outputs)

The site stack (another agent's) attaches this as an origin. It reads these
outputs from `edge-api/terraform.tfstate` (state keys are `<stack>/terraform.tfstate`,
as in `platform/aws/README.md`):

| Output | Use in the distribution |
|---|---|
| `origin_domain_name` | `origin { domain_name = ... }`, `custom_origin_config { origin_protocol_policy = "https-only", origin_ssl_protocols = ["TLSv1.2"] }` |
| `origin_verify_header_name`, `origin_verify_secret_arn` | `custom_header { name = "x-origin-verify", value = var.edge_origin_verify_value }`: the apply job reads the secret with the apps role and passes it as the sensitive `TF_VAR_edge_origin_verify_value`, so shared-infra holds no cross-account read on it (site stack README, "The edge API origin") |
| `origin_path_pattern` (`/_edge/*`) | `ordered_cache_behavior { path_pattern = ... }` |
| `cloudfront_cache_policy_id` | managed CachingDisabled |
| `cloudfront_origin_request_policy_id` | managed AllViewerExceptHostHeader (forwards Origin, User-Agent, DNT, Sec-GPC, Authorization, CloudFront-Viewer-Country and -Address) |
| `allowed_methods` | the behaviour's allowed methods |

Then `platform/edge/site.json` and `platform/counter/site.json` change from
the workers.dev URL to `https://marisstella.app/_edge` (one commit, after the
smoke test below). The function strips `/_edge` before routing, so the
Worker's paths are unchanged. The WAF rate-based rule that sits in front of
it belongs to the site stack; 300 requests per 5 minutes per IP on
`/_edge/*` is a sensible start (a page load sends one beacon).

## Apply order

1. **Owner, once** (AWS forces these): `platform/aws/bootstrap`, root MFA,
   card, IAM Identity Center. Then CI applies `org`, `baseline`, `spend`,
   `email` (PR #18749's stacks).
2. **This stack:** `tofu init -backend-config=backend.hcl && tofu apply -var
   state_bucket=...`. With `deploy_role_arn` null it assumes the
   organisation member role in apps, like the other stacks; once the
   github-oidc stack exists, pass `gha-oss-monorepo-edge-api-apply` and
   `permissions_boundary_arn` (the account's `workload-boundary`). Roles it
   creates are named `edge-api-*`.
3. **`email-ops`** (`../email-ops/`): it reads this stack's state for the
   inbox bucket and function.
4. **Site stack:** attaches the origin.
5. **Migrate** (twice, before and after the DNS move; it is idempotent):
   ```sh
   node platform/edge/aws/migrate-d1.mjs            # dry run: what would move
   TABLE_NAME=edge-api INBOX_TOKEN=<Worker's> node platform/edge/aws/migrate-d1.mjs --apply
   ```
   It reads the Worker's own routes (no Cloudflare token), keeps every id so
   `pull-feedback.mjs`'s cursor carries on, and only moves sequences forward.
6. **Smoke test** through CloudFront: `GET /_edge/healthz` is `ok`; a POST to
   `/_edge/hit` is a 204 and shows in `/_edge/counts`; the same request
   straight to the function URL is a 403; `GET /_edge/inbox` with the token
   from `edge-api/inbox-token` lists messages.
7. **Cutover:** the `site.json` commit above; MX moves in the email stack
   (`receive_mail = true`). The Worker stays deployed until
   `retire-cloudflare`, so rollback is reverting that commit.

## Verify locally

```sh
node --test 'platform/edge/*.test.mjs' 'platform/counter/*.test.mjs'   # Worker + Lambda + store contract + migration
cd platform/aws/stacks/edge-api
tofu fmt -check -recursive && tofu init -backend=false && tofu validate && tofu test
checkov -d . --framework terraform
```

`tofu test` runs against a mocked provider: encryption on the table, bucket,
logs and environment; all four public-access blocks; TLS-only bucket policy;
no wildcard IAM actions and no `Resource "*"` outside X-Ray; the Worker's caps
unchanged; secrets referenced by id only; the region and role validations.

CI: `platform/edge/*.test.mjs` already runs in `portfolio-validate.yml`. The
`tofu` and Checkov steps need the IaC scanning workflow (security-first
direction, another agent's); until it lands they are run by hand and the
output goes in the run record.

## Checkov skips (each with its reason in `main.tf`)

Key-policy `Resource "*"` (means the key itself); no VPC (AWS APIs only, a NAT
gateway would cost ~$32/month for no protection); no code signing yet (zip
built in CI from reviewed source; follow-up); public function URL (gated by
the origin secret); inbox-bucket access logs, replication and S3 events (one-day
staging copy, CloudTrail data events cover access, SES invokes directly);
secret rotation (see below).

## Rotating secrets

- `inbox-token`: `tofu apply -replace=random_password.inbox_token`; agents
  read the new value from Secrets Manager. The function caches it per
  container, so new containers pick it up within minutes.
- `origin-verify`: `tofu apply -replace=random_password.origin_verify` here,
  then re-run the site stack's apply job at once (it reads the new value and CloudFront sends it). Expect
  403s for the minutes between the two; do it at a quiet hour.

## Cost

At today's traffic (well under 100,000 requests a day): Lambda and DynamoDB
on demand fall inside the always-free tiers or cost cents; KMS is $1 a month
per key; Secrets Manager $0.40 per secret a month. About $2 a month in total.
