# Probes

Executable probes for candidates in [`portfolio/pipeline/`](../README.md).

A candidate write-up is an argument. A probe is the smallest working thing that
tests the argument's weakest claim. Neither is a venture: a candidate still
graduates only by one of the two paths in [../README.md](../README.md) — writing
`ventures/<name>/VENTURE.yaml`, or listing its slug under its host venture's
`product_lines` — and nothing in this directory does either, changes a score, or
creates a `ventures/` entry.

This directory exists because the pipeline had accumulated eight scored
candidates, ~20 research write-ups, and **no executable artifact for any of
them**. [`distribution-first.md`](../distribution-first.md) asked four times
over for "one probe to a real buyer," and
[`channel-inventory.md`](../channel-inventory.md) established that building a
free listing needs no credential and no capital — only publishing does. The gap
was therefore never permission or budget. Nobody had built one.

That last sentence is right about why this directory exists and wrong about what
happens next. `channel-inventory.md`'s own refutation table measures every
mapped channel as `EGRESS_DENIED` or `SCOPE_DENIED`, so a built probe is not one
approval away from a listing — publishing is blocked by network policy and app
scope, which approval does not change. Build probes here because they make a
candidate's weakest claim testable, not because a listing follows.

  A figure printed at a customer must not be able to go stale. `eaa-wcag-triage`'s
  `tests/test_accuracy_citations.py` checks each printed value against the
  research directory it cites, so a rate revised upstream fails the build rather
  than being quoted at a buyer. Copy that when you add a figure to a probe here.

  **`mcp-drift-watch`, added 2026-08-22, is the first probe built under this rule
  rather than retrofitted to it** — its record carries precision, recall, the
  direction that pays the operator and the silence caveat from its first version,
  and `test_subscriber_record.py` re-derives every printed figure from the
  committed labels rather than trusting the constant. It also shows why the rule
  needs to be about accuracy specifically: this probe's *alert rate* reproduced
  out of sample to within 0.2 points while its precision halved, so a stable rate
  is not evidence that the alerts are the right ones. Anywhere in this repository
  that a reproduced rate is doing duty for a correctness claim, it is doing the
  same thing the coverage rule used to do for accuracy.

  **Amended the same day, and it sharpens the rule rather than the example.** A
  third corpus (the remaining 103 eligible packages) put that probe's alert rate
  at 5.4% against 7.4% and 7.2%, and its precision at 0.625 against 0.40 — so
  neither the rate nor the accuracy reproduced, and *the rate is the one that
  looked stable*. The record now prints the **span across both held-out corpora**
  rather than either figure. Generalising: one held-out measurement cannot tell
  you whether its own figure is stable, so a single out-of-sample number is
  evidence that a figure was not tuned, not evidence of what the figure is. Where
  a probe here quotes one, say which corpus it came from and what a second would
  cost — `mcp-drift-watch`'s cost one command, because `collect_holdout.py`
  records the population it did not take.
- **Publishing is a separate decision from building.** A probe may be built and
  committed here freely; putting this portfolio's name on a public listing is
  the account owner's call.

## This table lags the probes, and the lag has a direction (2026-08-23)

`CLAUDE.md` routes the recurring "research new business projects" brief at this
directory — *"the useful moves are, in order: advance a probe that is already
specified in `portfolio/pipeline/`"* — so a next step named in a cell above is
what a session with no target of its own goes and does. That makes this table
load-bearing in a way a summary would not be, and it drifts in one specific
direction: **a probe's own README is updated by the pass that does the work,
while this index is updated by whoever remembers.** When they diverge, the cell
goes on advertising a step that is already closed.

Auditing all five cells against the probes' own READMEs on 2026-08-23 found
**two of five stale, both in that direction**, both closed the same day the work
they described had landed:

- **`eaa-wcag-triage`** ended at the SC 2.5.3 pass with *"2 disclosed as
  decidable but unbuilt"*. SC 1.3.4 landed later that same day. The real split
  is 18 / 9 / 1, and the single remaining row (`1.2.1`) is the only one in the
  catalog whose own note says the criterion is **not** decidable from the
  artifact. The cell advertised two buildable rules; zero existed.
- **`mcp-drift-watch`** said corpus 3's model question *"costs one run"*. That
  run was committed the same day and is the second held-out corpus on which the
  model beats the rules — the evidence that most matters to that candidate's
  `ai_leverage`. The index named it pending and omitted the result entirely.

The three cells that were current are worth reading too: `npm-reachability-triage`
is current **only because two pull requests earlier that same day
([#677](https://github.com/Duncan-Haywood/monorepo-projects/pull/677),
[#681](https://github.com/Duncan-Haywood/monorepo-projects/pull/681)) were spent
closing its stale pnpm-hand-review pointer**, after four independent sessions had
converged on that one sentence. So the observed rate is three stale pointers
across five cells within about a week, and the cost of one of them was two pull
requests and four sessions' attention — spent on a pointer rather than on a
probe.

**Why a check and not another paragraph.** `CLAUDE.md` makes exactly this
argument about itself ("this file has warned about duplicate and re-derived work
since 2026-08-18, in steadily more detail, and the re-verification share has not
fallen"). A warning here would be read by the sessions that already read
carefully and skimmed by the ones that route off the table. So the figures in
this index that a probe's own artifacts can recompute are now recomputed and
checked, by [`validate_probe_index.py`](validate_probe_index.py), which runs in
`portfolio-validate.yml` beside `validate_doc_consistency.py`. It is the
[`eaa-wcag-triage/tests/test_accuracy_citations.py`](eaa-wcag-triage/tests/test_accuracy_citations.py)
pattern — the one the rules section above already tells you to copy when you add
a figure to a probe — applied one level up, to the table that routes sessions to
the probes rather than to the record shown to a customer.

**What it does and does not catch.** Every check re-derives its number from the
probe's committed artifacts and asserts this file states it; the artifact is
always the source and the prose is always the thing checked, never the reverse.
It therefore catches a figure going stale. It **cannot** catch a cell that is
merely out of date in its narration, or that names a next step no artifact
contradicts — `mcp-drift-watch`'s pointer was catchable only because the run it
called pending had left a scored artifact behind. Auditing the cells by hand is
still the only way to find the rest, and the failure has now recurred often
enough to be worth an explicit pass rather than a glance.

## A note recorded here because it closes a standing question

`cra-evidence-desk` names EUVD integration as its wedge, and four passes
recorded that wedge as blocked after probing `euvd.enisa.europa.eu`.

That is the site host. The **API** is served from
`euvdservices.enisa.europa.eu` — documented at `euvd.enisa.europa.eu/apidoc`,
no authentication, endpoints `/api/search`, `/api/enisaid`,
`/api/lastvulnerabilities`, `/api/exploitedvulnerabilities`,
`/api/criticalvulnerabilities`, `/api/advisory`, `/api/dump/cve-euvd-mapping`
and `/api/kev/dump`.

Applying the rule from
[`feed-reachability`](../../research/data-reachability/README.md) — *probe every
channel a feed publishes, not just its canonical host* — this run probed that
second host for the first time. It is **also denied** (`connect_rejected` at
`$HTTPS_PROXY/__agentproxy/status`), and EUVD mirrors to no git or
object-storage channel.

The conclusion does not change, but its basis does: the wedge is now closed at
the address that actually serves the data, rather than assumed from the one that
serves the website. That is worth recording because the same class of error —
probing a canonical host and concluding "unreachable" — is what
`feed-reachability` was written to stop, and EUVD was the one feed nobody had
re-probed under the new rule.
