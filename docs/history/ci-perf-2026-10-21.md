# CI performance pass (2026-10-21)

The owner asked for performance engineering on the CI/CD workflows, and where
else it might pay. This builds on `pages-build-perf-2026-10-20.md`, which
handled the tools' own speed. This pass measures the runner pool.

## Why runner time matters on a free account

The repository is public, so standard runners cost no money. The
concurrent-job ceiling is the real limit. `ci_starvation.py` exists because
that pool ran dry from 2026-08-26 to 2026-09-01. Each job-minute one workflow
wastes is a minute some other PR's check waits.

## How it was measured

A new tool, `platform/ci/ci_profile.py`, reads job and step timings for the
most recent completed runs from the Actions API. It splits each job into
checkout, setup/teardown, and work, and reports job-minutes, overhead shares,
queue time and the heaviest steps for each workflow. The tests are in
`test_ci_profile.py`, run by `ci-profile-ci.yml`.

    python3 platform/ci/ci_profile.py --runs 1000 --top 30

Reading of 2026-10-21, covering 1,000 runs from 00:01 to 01:39 UTC (98
minutes):

- **1,320 jobs, 1,741 job-minutes.** That averages about 18 jobs running at
  once, near the account's ceiling. Queue time was still low (p50 3s, p90
  under 16s for every busy workflow), so the pool was full but not yet over
  its limit.
- **Checkout took 361 of the 1,741 job-minutes (21%).** Almost all of it was
  three workflows cloning full history:

| Workflow | jobs | job-min | median job | checkout share | median checkout |
|---|---|---|---|---|---|
| ventures tests | 42 | 114.7 | 107s | 60% | 95s |
| Research | 42 | 80.2 | 101s | 96% | 96s |
| Page integrity | 17 | 51.0 | 196s | 55% | 98s |

Clone timings from a cloud session (one sample each; runner times differ by a
constant factor):

| Clone | time | `.git` size |
|---|---|---|
| full (`fetch-depth: 0`) | 279s | 5.3 GB |
| blob-less (`--filter=blob:none`, full history) | 33s | 268 MB |
| depth 1 | 15s | ~160 MB |
| depth 1, then `git fetch --depth=1 origin <base>` | +1s | |

## What changed

1. **`research-ci.yml`**: removed `fetch-depth: 0`. `research/_homepage/build.py`
   never calls git. The job spent 96s cloning to do 1s of work.
2. **`ventures-tests.yml`**: depth-1 checkout, plus a step that fetches the
   one base commit. All three steps only run `git diff BASE HEAD`, which needs
   two trees, not the history between them. Checked on a fresh depth-1 clone
   with a base 25 commits back: the slug list matched the full clone's
   exactly (8 ventures), and `clauses.mjs --changed-since` passed. The fetch
   checks `--is-shallow-repository` first, as `validate_workflows.py`
   requires, so a local full clone under `run_workflow_locally.py` is never
   truncated. A base that is already present is not fetched.
3. **`page-integrity-ci.yml`** and **`a11y-external-coverage-reference-ci.yml`**:
   kept `fetch-depth: 0` and added `filter: blob:none`. Both read old commits
   on purpose: `history-blob.mjs` pins the checker against the blobs of pages
   that shipped broken. On a blob-less clone git fetches those blobs on
   demand. Results there: `node --test platform/webcheck/*.test.mjs` passed
   61 of 61 with none skipped, and the a11y suite passed 29 of 29 with none
   skipped.

Expected saving, from the window above: about 60 + 55 + 20 job-minutes per 98
minutes. That is roughly 8% of the pool, or more than one runner slot freed
all day. Each research or ventures PR also gets its check about 1.5 minutes
sooner. Re-run `ci_profile.py` after a day of merges to confirm.

## Not changed, ranked by job-minutes (for the next agent)

Search open PRs for each item's keywords before starting it.

1. **Portfolio Pages `test` job: 292 of 1,741 job-minutes, the largest single
   consumer.** `node --test "*.test.mjs"` in `platform/pages` takes 3-5
   minutes, and the job runs on every PR touching `ventures/**`, which is
   most PRs. Two options:
   - Shard it (`node --test --test-shard=i/3` in a 3-job matrix). This cuts
     PR latency but not job-minutes.
   - Run the builder suite only when `platform/pages/**` changed, and let the
     `build` job's `check.mjs` cover venture-only PRs. This cuts minutes, but
     first establish which tests read real venture content. Never drop a
     test that would catch a venture's breakage.
2. **`agent-permission-harness CI`: 262 job-minutes, median job 9 minutes.**
   It triggers on any `.github/workflows/**` change. Profile
   `python3 -m unittest discover` in
   `portfolio/pipeline/probes/agent-permission-harness/` (`-v` with
   per-test timing, or `cProfile`) before touching the trigger, whose comment
   says the wide path list is load-bearing.
3. **`hetzner-gitops CI`: 210 job-minutes.** The `gitops` job's `pytest` step
   takes about 10 minutes. It runs on changes to `platform/pages/build.mjs`
   and `platform/marketing/**`, but the origin it validates was retired on
   2026-10-01 (CLAUDE.md "Hosting"). Narrowing or retiring it is a judgment
   call about a dead route's tests, so it belongs with whoever owns
   `gitops/`. Do not just delete the checks.
4. **`Portfolio validate`: 170 job-minutes**, made of 80 serial steps. The
   largest step is "Check the apex tool mirror is not stale" (36 minutes over
   the window). Splitting it into two or three parallel jobs would cut
   latency. Total job-minutes would rise a little, from the extra checkouts.
5. **Allocator deepen** (item C of `pages-build-perf-2026-10-20.md`) is still
   open.
6. **The apex mirror check penalises anyone who edits `portfolio-validate.yml`.**
   It runs whenever that file changes. `gitops/prod/front-door/` goes stale
   with every catalogue change, and the mirror has served nothing since
   2026-10-01. On this PR the check failed twice. The second failure came
   after a regeneration, because `main` moved during the 25-minute CI run.
   This PR therefore wires its tests through `ci-profile-ci.yml` instead.
   Either regenerate the mirror on `main` automatically, or drop
   `portfolio-validate.yml` from the step's trigger regex. Both are owner-adjacent
   calls about a dead route.
