# seller-books: the Worker's cold start measured, minify ruled out, and the `inArray` audit (2026-11-28)

Perf track, "what visitors wait on" (`prompts/perf/prompt-0.md`, item 4). The perf backlog had no
agent-workable item (P063, P064 and P086 are owner rows). Bet #5 (`portfolio/monetization/bets.md`)
had app first-load and worker-test passes, but nobody had measured its Cloudflare Worker's startup.
The same pass ran today on payapps, jobshop-quote, einvoice-pro, and cmmc (PR #20142, open). Each
of those found one lever: a module-level statement, or the Anthropic SDK loaded eagerly. seller-books
has neither, so this run measured, tried the one untried lever (minification), and then took the top
item from `seller-books-worker-tests-perf-2026-11-28.md`'s ranked list: the `inArray` chunking audit.

## Readings

**The bundle.** `npx vite build` in `apps/seller-books` writes `dist/seller_books/`: `index.js`
1,593 KB plus `factory-*.js` 294 KB and `dist-*.js` 16 KB (wrangler reports 1,858 KiB, 459 KiB gzip).
That is about half of payapps' bundle. Generated bytes by source, read from the source map in
40-character steps: better-auth 322 K, our `src/worker/services` 316 K, @better-auth/core 167 K,
drizzle-orm 135 K, `src/worker/routes` 84 K, jose 77 K, hono 62 K, @noble/ciphers 45 K. No model
SDK (seller-books calls no model), and no dependency that only one route uses. Of our own files,
the largest is `services/books/service.ts` at 24 K, and the importers come to about 80 K together.

**Startup in workerd.** `npx wrangler check startup -c dist/seller_books/wrangler.json` (wrangler
4.165.0, the app's pin), "Active" CPU, 4-core cloud container. Five runs: 57.1 ms on the run that
printed it. Seven more runs, interleaved with the minified build below: 52.0, 50.3, 50.1, 50.5,
83.4, 49.1, 68.5, **median 50.5 ms**. That is lower than the other bets (payapps 68 → 52,
jobshop-quote 68 → 60) and about 5% of Cloudflare's 1 s startup limit.

**The profile.** Node with `--cpu-prof --cpu-prof-interval 50`, importing the built `index.js`,
with self time mapped through the source map: 887 samples (~44 ms). **397 (~20 ms) were V8's
`compileSourceTextModule`**, 146 (~7 ms) were zod's class set-up (`core.js init`, `mergeDefs`,
`defineBound`, from our schemas and Better Auth's), 29 were drizzle's table definitions, 17 were
Hono, and 59 were unmapped top-level code. No single hot statement like payapps'
`Intl.NumberFormat` or its AES table loop. `grep` for module-level `new Intl`, typed-array tables and
top-level loops found one: `routes/org/inventory.ts:571`, two iterations.

## Tried and dropped: minifying the Worker

Earlier passes didn't try this. The Worker bundle is not minified (Vite leaves non-client
environments unminified), and `wrangler.jsonc` sets `upload_source_maps: true`, so minifying would
not cost readable stack traces. I built it with `environments.seller_books.build.minify: true` (a
temporary config, since deleted): `index.js` 1,593 → 841 KB, factory chunk 294 → 142 KB.

| | workerd Active, 7 interleaved runs (ms) | median | Node import, 7 interleaved (ms) | median |
|---|---|---:|---|---:|
| as built | 52.0, 50.3, 50.1, 50.5, 83.4, 49.1, 68.5 | **50.5** | 110.3, 92.7, 88.7, 88.3, 101.5, 84.9, 138.8 | **92.7** |
| minified | 54.9, 48.7, 47.8, 51.0, 52.8, 55.0, 62.7 | **52.8** | 85.8, 96.1, 91.1, 87.7, 103.6, 91.3, 88.8 | **91.1** |

No difference beyond noise. V8 pre-parses function bodies lazily, so whitespace and long names cost
little. The cost is the number of functions and the work done at the top level, and minifying
changes neither. **Not changed.** The same result very likely holds for the other four bet Workers,
which share this template, so don't spend a run re-measuring it.

## The `inArray` audit, and the one fix

D1 binds at most 100 parameters per statement. `grep -rn "inArray(" ventures/*/apps/*/src/worker`
lists 75 calls in the four bet Workers that have them (payapps, jobshop-quote, cmmc, seller-books). I read each call whose list isn't a literal or already sliced:

| call | list | bound |
|---|---|---|
| payapps `tm-tickets.ts:469, 511` | ticket ids on one change order | `MAX_TM_PER_CHANGE_ORDER = 50` (schema) |
| payapps `payments.ts:269` | pay apps marked owner-paid | `MAX_OWNER_PAID_BATCH = 50` (schema) |
| payapps `timesheets.ts:413, 423` | jobs and lines on one worker's week | `TIMESHEET_MAX_ROWS` (schema) |
| payapps `estimates.ts:433` | accepted alternates | already chunked by 90 two lines up |
| jobshop `admin/metrics.ts:280` | listed accounts' org ids | already inside `allInChunks` |
| jobshop `rfq/index.ts:408, 654` | an RFQ's stale or linked parts | extraction schema `.max(50)` |
| jobshop `quotes/history.ts:136` | earlier quotes' RFQ ids | `MAX_PART_HISTORY = 10` |
| jobshop `quotes/index.ts:610` | routing ids on one quote's lines | the lines of one quote; not reached in practice |
| jobshop `customer-link.ts:406` | a quote's creator and senders | a handful of people |
| seller-books `receipts.ts:110` | expense ids | already sliced by 90 in its loop |
| **seller-books `routes/org/sales.ts:400, 405`** | **every line of one marketplace order** | **none** |

The last one has no bound. `GET /sales/:id/returned-items` for a refund that carries an order
number loads the items each line of that order sold. A bulk or wholesale order imported from Shopify
or eBay with more than about 98 lines failed with D1's "too many SQL variables", and the route
answered 500. Both lookups (current `soldBySaleId` and legacy `inventoryItemId`) now run in slices of
90 ids. Each id falls in exactly one slice, and the rows go into a map keyed by item id, as before, so
the answer is the same as one statement would give.

**Test.** `test/worker/returned-items.test.ts` gains a 120-line order, half linked the current way and
half the legacy way, plus a refund on the same order number. It expects all 120 items as
candidates. Against the old route it fails with `expected 500 to be 200`, and with the fix it
passes.

## Not changed, ranked for the next run

1. **zod's set-up, ~7 ms of a ~44 ms Node import.** This is the largest share of evaluation that is
   ours to change, but it comes from schemas declared at module top level across about 40 routes
   plus Better Auth's own. Making them lazy is a large diff for a few ms on a 50 ms start.
2. **Lazy-load the importers (~80 K generated)** behind the import route. V8 would skip compiling
   about 5% of the bundle, around 1 ms. Only worth doing together with something else.
3. **Bet Workers share template code** (the worker-tests doc's item 4 still stands). The chunk
   helper exists in payapps and jobshop as `db/in-chunks.ts` but not in seller-books or cmmc, which
   repeat `CHUNK = 90` loops inline. One shared package would let a lint rule ban unbounded `inArray`.
