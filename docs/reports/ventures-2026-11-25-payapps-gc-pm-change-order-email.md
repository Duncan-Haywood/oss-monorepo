# PayApps (bet #1): GC project manager per job, and change order email drafts

2026-11-25, ventures run. Private PR: Duncan-Haywood/private-monorepo#98.

**What landed.** This is the roadmap item "Change orders, part 4: a GC project manager contact per
job for the request", plus the email that goes with it. Each job now holds the GC's project manager
(name and email, migration 0027) next to the billing contact, on both the new-job form and the job
page. Change order requests go to the PM and pay applications go to the billing contact:

- The change order request PDF prints `Attn: <PM>` under the GC. It never prints the billing
  contact.
- Each pending change order has a new "Email" button on its row. It opens a draft to the PM, built
  from the change order as entered. If no sent date is recorded, the draft asks the PM to review and
  sign. If one is, it is a follow-up that counts the days since sending. The draft states the price
  (add or deduct), the contract-time sentence from the PDF, and the contract sum before and after
  this change order (only approved change orders count). It never claims a file is attached;
  instead the panel tells the contractor to attach the PDF from the same row. The contractor copies
  the draft or opens it in their own mail program. PayApps sends nothing.

**Why a buyer cares.** A sub can't bill change order work until the GC signs, and an unsigned
request is usually just sitting in a project manager's inbox. Before this change, the request PDF
had no addressee and nothing helped chase it. The cash page already drafts payment follow-ups to
accounts payable. Change orders now get the same help, addressed to the person who actually signs
them.

**Design choices to keep.**

- There are two contacts per job, not one. Accounts payable processes pay apps and the PM approves
  scope, so mixing them up sends the email to someone who can't act on it.
- The drafting logic is pure (`src/shared/change-order-email.ts`, no LLM). It reuses
  `scheduleText` from the request model, so the email and the PDF can't disagree, and it reuses
  `mailtoHref` from the payment follow-ups, so a hostile address can't add a recipient.
- The billing-contact component was generalised to `GcContact kind="billing"|"pm"`. The billing
  ids (`gc-billing-name`) are unchanged.
- The privacy draft now names the PM contact. `POLICY_VERSION` was not bumped: nothing has launched,
  and the drafts are still waiting for counsel.

**Verification.** Run locally in the private clone: `pnpm typecheck`; `pnpm test:unit` (37 files,
348 tests, including 7 new ones in `src/shared/change-order-email.test.ts`); `pnpm test:worker`

private PR's verification section has the final counts.
