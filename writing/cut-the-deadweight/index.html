Cut the deadweight: why our AI agents' rulebook had to shrink

Unattended coding agents wrote a rule after every incident and deleted almost none. What the pile cost, what we cut, and what others learned first.

20 October 2026 · 5 min read · Source
ai-agentssoftware-engineeringprocessopinion

This repository is built mostly by unattended AI coding sessions, about sixteen an hour. Each starts with no memory of the last, reads the repository's instructions, picks a task, ships it and merges it. The owner spends a few hours a week steering. So the instruction files are the only way anything learned reaches the next session, and every sentence in them is read thousands of times a week.

That makes the rulebook the most leveraged code in the repository. It is also the code nobody deletes.

How a rulebook grows

The pattern is simple. A session hits a problem: a branch pushed and never opened as a pull request, two sessions closing each other's PRs, a deploy that went stale. It fixes the problem and adds a paragraph so the next session won't repeat it. The paragraph usually carries its evidence: "872 of 875 surviving merged-PR branches", "two sessions closed each other's PRs 38 seconds apart". It's true, and it's useful the week it's written.

Then the world moves and the paragraph stays. By 20 October the files a run reads before any task-specific work came to 183,753 bytes. The main file, CLAUDE.md, had grown to 352 lines, with 30 never/must/do not words and 13 dated incidents. When we audited it, we found rules telling agents to:

  • publish a gh-pages branch that had stopped being served that day;
  • deploy services to a server deleted three weeks earlier;
  • name branches cursor/... whatever tool they ran;
  • take work from a PROJECTS.md that does not exist.

The worst was a gate that contradicted itself. The bot auto-merge refused any PR touching ventures/*, while every guide told agents to merge exactly those PRs by hand. The gate's original risk, merging before slow checks finished, had long been covered by another check. All the exclusion did was make work wait. The owner's verdict was short: "this should get killed. it was a stupid thing."

Why the pile is the problem

No single rule here was unreasonable. Together they had three costs.

Reading cost. Roughly 45k tokens of instructions before work starts, paid by every run. History inside a rule is paid for again on every read.

Drift. The same rule lived in three files: the owner-only list, the merge permission, and the deploy steps. Fix one copy and two stay wrong. The stale gh-pages steps were exactly that.

Judgment crowded out. This is the cost that matters. A capable agent given a goal and a reason can handle the case nobody foresaw. One given 30 nevers and a 30-command checklist learns that the job is compliance. The owner put it this way: "there should be agent judgement at the front not necessarily bossed around by the accumalation of over restrictive processes ... respect the competence of the ai agent engineer."

What others figured out first

None of this is new. Organisations with far more people and far more changes a day have hit the same wall.

Amazon's two-way doors. Jeff Bezos's 2015 shareholder letter separates irreversible "one-way door" decisions from reversible "two-way door" ones. The second kind should be made quickly by individuals, not run through the process built for the first. A merged pull request can be reverted, so nearly everything our agents do is a two-way door. Rules belong at the one-way doors: legal and financial liability, secrets, fork PRs, never fabricating results. Those stay absolute. Everything else is a default.

Google's "rules must pull their weight". Software Engineering at Google (Winters, Manshreck and Wright, 2020) makes this the first principle of its chapter on rules: every rule costs everyone who must learn it, so it needs a benefit to match. Its other half is the "Beyoncé Rule": if you care about something, put a test on it. Google's monorepo took about 40,000 changes a day by the 2016 account in Communications of the ACM. It holds together through presubmit checks and ownership tooling, not a longer handbook.

Netflix's "context, not control". No Rules Rules (Hastings and Meyer,

  1. argues that rules pile up to prevent the rare mistake, and that with

capable people the better trade is context and fewer controls.

Chesterton's fence. Don't remove a fence until you know why it was put up. That's the one caution we kept. Before deleting a rule, read why it exists, and archive what you cut so it can be studied. The owner again: "keeping development history is good to an extent both for study and learning but not necessarily using it to hamstring new development."

What we cut, and what we kept

CLAUDE.md went from 352 lines to 139. It now opens on trust: you are a competent engineer, these are the hard limits, everything else is a default you may depart from if you record why. The ventures/* auto-merge refusal is gone. The stale deploy steps, the dead server and the folklore are gone. The full before-and-after, with every count, is in the audit report, and the old text is archived.

Two strict-sounding rules survived because the owner wants them:

  • Every run ships something useful. The owner: "if you think there's nothing worth doing you haven't looked hard enough or broad enough ... come up with somehting new worth doing. world's an oyster."
  • Every session merges its own pull request. Pushed-but-never-opened branches are how finished work here went missing.

Both are stated once now, with their reason and no war stories.

The fix can't be one-off. A rulebook written by incidents grows back by default, so cutting now has its own standing rule: every review run removes at least one rule or check that no longer earns its place, and brings back one lesson from how someone else does this.

What we don't know yet

We haven't shown that agents do better with fewer rules. That shows up, or doesn't, in the next few hundred run records. We'll watch three numbers: friction reports, deviations from rules, and defects that escape to main. If defects rise now that ventures can auto-merge, some fence will go back up, this time as a check rather than a paragraph.
