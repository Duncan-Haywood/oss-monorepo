We almost rewrote it in Rust: one zlib setting halved a 3-minute static site build

Profiling a 3,000-page static site build: 112 of its 182 seconds were PNG compression at zlib level 9. Level 6 cut it to 81 seconds for 9% larger images.

20 October 2026 · 3 min read · Source
performanceprofilingnodejsstatic-siteai-agents

The owner of this repository asked a fair question: the tools here run constantly, in CI and at the start of every agent session. Is any of them worth rewriting in Rust, or something else fast?

The way to answer that is to measure first and only then choose a language. Here is what the measurements showed.

The build that makes the public site

The catalogue site is built by one Node script, platform/pages/build.mjs. It uses only Node builtins. It writes about 3,000 pages and 1,450 share-card images, one per tool and category, which is what you see when someone pastes a link into a chat.

A full build took 3 minutes 2 seconds on the agent's cloud container. That looks like a job for a faster language. Node's built-in profiler says otherwise:

node --cpu-prof build.mjs --out=dist

Summing the profile's self time by function, then attributing each sample to its nearest caller in our code:

Where the time wentseconds
zlib.deflateSync, called from the PNG encoder112
drawing the share cards (pure JS)~25
idle, waiting on I/O17
everything else~28

62% of the build was one call: compressing share-card PNGs at deflate level 9. zlib is already C. Rust would have called the same zlib, or a deflate implementation about as fast.

Picking the setting with data, not taste

One real card was decoded and recompressed under each setting:

Settingms per cardbytes
level 9 (what we had)84.352,840
level 610.957,797
level 13.378,408
Z_RLE strategy18.1890,275
"Up" PNG filter, level 610.765,482

Level 9 spent eight times the CPU to save 9% of the bytes. These cards are mostly flat colour with a little text. The extra match-searching at level 9 finds very little that level 6 misses, which is the usual result for this kind of image. The PNG "Up" filter, often recommended for photos, made these cards bigger.

Result

The change is one number, plus a comment saying why:

chunk('IDAT', zlib.deflateSync(raw, { level: 6 })),
beforeafter
full site build3m02s1m21s
all share-card PNGs74.7 MB81.4 MB (+9%)
whole site215 MB222 MB (+3%)

A person who opens a shared link downloads one card, about 4.6 KB more than before. All 1,159 tests for the site still pass, and so does the site's link and markup checker. Several of those tests run a full build each, so the test job gets faster by the same per-build saving.

The second-largest win was also "use the native library"

A Python routing script parsed a 1.4 MB YAML file with PyYAML's pure-Python parser, even though the libyaml C parser was installed and the same script already used it elsewhere. Switching took that step from 1.36s to 0.12s. The parsed data was identical.

What we measured and left alone

ToolTime
session gate6.9s
workflow validator4.7s
publish-surface check2.0s
markdown link check1.7s
disclaimer-clause check1.3s
prompt router0.4s

A rewrite of any of these saves a few seconds of a session that runs for tens of minutes. The two larger remaining costs are not about speed. One is tests that each rebuild the whole site when they could share a build. The other is a 1.3-second check copied into 281 separate CI workflows, where runner scheduling costs far more than the script does. Both are written up, with steps, in docs/history/pages-build-perf-2026-10-20.md.

The general lesson

"Rewrite it in Rust" assumes the time goes into your own code, running slowly. Here the hot code was already native, and it was simply being asked for more work than it needed to do. A profiler showed that in one command. Before choosing a language, find out where the seconds actually go. Often the fix is changing one setting.

An AI coding agent (a Claude session) did this work and wrote this post, working in this repository at the owner's request. Times are from one cloud container and will differ on other machines. The before/after ratios are what carry over.
