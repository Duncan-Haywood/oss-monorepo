SSHD_CONFIG CHECK · RUNS IN YOUR BROWSER

What will your SSH server really do?

sshd keeps the first value it reads for a setting and silently ignores the rest. On Ubuntu and Debian the first line of sshd_config pulls in every sshd_config.d/*.conf file, so a cloud-init drop-in that says PasswordAuthentication yes beats your no further down.

A drop-in named hardening without .conf is never read, and a line written flush left after a Match block still belongs to it. Paste /etc/ssh/sshd_config and its drop-ins below: this page reads them in sshd's order and shows which value wins, the lines that do nothing, and the settings that let people in more easily than you meant.

Nothing is uploaded. What you paste is read in this browser and never leaves your device, and the tool makes no network calls of its own. It reads the files, not a running server: it is not sshd -T and not a security audit.

1. Paste your sshd_config files

Name each block like its path under /etc/ssh. The block named sshd_config is read first, and its Include lines pull in the blocks they match (sshd_config.d/50-cloud-init.conf), in name order, the way sshd does. On the server, sudo head -n 200 /etc/ssh/sshd_config /etc/ssh/sshd_config.d/* shows them.

      What it checks

      • Stops sshd starting: an unknown or misspelt keyword, a value sshd does not accept (PermitRootLogin maybe), a keyword with no value, a global-only keyword (Port, Ciphers, UsePAM) inside a Match block, a bad Match line.
      • High: PermitRootLogin yes with passwords on; PermitEmptyPasswords yes; PermitUserEnvironment yes (or a list admitting LD_PRELOAD); RC4 ciphers.
      • Medium: password logins on, including by default; keyboard-interactive through PAM (UsePAM yes) even after PasswordAuthentication no; a security setting that is ignored because an earlier file set it first; a drop-in that is never read; a setting written like a global one that sits inside a Match; CBC ciphers, MD5 MACs, the 1024-bit group1 key exchange, ssh-dss; StrictModes no; IgnoreRhosts no. A Match block that turns any of these back on is reported in its scope.
      • Low: X11Forwarding yes; GatewayPorts; PermitTunnel; host-based login; MaxAuthTries over 10; LoginGraceTime 0; SHA-1 MACs, key exchange and ssh-rsa; deprecated options that do nothing; other ignored repeats.

      The reading follows OpenSSH 9.6p1's own parser (servconf.c, match.c) and the sshd_config(5) manual of that release: first value wins, case-insensitive keywords, an optional =, quotes and trailing comments, Include globs relative to /etc/ssh in byte order, a Match block running to the next Match or the end of its file, Match all, and Match values replacing global ones. It is checked against the real sshd -T of 9.6p1 on 2,000 generated configurations (parity run). This tool is not affiliated with the OpenSSH project.       Common questions

      Why is my PasswordAuthentication no ignored?

      sshd keeps the first value it reads for a setting and ignores later ones, the opposite of most config files. On Ubuntu and Debian, the first line of /etc/ssh/sshd_config is Include /etc/ssh/sshd_config.d/*.conf, so any drop-in that says PasswordAuthentication yes (cloud-init writes one, 50-cloud-init.conf, when an image asks for password logins) wins over your line further down. Put your setting in a drop-in that sorts first, such as 00-hardening.conf, or remove the other one, then check with sudo sshd -T | grep -i passwordauthentication.

      Why is my file in sshd_config.d not read?

      The stock Include line matches only names ending in .conf, so /etc/ssh/sshd_config.d/hardening or hardening.cfg is never read. Rename it, for example to 10-hardening.conf.

      Does indentation end a Match block?

      No. sshd ignores indentation: every line after a Match line belongs to that block until the next Match line or the end of the file. A setting written flush left after an indented Match body applies only to the connections that Match selects. Put global settings above the first Match, or write Match all before them; note that lines after Match all are not plain global lines: they apply to every connection and override a value set earlier in the file.

      Is PasswordAuthentication no enough to stop password logins?

      Not always. With UsePAM yes (the Ubuntu and Debian default), keyboard-interactive login asks PAM, which asks for the Unix password. KbdInteractiveAuthentication defaults to yes; Ubuntu's stock file sets it to no, but older files and other distributions may not. Set both to no unless PAM drives a second factor.

      Does a clean result mean my SSH server is secure?

      No. It reads only the patterns listed on this page, from the files you paste. It does not know your OpenSSH version's compiled-in defaults if they differ from 9.6, the keys in authorized_keys, your PAM stack, firewall or fail2ban, or which users have passwords. Confirm with sshd -T on the server, and have a qualified person review anything that protects valuable data.
