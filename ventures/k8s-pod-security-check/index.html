Common questions

What makes a Kubernetes pod spec risky?

Settings that hand a container the node or leak a credential: privileged: true, hostNetwork, hostPID or hostIPC, hostPath volumes such as /etc or the Docker socket, capabilities like SYS_ADMIN or ALL, a missing allowPrivilegeEscalation: false, running as root, a writable root filesystem, :latest images and passwords written as literal env values. Any one of them can turn a bug in one container into control of the node.

Why is privileged: true dangerous in Kubernetes?

A privileged container gets nearly every Linux capability and access to the node's devices, so a compromised process can mount the node filesystem, load kernel modules and escape to the host. Almost every real need is narrower: add one capability such as NET_ADMIN under capabilities.add, and keep privileged off.

What should securityContext contain?

A sensible baseline per container is allowPrivilegeEscalation: false, runAsNonRoot: true with a numeric runAsUser, readOnlyRootFilesystem: true, capabilities drop: [ALL] and seccompProfile type RuntimeDefault. Add back only what the workload demonstrably needs.

Does this tool send my manifests anywhere?

No. It makes no network calls at all. The YAML you paste is scanned in this page and never leaves your device, and secret values are never printed in the results.

Does a clean scan mean my cluster is secure?

No. This is a heuristic line scan, not a YAML parser, a full audit or a compliance claim. It reads only the patterns listed here, does not expand Helm templates, Kustomize overlays or anchors, and cannot see your cluster's admission policies, RBAC, network policies or images. Have a qualified person review anything that protects valuable data.
