Common questions

Why is pinning a GitHub Action to a tag like @v4 a risk?

A tag or branch name is mutable: the action's owner — or an attacker who compromises their account — can repoint it at a different commit at any time. The next time your workflow runs, it runs whatever code that tag now points to, with whatever permissions and secrets your workflow has. A full 40-character commit SHA cannot be silently repointed, which is why GitHub's own hardening guidance recommends it.

Has this actually happened?

Yes. In March 2025 the widely used tj-actions/changed-files action had its version tags repointed at a malicious commit that dumped CI secrets into logs in any workflow that referenced it by tag. Workflows that had pinned it to a commit SHA were unaffected by the retag.

Does this tool fetch anything from GitHub for me?

No. It makes no network calls at all — nothing here can, because nothing here talks to a server. For every mutable reference it finds, it prints the exact git ls-remote command you can run yourself to look up what that ref currently resolves to. The lookup, and the decision to pin, stay entirely yours.

Does a clean scan mean my repository is secure?

No. This checks one specific, well-documented thing: whether third-party uses: references are pinned to a commit SHA. It is not a security audit, and it makes no claim about your repository's overall security or compliance posture.

What about actions in my own repository?

References starting with ./ (a local composite or JavaScript action in the same repository) and docker:// (a container image reference) are skipped — neither is the third-party supply-chain risk this tool exists to catch.

Pinned SHAs stop a mutable tag from being swapped out from under you, but they don't catch every risk in a workflow: Actions Injection Check flags pwn-request checkouts and script-injection from untrusted ${{ github.event }} expressions, Actions Permissions Check flags workflows and jobs with no explicit permissions: grant or with write-all, Actions Cache Poisoning Check flags an actions/cache write reachable from a fork trigger or an unscoped restore-keys fallback, and Actions Secret Leak Check flags a step that transforms a secret before it can be masked, or exports one to $GITHUB_ENV/$GITHUB_OUTPUT without ::add-mask:: — four more slices of a hardened CI setup. The same mutable-tag-vs-pinned-reference question applies past CI, too: Docker Base Image Pin Check asks it of a Dockerfile's FROM line instead of a workflow's uses: line. A pinned, permission-scoped workflow can still leave branch protection stuck: Required Checks Drift Check flags a required status check name a renamed job, a removed job, or a dropped pull_request trigger has left nothing can ever satisfy again. And a workflow that is pinned, permission-scoped and green can still put the wrong revision live: Deploy Concurrency Check flags the ways two runs of a deploy workflow are allowed to overlap, so the one that finishes last -- not the newer one -- is what is deployed. A reference this tool marks pinned is pinned only at that one hop — Actions Transitive Pin Check fetches what a pinned reusable workflow or composite action itself loads and flags it if that is unpinned underneath, a gap this tool's own "no network calls" design cannot see into.
