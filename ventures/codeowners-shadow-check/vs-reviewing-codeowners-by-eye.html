CODEOWNERS Shadow Checker vs. reviewing CODEOWNERS by eye

Reading CODEOWNERS top to bottom is how most teams catch a shadowed rule today, because it is the only tool most reviewers reach for. It works well for a syntax mistake — a pattern missing its leading slash, an owner that is not a real handle — because those are visible on the single line you are looking at. It works badly for a shadowed rule, because last-match-wins resolution is a property of the whole file against a real path, not of any one line, and a rule added far below — possibly in an entirely different pull request, months later — can silently take over a pattern near the top without anything about that top line changing.

What each approach actually does

A reviewer eyeballing the file can confirm every pattern parses and every owner looks like a real team or handle. What they cannot easily do is resolve, for every path that actually exists in the repository, exactly which rule GitHub's last-match-wins logic would pick — that requires checking each file against every pattern below it too, for every file, which is exactly the kind of exhaustive cross-check a reviewer skimming a diff does not have time to run by hand.

CODEOWNERS Shadow Checker runs that exhaustive cross-check instead of asking a reviewer to hold it in their head. Paste the file and a file list (or let the CLI pull both from git ls-files), and it resolves every file the same way GitHub does, then names every rule that never actually wins ownership of anything in that list because a later, broader rule always overrides it.

Common questions

Isn't reading the CODEOWNERS file enough to catch a shadowed rule?

It catches an obviously wrong pattern or a typo’d username, because those are visible on the line itself. A shadowed rule is not visible on its own line at all — you have to notice that some other rule, possibly dozens of lines away or added in a completely different pull request months later, matches the same files and sits after it. That is a resolution problem across the whole file, not a reading problem on one line, and it gets harder exactly as the file grows past what a reviewer can hold in their head at once.

When is reviewing CODEOWNERS by eye actually the right call?

For a small file — a handful of rules, a handful of owners — where a reviewer can trace every pattern against the files that matter without missing an interaction. It is also the only option when there is no representative file list to check against yet, such as reviewing a brand-new CODEOWNERS file's syntax before any files exist to resolve it against. This tool needs a file list to be useful; eyeballing the file does not.

What does eyeballing the file miss that this tool catches?

The interaction between rules, specifically. A reviewer can confirm each individual pattern looks correct and each owner is a real handle. What is much harder to do by eye is resolve, for every file that actually exists in the repository, which single rule GitHub's last-match-wins logic would pick — and then notice that one particular earlier rule never wins that resolution for any file at all. This tool does exactly that resolution, against the file list you paste or the CLI reads from git, and names the dead rule directly instead of leaving a reviewer to reconstruct it.

Does this replace reviewing a CODEOWNERS change in a pull request?

No, and it is not built to. A human reviewer still decides whether the ownership a rule assigns is the ownership you actually want — whether @payments-team should review that path, whether a new broad rule is intentional. This tool answers a narrower, mechanical question underneath that judgment call: given the rules as written, does every rule you kept actually win ownership of something, or is one of them dead weight a later rule already overrides. Both are worth doing; they are not the same task.
