Will my pyproject.toml build, install and upload?

Paste your pyproject.toml. You get every line that setuptools, hatchling or flit_core will refuse, that pip will not install or that PyPI will reject on upload, plus the ones that build fine and quietly do the wrong thing: a sys_platform == 'windows' marker that is never true, a requires-python cap that hands newer Pythons an old release, Poetry's ^ in a standard dependency list. Each finding has the line and the fix.

Nothing you paste leaves this tab. The TOML reader agrees with Python's tomllib on all 717 TOML 1.0 cases of the toml-test suite, and the dependency, version and licence grammars with the packaging library on 16,000 generated strings (see the README).

What it checks

    
    
      
  • The file itself: TOML 1.0, with the line of a duplicate key or a table defined twice.
    • 
      
  • [build-system]: requires present and valid, and the package that provides your build-backend actually in it (otherwise an isolated build stops with ModuleNotFoundError); [tool.poetry.dependencies] or [tool.setuptools] that your backend never reads.
    • 
      
  • [project]: unknown keys (with the right spelling: python_requires, author, homepage...), name, a PEP 440 version (and the local +label PyPI refuses), dynamic clashes, the readme and its content type, people and e-mail addresses, URLs, scripts and entry points.
    • 
      
  • Licences (PEP 639): SPDX expressions against the SPDX list 3.27, deprecated identifiers, the table form, license-files patterns, and the licence classifier conflict, named per backend.
    • 
      
  • Dependencies (PEP 508): every string parsed the way pip parses it, Poetry's ^ and ~, direct URL references PyPI rejects, markers that compare with a value the variable never takes, extra markers in the main list, extras (PEP 685), duplicate and exact pins.
    • 
      
  • Classifiers: against PyPI's list (trove-classifiers), deprecated ones with their replacement, and Python versions that requires-python excludes.
    • 
      
  • [dependency-groups] (PEP 735): names, includes that point nowhere, and cycles.

Questions

    
Why does license = "MIT License" fail to build now?

    
Since PEP 639, a string in project.license must be an SPDX license expression such as MIT, Apache-2.0 or GPL-3.0-or-later. "MIT License" is a name, not an identifier, so setuptools, hatchling and flit_core all refuse it. Write license = "MIT" and list your licence file in license-files.

    
Can I keep the License :: classifier next to license = "MIT"?

    
With setuptools (84 tested) or flit_core, no: both stop the build and ask you to remove the classifier. hatchling 1.33 still accepts the pair. PEP 639 deprecates licence classifiers, so deleting them is the safe choice with every backend.

    
Is it bad to cap requires-python, like <3.13?

    
Usually. pip picks the newest release whose requires-python matches the running Python, so on Python 3.13 your users silently get an older release of your package, or an install error, even if the new one would work. Poetry and PDM also push the cap onto every project that depends on yours. Keep only a lower bound unless a release really cannot run on newer Pythons.

    
Why is my dependency with sys_platform == 'windows' never installed?

    
sys_platform is win32 on Windows, darwin on macOS and linux on Linux; platform_system is Windows, Darwin and Linux. A marker that compares with 'windows' is always false, so the dependency is skipped everywhere. The checker lists the value each variable really takes.

    
Which backends does the checker know?

    
It checks the standard [project] table, which every modern backend reads, and names where setuptools 84, hatchling 1.33 and flit_core 4.2 differ, from building small projects with each of them. It also checks that build-system.requires installs the backend you name for setuptools, hatchling, flit_core, poetry-core, pdm-backend, maturin, scikit-build-core, meson-python and uv_build.

    
Is anything I paste uploaded?

    
No. The checker runs in this browser tab. There are no accounts, cookies or analytics vendors, and the command-line version makes no network calls.
