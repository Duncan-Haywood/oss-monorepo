Can a fork PR's artifact get executed by your privileged workflow?

A job triggered by workflow_run runs with your repository's full GITHUB_TOKEN and secrets, even though the run it reacts to was raised by a stranger's fork. GitHub's own Actions Security Lab, and independent research from Wiz, Legit Security and Orca Security, document the resulting attack as "artifact poisoning": the fork-triggered workflow uploads an artifact, your privileged handler downloads it, and if it executes anything from that artifact, the fork gets code execution in your context. Common questions

What is GitHub Actions artifact poisoning?

A workflow triggered by workflow_run runs with the base repository's full GITHUB_TOKEN and secrets, even though the run it reacts to — typically a pull_request build or test workflow — was raised by a stranger's fork. GitHub's own Actions Security Lab, and independent research from Wiz, Legit Security and Orca Security, document artifact poisoning as the resulting attack: the fork-triggered workflow uploads an artifact, the privileged workflow_run handler downloads it, and if that handler executes anything from the downloaded content, the fork gets code execution in the privileged context.

How is this different from the pwn-request or cache-poisoning patterns?

Same trigger gate — a job reachable from an untrusted fork that a privileged workflow later trusts — applied to a third sink. Actions Injection Check flags checking out an untrusted git ref or interpolating an untrusted event expression into a shell command. Actions Cache Poisoning Check flags a fork-writable Actions cache entry a privileged workflow later restores. This flags a downloaded artifact's file contents being executed, or an artifact download with no name: pin.

Does this tool fetch anything from GitHub for me?

No. It makes no network calls at all — nothing here can, because nothing here talks to a server. Paste your workflow YAML and the scan runs entirely in this page.

Does a clean scan mean my workflow_run jobs are safe?

No. This checks two specific, narrow patterns in a single workflow file at a time. It is not a security audit and makes no claim about your repository's overall security. It assumes a workflow_run download is reading the triggering run's own artifacts, and it does not inspect what an action called by uses: does internally with a downloaded path.

Why is an unscoped download flagged even with no execution nearby?

A download-artifact step with no name: input pulls in every artifact the fork-controlled triggering run uploaded, not one specific, expected one. That widens what untrusted content enters the privileged job even if nothing in this file executes it directly — a later step, or a called action, might still read it.
