Why a subpath site cannot govern its robots.txt

Everything below follows from one sentence in the standard, and the consequence is worth more attention than the rule, because it is invisible from inside the site it affects.

Where exactly does a crawler look for robots.txt?

At the origin root, and nowhere else. RFC 9309 §2.3 fixes the location as scheme://host:port/robots.txt. The file is scoped to the origin, so one file governs every path on that host, and no per-directory file is ever consulted.

That is a deliberate design choice, not an oversight. A crawler would otherwise have to fetch and merge a file for every directory it descends into, and the rules could contradict each other at different depths.

The practical result is that a site published under a path prefix inherits a policy file it did not write and cannot edit:

https://acme.github.io/widget/       <- your site
https://acme.github.io/robots.txt    <- the file that governs it
https://acme.github.io/widget/robots.txt  <- fetched by nothing

What does this actually cost?

Sitemap auto-discovery, which is the mechanism that enumerates pages. A crawler finds a sitemap by reading the Sitemap: line out of the governing robots.txt. A sitemap advertised only from a subpath is therefore never fetched, and the URLs listed in it are never discovered that way.

There is a second cost that runs the other direction, and people notice it even less: a Disallow: written in a subpath robots.txt is equally inert. A draft section you thought you had excluded from search is not excluded from anything.

What does it not cost?

Crawling by following links, which is entirely unaffected. Any page linked from a page the crawler already knows is still reached and can still be indexed.

That is precisely why this failure is hard to spot. Some pages do get indexed. Nothing returns an error. Every tool that checks the origin root finds a perfectly healthy robots.txt — it just belongs to someone else. The gap only shows up as a slow, unexplained shortfall between how many pages you published and how many were ever found.

A measured instance

The portfolio that publishes this tool has the same defect, on the same day this page was written, and says so in its own repository rather than quietly. Its catalogue of several hundred free tools is served from a GitHub Pages project subpath; the Sitemap: line it publishes is at an address no crawler requests; and its own deployment check reports the condition as subpath-robots every time it runs.

That is the honest version of a case study: not a claim that the tool found a customer's problem, but a statement that the problem is real, current, and cost the people writing this the same thing it may be costing you.

Is a custom domain really the only complete fix?

It is the only one that restores auto-discovery itself, because it moves the site to an origin root where its own robots.txt governs. The alternatives are real and worth doing, but they are per-search-engine pushes rather than a repair to the discovery mechanism:

OptionWhat it fixesWhat it does not
Custom domainEverything here. Your robots.txt governs, auto-discovery works, your Disallow: rules apply.Costs a domain registration and a DNS record.
Direct sitemap submissionEnumeration, for the search engines you submit to.Needs a verified account per engine; covers only those engines.
IndexNowFast notification of new and changed URLs, no account needed.Google does not consume it. Bing, Yandex and Seznam do.
A complete internal link graphDiscovery, via the route that still works.Slower than a sitemap, and needs at least one inbound link from an already-crawled page.
meta name="robots"Exclusion, reliably and per page.Nothing about discovery. It is the answer to the other half of the problem.

What this tool cannot tell you

Stated plainly, because a checker that implies more than it measures is worse than none:

  • Whether any search engine has actually indexed your pages. It reasons about mechanism, never about a search engine's decisions.
  • How a specific crawler behaves in practice. Compliance with RFC 9309 is voluntary, and implementations differ in the details.
  • Whether your content ranks. Discovery is a precondition for ranking, not a cause of it.
  • What a robots.txt you have not pasted contains. The browser page makes no network calls at all; the CLI fetches only with --fetch, and only the origin-root file.
  • Whether a non-compliant crawler honours anything at all. Some ignore robots.txt entirely, which is outside what any checker can observe.
  • Anything about hosts it has no specific knowledge of. GitHub Pages and GitLab Pages are named because their ownership model is documented; every other host is reported as a generic subpath without inventing an owner for it.
