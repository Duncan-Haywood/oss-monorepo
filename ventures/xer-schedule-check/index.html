XER Schedule Check: the DCMA 14-point assessment of a P6 schedule

Open a Primavera P6 .xer export or a Microsoft Project schedule saved as XML and get the DCMA 14-point assessment with every activity behind each failing point, a critical path recomputed from the logic, the critical path test, and the faults the 14 points miss (logic loops, out-of-sequence progress, open finishes, expected finish dates that hide delay, float that no longer matches the logic). Everything runs in your browser: the schedule is never uploaded.

Float paths to any activity

Multiple float paths, in the manner of P6's "free float" option (not compared with P6's own result: no public file stores one): path 1 is the driving chain into the activity you name, each later path the next least float relative to it. Relative float is how far an activity can slip before it moves that one activity, which total float answers only for the project finish. Name an interim milestone (a handover, a permit, a sectional completion) to see what really drives it.

Float P6 does not show across calendars

Where a finish-to-finish (or start-to-finish) link joins two calendars with different working days, P6 counts the predecessor's late finish back from the successor's late finish, say Thursday 16:00. But a successor on a Friday-off calendar may just as well finish at Saturday 08:00, so a predecessor on a 7-day calendar (curing, say) can finish a day later without delaying anything, and so can the work driving it. This lists those links and every activity with more total float than P6 shows. The dates elsewhere on this page stay P6's.

Time milestones hold back across calendars

A milestone has no duration, but P6 still puts it on its own calendar. A start milestone after a Thursday 16:00 finish, on a calendar with Friday off, sits at Saturday 08:00, so a successor crew working Monday to Friday cannot start until Monday: a day lost to a zero-length activity. This schedules the file again with every milestone on a 24-hour calendar and lists the milestones that hold work back, the hours each successor loses, and how much float comes back. The dates elsewhere on this page stay P6's.

Earned value and the S-curve

From the cost (or, with no cost, the labour hours) loaded on the resource assignments and expenses: budget at completion, planned value to the data date from each assignment's planned dates, earned value from each activity's percent complete (physical, duration or units, as P6 earns it), actual cost, SPI and CPI, three estimates at completion, earned schedule (SPI(t), which does not drift back to 1.0 at the end of a late job), the curve by month and the checks a reviewer runs before paying on a cost-loaded schedule: unloaded work, cost booked on unstarted work, remaining left on finished work, progress with nothing spent, value earned far ahead of spending (front-loading), overruns, and actuals that equal earned value on almost every activity, which means they were computed from progress and the CPI proves nothing.

Time impact analysis (fragnet)

For an extension of time request, or reviewing one: write the delay event as a fragnet, the new activities it added with their working days, what each follows and what each holds up (A1030, A1030 SS, F110 FS+2; several separated by ;), and optionally the date the event happened (it starts on or after it) and an event name. +10 on an existing activity's row makes it 10 days longer. The fragnet is inserted into this update and the schedule recomputed with the file's own calendars, logic and options (AACE RP 52R-06): how far the finish and each milestone move, the float every other activity gives up, and with two or more events, each event alone, so concurrent delay shows. Download the impacted schedule as an XER to import into P6 and confirm. It models the delay; who caused it, and whether time is due, is for the contract.

Look-ahead for the site meeting

The next few weeks of work from the recomputed dates, grouped by WBS, a bar for each working day on the activity's own calendar, and a make-ready check from the logic: ready (every predecessor that gates the start has finished or started), waits on work in the look-ahead (named, with its date), waits on work outside it, or no predecessor (an open start). Crews, materials and permits are not in the file: they are the meeting's to check.

Constraints log: materials, permits, RFIs, crews (optional)

Paste the site team's constraints log from a spreadsheet, or open it as a CSV. Columns are found by name: activity ID (required; several separated by ;), constraint, type, owner, need by, expected (the date it should clear), cleared (a date, or yes/done) and notes. An activity that is ready by its logic but has an open row becomes constrained; each row gets the date the schedule needs it by and a status (overdue, late, no date, on track), and the finish is recomputed as if every open row clears on its expected date, so you can see which one to chase first. The log stays in this browser tab.

The schedule CSV lists every open activity with its recomputed early and late dates, total float and free float, beside the values the file stores. Free float matches P6's own on 19,820 of 19,822 activities in six public files.

Finish date risk (Monte Carlo)

One CPM date hides how likely it is. This runs the recomputed schedule hundreds of times with every open activity's remaining duration drawn from a range, and gives the P50 and P80 finish dates, the chance of meeting the forecast and the must-finish date, and the criticality index: how often each activity drives the finish, including near-critical work the single driving path hides.

The file stores one duration per activity, so the range below is an assumption, not data. Replace it with ranges from the people doing the work: paste one line per activity (activity ID, optimistic, most likely, pessimistic in working days) to override the default for those activities.

When an event occurs in a run, its drawn delay is added to every activity it names. Each run is also scheduled without the events, so the result shows how much contingency the register itself asks for, and ranks the events by how far they move the finish.

Resource levelling

The logic alone lets every crew work on everything at once. This delays activities that have not started until each resource stays within its maximum units per hour from the file, the way P6's Level Resources does: activities are taken by early start, ties by the file's levelling priority, then total float; each moved activity carries its successors by the same logic, lags and calendars. You get the levelled finish, every activity that moved and which resource moved it, the peak use of each resource before and after, and a bound no levelling can beat (a resource's remaining work at the limit in force on each date).

The limits come from the file. P6 gives every new resource a limit of 1 per hour (8 hours a day); if nobody set the real crew or fleet size, the levelled finish says more about that default than about the job. Use the crew size box to see the finish with bigger crews.

How it works

The file is read table by table (TASK, TASKPRED, CALENDAR, PROJECT, SCHEDOPTIONS, TASKRSRC). Each activity is scheduled on its own work calendar, holidays and changed days included, with finish-to-start, start-to-start, finish-to-finish and start-to-finish links and their lags, the project's lag-calendar and float settings, primary and secondary constraints, the planned start and must-finish-by dates, and progress at the data date under retained logic or progress override. The forward and backward passes give early and late dates, total float and free float, the same quantities P6 computes.

Checked against P6 itself: six public XER files exported from P6 versions 5.0 to 24.12, 19,822 open activities in all. Early finish, late finish and total float all equal what P6 stored on 19,820 (99.99%): 100% on five files, including a 4,200-activity hotel schedule, and 14,268 of 14,270 on a 16,000-activity programme with heavy out-of-sequence progress (the 2 left sit behind one lag lengthened after P6's last schedule run, which the tool now names). Free float equals P6's on 19,820 (99.99%). Method and every number: README.

The DCMA points use the published thresholds: 5% for logic, lags, hard constraints, high float, high duration and missed tasks; none for leads, negative float and invalid dates; 90% finish-to-start links; 0.95 for CPLI and BEI; 44 working days for high float and high duration, counted on each activity's own calendar.

Questions

Can I see a Gantt chart of an XER file without Primavera P6?

Yes. Open the XER (or a Microsoft Project XML file) and press Show Gantt chart. The WBS is drawn as a tree in P6's order with a summary bar per node that folds and opens on a click, a bar per activity with the actual part in grey and the remaining part in blue, or red when critical (by the project's own critical setting, or the longest path), milestones, the data date and must-finish lines, and optionally the relationships between the rows on screen. Level of effort and WBS summary activities get the dates P6 gives them: on the public files used for testing, 305 of 305 equal P6's stored dates to the minute. Open a baseline or last month's update next to it to see each activity's baseline bar and its finish variance in working days. The chart prints as a landscape page and downloads as a CSV. Nothing is uploaded.

Can I group an XER's activities by activity code, like Group and Sort in P6?

Yes. After opening the file, pick a code type under Group by (responsibility, area, phase, trade: the types the scheduler set up, global ones first, in P6's order) and, optionally, a second level such as the WBS. Nested codes draw as a tree, activities with no value of the type sit under "no" that type at the end, and each group gets a summary bar, a count and a fold. On the four public P6 files with codes used for testing (46 code types, 92 charts), every activity sat under exactly the value the file gives it.

What is the DCMA 14-point assessment?

A set of fourteen schedule-quality checks published by the US Defense Contract Management Agency and now used across construction and engineering: missing logic, leads, lags, relationship types, hard constraints, high float, negative float, high duration, invalid dates, resources, missed tasks, the critical path test, the critical path length index (CPLI) and the baseline execution index (BEI). Each has a published threshold.

Is my schedule uploaded anywhere?

No. The file is read and analysed in this browser tab. There is no server, no account and no analytics vendor, so a confidential project schedule never leaves your computer.

Does it recompute the schedule or trust the dates in the file?

Both. The float checks use the total float P6 stored in the file, as a reviewer would see it. Separately the tool recomputes every open activity's early and late dates from the logic, calendars, constraints and progress, uses that to run the critical path test, and lists every activity where the file's stored dates disagree with the recomputed ones. When a duration or a lag was changed after the last schedule run, it names the activity or the link and says how many of the disagreements that edit accounts for, so you can tell a file that was not rescheduled from one whose logic does not produce its dates.

How close is the recomputed schedule to P6's own?

On six public XER files exported from P6 versions 5.0 to 24.12 (19,822 open activities), early finish, late finish and total float all agree with the values P6 stored on 19,820 activities (99.99 percent), late finish on all 19,822, and free float on 19,820. Every one of the six files agrees on 99.98 to 100 percent, including a heavily progressed 16,000-activity file with over 2,000 out-of-sequence links, where the 2 that differ sit behind one lag lengthened after P6 last scheduled it.

Can I open a P6 XER file in Microsoft Project?

Yes. Open the XER here and press Download for Microsoft Project, then in Microsoft Project use File, Open and choose the .xml file (ProjectLibre and GanttProject open it too). The WBS becomes summary tasks in P6's order, each activity keeps its activity ID in the Text1 column (named Activity ID), and every calendar keeps its working week, holidays and changed days. Relationships keep their type and lag, constraints map to Project's (start on becomes must start on, on or after becomes start no earlier than, and so on), progress keeps its actual dates with the remaining work restarting where P6 has it, the planned dates become baseline 0, resources and assignments keep their hours and cost, and P6 expenses become cost resource assignments with their budget, actual and remaining cost, category and accrual (back to the same expenses on the way to P6, to the cent on 1,526 of 1,526 tested). Activity codes become text columns named after each code type (Text2 to Text30), holding each activity's code, or code and description if you tick the box, so a Project user can group by Phase, Area or Responsibility; on four public P6 files, 276,042 of 276,042 code values written read back to the same value, and MPXJ read every one under the right column name. Project has 29 spare text columns, so a file with more code types keeps the 29 most used and names the rest. Level of effort activities have no Project equivalent, so they become manually scheduled tasks on their P6 dates with their relationships listed in the task notes. On six public P6 files (21,422 activities, 54,843 relationships) every activity and relationship read back unchanged, and MPXJ, an independent open-source reader, read the same names, dates, durations, progress, logic and resource hours from the XER and from the converted file. Project schedules with its own rules: it counts lags on the successor's calendar and puts a milestone that has a predecessor at that predecessor's finish, so some dates and floats can move once Project recalculates; the tool lists what applies to your file. Nothing is uploaded.

Can it check a Microsoft Project schedule?

Yes. In Microsoft Project use File, Save As and choose XML Format, then open the .xml file here wherever an XER goes: the 14-point check, the comparison of two updates, the windows analysis, risk, levelling and the written review. Summary tasks are treated as WBS, the status date is the data date, baseline 0 gives the planned dates, lags count on the successor's calendar as Project does, and updates are matched by Unique ID so inserted rows do not break the comparison. Manually scheduled tasks, links to summary tasks and deadlines are listed in the warnings. On 102 files saved by Microsoft Project 2002 to 2019 (2,491 open tasks), early finish, late finish and total float equal Project's own on 2,442 (98 percent). Each task runs on its resources' calendars as Project schedules it, so a night-shift crew's task works nights, and in-progress work restarts at its Resume date. The rest are contoured or timephased work and split tasks, which are not modelled. The .mpp format itself cannot be read; save as XML first.

Why does missed tasks use planned dates instead of a baseline?

A single XER export usually holds only the current project, not the baseline project. P6 keeps each activity's planned start and finish, but it moves the planned dates of an activity that has not started to its early dates every time it schedules, so they stand in for the baseline only on activities that have started or finished. Late work that has not started yet is therefore not counted as missed, and both missed tasks and BEI can read better than against the true baseline. The tool says so next to the result; compare against the baseline project where you have it.

What does the critical path test do?

It adds 600 working days to an open activity on the longest path and recomputes the schedule. The project finish should move by at least that much. If it moves less, a constraint, a lag, an open end or a broken link is stopping delay from flowing through the path, and the reported critical path cannot be trusted.

Which P6 settings are honoured?

Each activity's own calendar with its holidays and changed days, the lag calendar setting, total float as finish, start or smallest float, retained logic or progress override, the project's planned start and must-finish-by date, primary and secondary constraints including as late as possible, and external dates from links to projects not in the file. Expected finish dates, when the project uses them, set the remaining duration as in P6, and each one is listed because it absorbs delay from its predecessors; resource levelling is a separate step below (it never changes the unlevelled dates the checks use).

How does the update-to-update comparison work?

Open this month's XER and last month's. Activities are matched by activity ID and relationships by predecessor, successor and type. The report lists progress claimed, actual dates edited after they were reported, logic, duration, constraint and calendar changes, float used and driving-path changes. A half-step run recomputes last month's schedule with only this month's progress applied, so the change in the forecast finish splits into the part progress caused and the part the revisions caused. On six real P6 files with 720 planted edits, every edit was reported and nothing else.

How does the windows analysis across many updates work?

Open every update of the job at once. The tool puts them in data-date order and compares each consecutive pair. For each window it reports how far the forecast finish moved, splits that by a half-step run into the part progress caused and the part revisions caused (a re-estimate on work not yet started counts as a revision), and lists the activities on the driving path at the start of the window behind it. The windows add up to the whole movement. Checked on 36 series built from six real P6 files, with 86 windows carrying planted slips, lag changes and re-estimates: every split matched and every planted change was named in its window.

Can I add a constraints log (materials, permits, RFIs) to the look-ahead?

Yes. Paste the site team's constraints log from a spreadsheet, or open it as a CSV, in the look-ahead's Constraints log box. Columns are found by name: activity ID (required; several separated by semicolons), constraint, type, owner, need by, expected (the date it should clear), cleared (a date, or yes/done) and notes. Each row gets the date the schedule needs it by, from the recomputed early start, and a status: overdue, late (it clears after the need-by day), no date, on track or cleared. Work that is ready by its logic but has an open row is marked constrained. The finish is then recomputed as if every open row clears on its expected date, and each late row is also run alone, so the rows are ranked by how far each would move the finish. The updated log downloads as a CSV for next week's meeting. On six public P6 files with planted logs, the recomputed dates equal the ones from writing the same dates into the file as P6 start-on-or-after constraints.

Can it make a three-week look-ahead from a P6 schedule?

Yes. After opening the XER, choose the number of weeks (three by default) and, if you like, a later start date. The look-ahead lists every activity with work in the window by WBS, with a bar for each working day on the activity's own calendar, critical work in red, and a make-ready check from the logic: ready when every predecessor that gates the start has finished or started, waiting on named work in the look-ahead with its date, waiting on work outside it, or an open start with no predecessor. Started work whose predecessors are not done is marked out of sequence. Print it from the browser for the site meeting or download it as a spreadsheet. On seven public P6 files, the activities in 1-, 3- and 6-week windows are the ones P6's own stored dates put there on 6,476 of 6,479 (the 3 sit behind a lag edited after P6 last scheduled the file), and all 1,259 waits it names are consistent with P6's dates.

Can it run a time impact analysis (fragnet) on a P6 schedule?

Yes. Write the delay event as a fragnet: one row per new activity with its working days, what it follows and what it holds up (for example A1030, A1030 SS or F110 FS+2), optionally the date the event happened and an event name; +10 on an existing activity makes it 10 days longer. The tool inserts the rows into a copy of the update as a scheduler would in P6, recomputes it with the file's own calendars, logic and options, and reports how far the finish and every open milestone move in working days, the float each activity gives up, and with two or more events each event alone, so concurrent delay shows. It writes a printable exhibit, a CSV and the impacted XER to import into P6. Days added to a milestone are refused, and activities whose expected finish date absorbs the delay, or whose successors are tied only to their start, are named. On six public P6 files with planted fragnets, a null fragnet moved nothing 120 of 120 times, and a new activity after an activity matched making that activity longer 115 of 115 times. It models the delay; who caused it and whether time is due is for the contract.

Can the written review include the windows analysis?

Yes. Run the windows analysis on the job's updates, including the one you are reviewing, then print the review: it gains a delay-by-window section (each window's finish movement split into progress and revisions, and the driving-path activities behind it) and two corrections. Revisions that moved the finish later are listed for the contractor to justify, medium from 5 working days. Where progress slipped the finish and revisions took back 2 or more of those days, the review asks for the recovery plan behind the shortened or re-sequenced work, since the date then holds only on paper. An optional appendix lists every activity behind every correction, not only the first 40.

Can it compute earned value and an S-curve from a cost-loaded P6 schedule?

Yes. Open the XER and press Show earned value. The budget, actual and remaining cost come from the resource assignments and project expenses (labour hours when no cost is loaded). Planned value spreads each assignment's budget over the working time of its planned dates; earned value is the budget times each activity's percent complete, physical, duration or units as P6 earns it. You get SPI, CPI, TCPI, three estimates at completion, earned schedule SPI(t), a monthly S-curve with the forecast over the recomputed dates, a WBS breakdown, and checks for unloaded work, cost on unstarted work, progress with nothing spent, front-loading, overruns, and actuals that equal earned value on nearly every activity, which means P6 computed them from progress and the CPI proves nothing. On a public 16,000-activity hospital file all 2,020 activities with actuals were like that. A file carries no timephased baseline, so planned value follows the planned dates in the file.

How does the finish date risk analysis work?

Each run draws every open activity's remaining duration from a triangular range (by default 90, 100 and 125 percent of what the file says, or your own optimistic, most likely and pessimistic days per activity), recomputes the schedule with the same engine that matches P6's dates on 99.9 percent of 19,822 activities, and records the project finish and the driving path. Over hundreds of runs that gives P50 and P80 finish dates, the chance of meeting the forecast and the must-finish date, and how often each activity drives the finish. Where parallel paths merge, the later of several uncertain paths is later on average than any one, so the single CPM date is usually below the P50. The ranges are an assumption the file cannot supply, so the result is only as good as they are; a correlation setting widens the spread when one cause, such as weather, affects many activities.

Can the risk run use the duration ranges kept in my P6 user-defined fields?

Yes. If the schedule keeps each activity's optimistic, most likely and pessimistic duration in activity UDFs (for example Optimistic Duration, Most Likely Duration and Pessimistic Duration, or Min Dur and Max Dur, or BC % and WC %), the XER carries them and the tool reads them: it recognises the fields by name, takes the unit from the name (working days, hours or percent of the remaining duration), and lets you pick other fields by hand. Without a most-likely field the file's remaining duration stands in. Activities with only some of the fields keep the default range and are named. On six public P6 files with ranges planted on 16,989 activities, the result equals the one from pasting the same numbers in 24 of 24 runs, and none of the 16 real numeric UDFs in those files was mistaken for a range.

Can I add risk register events to the Monte Carlo?

Yes. Paste one line per event with its probability, an optimistic, most likely and pessimistic delay in working days, and the activity IDs it hits. In each run the event happens with that probability and its drawn delay is added to every activity it names. Every run is also scheduled without the events using the same duration draws, so the gap between the two P80 dates is the contingency the register asks for, and each event is ranked by how much later the finish is in the runs where it happened.

How does the resource levelling work?

It takes the not-started activities that use a resource with a maximum units per hour in the file, in order of early start, ties by the file's levelling priority and then total float, and places each at the earliest time every resource it uses stays within its limit for the whole assignment. A moved activity is handed back to the same CPM engine as a start floor, so its successors move by the same logic, lags and calendars. Started work keeps its dates and counts against the limits. On six public P6 files (four with resource limits), no placed activity is ever over a limit, all 37,670 zero-lag links between unstarted activities still hold, nothing starts earlier than before, and with the limits raised a million-fold the dates equal the unlevelled ones on all 19,841 open activities. It is a serial levelling pass like P6's, not a copy of P6's code, so its dates can differ from P6's own levelled dates.

Does a pass mean the schedule is good?

No. The fourteen points are screening metrics that find common faults; a schedule can pass them all and still be unrealistic, and some failures are justified. Use the lists to decide what to fix or explain, and have a qualified scheduler review the schedule before relying on it.
