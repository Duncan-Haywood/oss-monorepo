How to run a time impact analysis on a P6 schedule

A contractor asking for more time, or an owner's rep reviewing the request, needs one number they can both check: how far did this event move the finish? A time impact analysis answers it by modelling the event. You write what the event added to the work as a fragnet, insert it into the schedule update that was in force when it happened, and recompute. Scheduling consultants charge for that model, and P6 can build it only for someone with a seat and the time to wire the activities in by hand. This tool inserts the fragnet into a copy of the XER, schedules it with the file's own calendars, logic and options, and writes the exhibit.

Open the free schedule check (open the update, then go to Time impact analysis)

Steps

  1. Export from P6, as XER, the last accepted update before the event, with its data date at or just before the event began.
  2. Open it on the tool page and write the fragnet, one row per activity: Activity ID, Name, Duration in working days, Predecessors and Successors (A1030, A1030 SS, F110 FS+2, several separated by ; or ,, as P6 and Microsoft Project export them), and optionally Not before (the date the event happened) and Event. A row with an existing activity ID and +10 as its duration makes that activity 10 working days longer. Paste it from a spreadsheet or open a CSV.
  3. Press Run time impact analysis. Read the finish before and after, each milestone's movement, the float every activity gave up, and, with two or more events, each event alone.
  4. Download the Printable exhibit (HTML) for the request, the CSV, and the Impacted schedule (XER) to import into P6 and confirm the dates there.

A worked example

On the built-in example (an invented office fit-out with its data date on 2026-04-06; press Load an example schedule, then Example fragnet), two events go in at once. CO-03 is an owner change to the level 2 MEP layout: a notice after the submittal review, not before 2026-04-08, then 12 working days of redesign and 5 of re-approval before the level 2 rough-in can start. The other is a late hardware approval that makes door and hardware procurement 25 working days longer.

Alone the two events add up to 12 working days; together they cost 9, so 3 days of the change order's delay sit on time the hardware delay had already taken. The tool reports those 3 days as overlap. Substantial completion, the milestone the contract dates, moves further than the last activity: 15 working days, from 2026-07-17 to 2026-08-07, because the hardware now drives it through the door hanging and the punch list. Fourteen activities give up float, six become critical and seven go negative against the project's must-finish date of 2026-07-31.

When the event can go more than one way

A resubmittal can come back approved or rejected; a test can pass or need rework. Add Branch group, Branch and Probability columns: rows that share a group are alternatives, the same activity ID can sit on two branches with different durations, and every combination is scheduled. The result gives the expected delay, the P50 and P80, and the delay if each branch happens, so a request can say what the event costs if the resubmittal is rejected as well as what it costs on balance.

How it was tested

No public job publishes its fragnets with P6's answer, so fragnets were planted in six public P6 files (versions 5.0 to 24.12, up to 16,000 activities) where the right answer was known another way. A zero-day milestone between two activities already linked moved nothing 120 of 120 times. A new activity inserted after an activity gave the same finish, milestones and successor start as making that activity longer by the same days 115 of 115 times, and the impacted XER read back and scheduled again gave the same finish 115 of 115 times. An activity made longer moved the finish by its days less its float on the path to the finish 112 of 120 times; the 8 others had a different calendar, a constraint or an expected finish date on the path, which the simple arithmetic leaves out and the schedule does not. Each outcome of a branched fragnet equalled a plain run of that outcome's rows 244 of 244 times. The full results are in the project's eval folder.

Things to know

  • Expected finish dates can hide a delay. If the project schedules with expected finish dates, P6 shortens an activity to keep its date, and a delay upstream disappears into it. The tool names every activity that absorbed the delay this way; tick without expected finish dates to run both schedules without them.
  • Some added days reach nothing. Days added to a milestone are refused, since a milestone has no duration. An activity whose successors are tied only to its start passes nothing on when it is longer, and the tool says so.
  • The model is only as good as the update. Open logic, hard constraints or stale progress in the update move the answer. Read the DCMA findings on the same file before relying on the delay.

Questions

What is a time impact analysis?

A prospective delay analysis. The delay event is written as a fragnet, a small network of the activities it added or lengthened, tied into the logic where the event touched the work. The fragnet is inserted into the schedule update in force just before the event, the schedule is recomputed, and the difference between the finish before and after is the delay the event caused. AACE International's Recommended Practice 52R-06 describes it, and its forensic form is MIP 3.7 in 29R-03.

What is a fragnet?

A fragment of a network: the new activities a delay event brings with it (a change notice, a redesign, a re-approval), each with a duration in working days, what it follows and what it holds up. An existing activity the event made longer can be in the fragnet too, as added days on its own row.

Which schedule update should the fragnet go into?

The last accepted update before the event, with its data date at or just before the event began. Putting it into a later update mixes the event with progress and other changes that happened after it; putting it into the baseline ignores what had already slipped.

What does each event alone mean?

With two or more events in one fragnet, the tool also runs each event on its own. If the delays alone add up to more than the delay with all of them in, the difference is time two events took on the same path at the same time. The tool reports it as overlap; whether that is concurrent delay under a contract is for the parties.

Which event caused which days when there are several?

With two or more events, the tool also inserts them one at a time in the order they happened (the earliest event date on each event's rows; an event with no date keeps its place in the fragnet) and recomputes after each, so each step is what that event adds on top of the ones before it and the steps add up to the total. Stepwise splits depend on the order: an event that uses up float leaves the next one to reach the finish, and the later event gets the days. So the same steps are run newest first and shown beside them, and the tool says when the two orders disagree. On the built-in example the owner's change (dated 8 April) adds 3 days and the late hardware approval 6 more; newest first the hardware takes all 9 and the change none.

Does it decide whether an extension of time is due?

No. It measures how far the modelled finish and milestones move. Entitlement depends on the contract, the notices given and the facts, and is for the parties, an expert or a tribunal.

Is the schedule uploaded?

No. The XER and the fragnet are read and rescheduled in your browser tab. There is no server, account or upload.
