# Microsoft Project XML to a P6 XER, checked three ways, 2026-11-21

**Question.** A planner who works in Microsoft Project is often told to submit
the schedule as a Primavera P6 XER (owners and general contractors on larger
jobs run P6). Without a P6 seat the options are a paid converter or retyping.
Does `p6xer.mjs` write an XER that P6's import would take, carrying the whole
schedule, so that P6's first schedule run gives the dates Project showed?

P6 itself was not available for this check (no seat). What stands in for it:
P6's own field lists, an independent reader of both formats (MPXJ), and this
tool's CPM engine, which reproduces P6's stored dates on 19,820 of 19,822
open activities in six real files (`eval/cpm-vs-p6-2026-11-19.md`) and
Project's on 2,442 of 2,491 tasks (`eval/cpm-vs-project-2026-11-19.md`).

**Data.**

- Every Microsoft Project XML (MSPDI) file in MPXJ's test corpus
  (github.com/joniles/mpxj, `junit/data`, sparse clone 2026-11-21; read for
  measurement, not copied here): 143 files saved by Project 2002 to 2019,
  2,520 tasks, 65 links, 181 text-field code values, 890 resources and 426
  assignments. Four files with `<Project>` inside P6's own XML format
  (APIBusinessObjects) are not MSPDI and are skipped.
- The six public P6 files of `eval/cpm-vs-p6-2026-11-19.md` (P6 5.0 to 24.12),
  for the round trip.

Command (both parts; `--write` keeps the XERs for MPXJ):

```
node eval/p6xer-check.mjs --mspdi <mpxj>/junit/data --xer <dir of the six XERs> --write <out> --json eval/p6xer-check-2026-11-21.json
python eval/p6xer-mpxj.py <mpxj>/junit/data <out> --json eval/p6xer-mpxj-2026-11-21.json
```

## 1. What P6's import needs

P6 refuses an XER whose ids are not whole numbers, whose references do not
resolve, whose activity IDs repeat, or whose project has no WBS project node;
it truncates or refuses over-long names. `mspdi.mjs`'s tables (built for the
checks) had text ids for synthetic calendars (`mspdi-24h`, `mspdi-res-1`) and
code types, no project node, no CURRTYPE, and only the fields the checks read.
`p6xer.mjs` writes every field a real P6 20.12 export carries for each table
(the `%F` lines of the 20.12 sample file, RSRC and TASKRSRC from the 24.12
one), renumbers every id, and `p6Problems` checks the result against those
rules.

**Result: 0 of 143 files, and 0 of the 6 round-tripped files, break a rule.**

## 2. Read back by this tool, against the MSPDI reading

Each XER read back with `xer.mjs` and compared with `mspdi.mjs`'s reading of
the source file: name, status, remaining duration, actual start and finish,
constraint, baseline start and finish, calendar (working periods day by day
from a month before the first date to a year after the last); every link
(type, lag); every code assignment; and the schedule, both through `cpm.mjs`
(early finish, late finish, total float on every open task).

| | Result |
|---|---|
| Activities intact on every field | **2,520 of 2,520** |
| Links (predecessor, type, lag) | **65 of 65**, 0 extra |
| Activity code assignments | **181 of 181** |
| Schedule equal (EF, LF, TF) | **2,509 of 2,509** open tasks |

Two fixes came out of this part. The first run matched 2,492 of 2,509: 17 tasks
in progress whose remaining work Project restarts later (its Resume date)
finished earlier in the XER. P6's equivalent is suspend and resume, so the
writer now puts Project's Stop (else the actual start) in `suspend_date` and
Resume in `resume_date`; all 2,509 then match. The second: two files record
actual dates after the data date. The first version moved the data date to
the latest actual; on the round trip below that shifted every date in the CCA
file (0 of 14,270 matched), whose own actuals run ten months past its status
date. Now a file's status date is always kept (and the late actuals counted
in a warning, as P6's schedule log will list them); only a file with no status
date, where the project start stands in, gets the latest actual as its data
date.

## 3. MPXJ reads the XML and the XER the same way

MPXJ 16.10 (`pip install mpxj jpype1`, with a Java runtime) read each source XML and the XER
written from it. Matched by activity ID (A + row ID x 10). A manual task not
yet started is expected back as start on or after its start (the writer's
mapping, so P6 holds it where it was typed), and MPXJ's "no constraint" is
named None for an XER and as soon as possible for an XML.

## What is not carried

Counted in the warnings for the file being converted: task notes; Project's
deadlines (no P6 field); elapsed lags on links (P6 has one lag calendar per
project, set to the successor's, as Project counts lags); cost resources
(P6 keeps such costs as expenses); custom number, date and flag fields; task
splits and contoured work. Level of effort written to Project returns as
ordinary tasks.

## Limits

Not imported into P6 itself; the field lists come from P6 20.12 and 24.12
exports, and the file is headed 20.12. Import into older P6 versions was not
tried. MPXJ's corpus is test projects, not construction schedules;
the construction-sized evidence is the round trip of the six P6 files.

## Correction, later on 2026-11-21: repeated resource IDs

Section 1's "no file breaks P6's import rules" was measured with a
`p6Problems` that did not check resource IDs. P6 needs each resource ID
(`rsrc_short_name`) to be unique, and the writer took it from Project's
Initials, which Project fills with the first letter of the name ("Resource 1",
"Resource 2" and so on are all "R"; Carpenter and Crane are both "C"). Over the
same corpus (`node eval/p6xer-resource-ids.mjs <mpxj>/junit/data`, with the
old p6xer.mjs as the second argument for the "before" row):

| | files with a repeated resource ID | repeats (of 890 resources) |
|---|---|---|
| before | 55 of 143 (7 of the 21 not under `generated/`) | 798 |
| after (repeats get -2, -3, kept within 40 characters) | 0 | 0 |

`p6Problems` now names a repeated resource ID, so the claim holds again under
the stricter check. The same run counts assignments on summary tasks, which
the writer used to drop without a warning: 2 in 1 file, now reported (summary
tasks become WBS nodes in P6, which hold no resources). Found by the red-team
run of 2026-11-21 (`prompts/runs/2026-11-21-session_01EhTJVMb6UCeWxqNoVkLkug.json`).
