# Recomputed CPM against P6's own stored dates, 2026-11-19

**Question.** Does `cpm.mjs` compute the early and late dates and total float
that Primavera P6 computed for the same schedule? An XER export stores, for every
activity, the values P6 wrote at its last schedule run (`early_end_date`,
`late_end_date`, `total_float_hr_cnt`, ...). If the engine reproduces them, its
critical path test and its "stored dates disagree with the logic" list can be
trusted.

**What it took (each rule found from a mismatch, then kept only if the totals rose):**

1. Calendars: P6's nested `clndr_data` record, with 0x7F as its line break in
   older exports and real line breaks inside a quoted field in P6 Web exports.
   Day 1 is Sunday; exception days are serial numbers from 1899-12-30.
2. Nothing unstarted starts before the project's planned start, even when the
   data date is earlier (Expressway: 0 to 823 of 823).
3. As late as possible: the early dates take up the free float, from the last
   activity back so a chain of ALAP activities moves together (hotel: 4,206 to 4,212).
4. A finish milestone after a predecessor on a longer calendar snaps forward to
   the next working start; a zero-duration task's late finish snaps back to a
   period's end (hotel 4,216; example 404 of 404).
5. Completed activities stay in the network as zero-length nodes at the data
   date, pushed later only by unfinished predecessors (out of sequence); a
   finished predecessor still passes its lag, counted from its actual finish, to
   unfinished successors (a cure time still runs).
6. A started activity (or a completed node) with a start-to-start predecessor
   waits for that predecessor's remaining work to start: lag already spent if the
   predecessor has started, still running if not. The backward pass mirrors it.
   (CCA: 10,190 at first, then 11,006, 11,716, 11,888, 11,964, 12,385 and 12,582
   as rules 5-6 and the zero-duration snap landed.)

7. *(Second pass, same day.)* A start-to-start successor of a started
   predecessor whose remaining work P6 pushed past the data date (its own
   predecessors are unfinished) waits for that remaining work: its early start is
   the later of the predecessor's remaining start (no lag; it was spent) and the
   actual start plus lag. Before, the lag from the actual start fell before the
   data date and the successor started at the data date. (CCA 12,582 to 13,709.)
8. A start-to-start link from a finished activity that P6 placed out of
   sequence passes that node on, with no lag, to started and unstarted
   successors alike (13,709 to 13,727; rule 7's backward mirror, a started
   predecessor's late start bounded by its SS successor's remaining late start
   with no lag, 13,727 to 14,047; the same for a finished predecessor, 14,047 to 14,084).
9. Finished activities are zero-length nodes in the backward pass too: each
   gets a late date (the earliest its successors allow, FS and SS with no lag)
   and bounds its own predecessors (14,084 to 14,144; to 14,181 once a finished
   node's SS link to a started or unstarted successor also carries no lag back).
   The late dates of finished nodes now equal P6's stored ones on 1,175 of
   1,534 in CCA and 21 of 21 in the 24.12 file (each was a gap before).

10. *(Third pass, same day.)* A finished activity takes no lag back from any
    link to an open successor, FS, FF and SF as well as SS: its late date is the
    successor's late start (FS) or late finish (FF, SF). Rule 5 counts the lag
    forward from the actual finish, so a cure time still delays the successor, but
    the lag does not pull the finished node's late date back. Found on a chain of
    finished nodes all 14 days early: its root was an FS lag of 168 h into a
    started activity (P6 put the node at that activity's late start). Same on an
    FF lag of 112 h. (CCA 14,181 to 14,230; finished-node late dates 1,175 to
    1,493 of 1,534.) Switch: `bwDoneFS`.
11. *(Third pass.)* An SS lag from a started predecessor that is not yet fully
    spent at the data date still runs: the successor waits for the unspent part,
    counted from the predecessor's remaining start. Before, rule 7 took the
    later of the remaining start and the actual start plus lag, which loses the
    unspent part when the remaining work was pushed out. Example: SS lag 192 h,
    176 h of it worked between the actual start and the data date; the
    remaining work starts 2011-10-01 14:36, so the successor starts 16 h of work
    later, 2011-10-03 14:36, as P6 stored (we had 10-03 08:00). It moved a chain
    of 26 activities. (CCA 14,230 to 14,256.) Switch: `ssActivePred: "maxleft"`
    (`"max"` is rule 7 alone). Its mirror in the backward pass (the late start
    bounded by the successor's late start less the unspent lag) moved nothing in
    any file and was left out.

Ablation on CCA (open activities matching all three / finished nodes' late
dates matching): both rules 14,256 / 1,493; without rule 10 14,207 / 1,175;
without rule 11 14,230 / 1,493; neither 14,181 / 1,175. The other five files
are unchanged by either.

Each rule is a `variant` switch in `cpm.mjs` (`ssActivePred`, `ssDoneNode`,
`bwSSActivePred`, `bwDoneNode`, `bwDoneSS`, `bwDoneFS`, and from the fourth pass
`bwDoneSuccLag`, `bwRsrcRemain`, `bwDoneSSLeft`, `alapActive`, `activeSSLeft`), so the run without it can be
repeated; none changed a match in the other five files.

12. *(Fourth pass, same day.)* An open predecessor's FS lag into a finished
    node does come back off. Rule 10 took no lag back *from* a finished node;
    the other direction is different: the forward pass pushes the node to the
    open predecessor's finish plus the lag, so the backward pass mirrors it,
    and the predecessor's late finish is the node's late date less the lag.
    Found on the PP2S/PP1S/PGLS 7033xx chain: the last activity fed a finished
    node FS lag 120 h, and P6's late finish was exactly 120 h of work before
    the node's. SS and FF links the same way lose 31 activities, so only FS.
    (CCA 14,256 to 14,261.) Switch: `bwDoneSuccLag: ["PR_FS"]`.
13. *(Fourth pass.)* A started activity with no remaining duration whose
    labour assignment still has work left (TASKRSRC `restart_date` to
    `reend_date`, 448.8 h on DP1CL26009C0, 239 h on D03UR26001C0) takes that
    work as its remaining duration in the backward pass: P6 rolls the
    assignment's late dates up, so the late start is that much before the late
    finish (`rem_late_start_date` is stored that way), while the early dates
    keep a zero duration. It fixed D03UR26001C0 (P6's late finish 36 days later
    than ours: an SS successor bounds the late start, the late finish is 239 h
    on) and the two DP1CL activities upstream of DP1CL26009C0. Two other
    activities of the same shape have no work left on their labour rows and
    are unchanged. (14,261 to 14,264.) Switch: `bwRsrcRemain` (`"zero"`, the
    default, only for started activities with no remaining duration; `"all"`
    for every activity gives the same count here).
14. *(Fourth pass.)* Rule 11's backward mirror does exist, into a finished
    node: a started predecessor whose SS lag is not fully spent at the data
    date starts its remaining work the unspent part before the node's late
    date. I08SL26001C0: SS lag 96 h, 28 h of it run, P6's late start 68 h
    before the node's late date. (14,264 to 14,266.) Switch: `bwDoneSSLeft`.
    Mirrored onto open successors as well, it moves nothing.
15. *(Fourth pass.)* As late as possible applies to a started activity too:
    its remaining work moves up to its successors (UP3S305509C0, 9.6 h left).
    The actual start stays. (14,266 to 14,267.) Switch: `alapActive`.
16. *(Fourth pass.)* A started predecessor whose actual start is *after* the
    data date (GV10GL10904R2: started 2012-08-11 in a schedule with data date
    2011-09-30, a data error P6 accepts) has spent none of its SS lag, so a
    started successor waits the whole lag from the predecessor's remaining
    start. Applying the unspent-lag rule to every started predecessor here
    loses 9; only the future actual start is different. (14,267 to 14,268.)
    Switch: `activeSSLeft: "future"`.

Ablation of the fourth pass on CCA (all three matching): all five rules
14,268; without rule 12 14,263; without 13 14,265; without 14 14,266; without
15 14,267; without 16 14,267; none of them 14,256. The other five files are
unchanged by any of them. Finished-node late dates matching P6: 1,493 to
1,497 of 1,534 (rule 12). Free float also rose by one (19,809 to 19,810).

17. *(Fifth pass, 2026-11-19.)* A finished activity's FS or FF lag that is
    not yet spent at the data date comes back off its late date. Rule 5 runs
    the lag forward from the actual finish; rule 10 took none of it back. The
    unspent part, `lag - work(actual finish, data date)` on the lag calendar,
    does come back, to finished and open successors alike. Found by listing
    the 37 finished nodes whose late date differed (all in CCA): they formed
    six chains, and at each chain's root P6's late date was exactly that
    unspent part before a successor's late start. PGLS103391C120 finished
    2011-09-29 00:00, one 8 h day before the data date, with an FS lag of
    240 h into a finished node: P6 has it 232 h back. PFNS103304R02 (finished
    9-20, 72 h before the data date, FS lag 96 h into an unstarted activity):
    24 h back. T20CO05305C0 (FF lag 48 h, 8 h spent): 40 h. G02BM05501C0
    (240 h, 8 h spent): 232 h. Taking the *whole* lag back instead loses 318
    (1,497 to 1,179), and taking it back only into unstarted successors loses
    231, so rule 10 was right for spent lag and wrong only for the unspent
    part. **Finished-node late dates 1,497 to 1,529 of 1,534** in CCA (21 of
    21 in the 24.12 file unchanged; the other files store none); no open
    activity's dates or float moved in any file. Switch: `bwDoneLagLeft`.
    `node eval/cpm-vs-p6.mjs` now prints this count per file
    ("finished-node late dates"); the total over six files is 1,550 of 1,555.

**What is left.** 2 CCA activities, a finish milestone and its successor
(BAFT2305509C1, SAFT2305509C0) that P6 puts 24 days earlier. Explained on
2026-11-19 (`eval/edited-lags-2026-11-19.md`): the milestone's 608 h FS lag
from a finished milestone is broken by P6's own stored dates, which leave
exactly 440 h (55 days) for it, so the lag (or the predecessor's actual
finish) changed after P6's last schedule run; no other link of 46,727 into
unstarted activities on the seven P6 files is broken. With 440 h the successor
agrees exactly and the milestone but for an overnight gap (P6 08:00 the next
working day, the engine 17:00). 5
finished CCA nodes still differ from P6's stored late dates (37 before rule
17), one chain: CFNS103317C0 and the four finished pile caps behind it on SS
links. Its root has an SS lag of 312 h, spent in 2010, to CP3S105101C0, whose
late date (2011-10-10 09:36, equal to P6's) should bound it; P6 puts the root
118.4 h of work *after* that date, which no SS rule can give. Deleting the link
does not reproduce P6 either (it then gets 2011-12-01 16:36 from its other
successors), so P6 honours the link with some offset not found; 118.4 h is
not the lag less the root's actual duration (424 h) or its planned one
(401.7 h). Free float differs on 9 activities of the 24.12 file (free float is
not used by any DCMA point). Not modelled at all: resource levelling,
expected finish dates, "make open-ended activities critical", multiple float
paths; resource assignments only through rule 13.

**Not checked.** No file here uses progress override, start or smallest float,
the successor or 24-hour lag calendar, or mandatory constraints; those paths are
covered by unit tests only. Six files from six sources is a small sample: a
seventh exporter could show a rule none of these does.
