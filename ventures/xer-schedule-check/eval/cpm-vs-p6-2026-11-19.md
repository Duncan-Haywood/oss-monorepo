# Recomputed CPM against P6's own stored dates, 2026-11-19

**Question.** Does `cpm.mjs` compute the early and late dates and total float
that Primavera P6 computed for the same schedule? An XER export stores, for every
activity, the values P6 wrote at its last schedule run (`early_end_date`,
`late_end_date`, `total_float_hr_cnt`, ...). If the engine reproduces them, its
critical path test and its "stored dates disagree with the logic" list can be
trusted.

**Data.** Six XER files from public GitHub repositories, fetched for this check
and not committed (their licences do not cover redistribution, or they have none):

| Expressway_Project.xer | 7.0 | MutahirAbbas/xer-checker @ 2296ee1, `data/` | 823 |

**Method.** `node eval/cpm-vs-p6.mjs <dir> --json eval/cpm-vs-p6-2026-11-19.json`.
An activity matches when early finish and late finish equal P6's to the minute
and total float to 0.01 h.

**What it took (each rule found from a mismatch, then kept only if the totals rose):**

1. Calendars: P6's nested `clndr_data` record, with 0x7F as its line break in
   older exports and real line breaks inside a quoted field in P6 Web exports.
   Day 1 is Sunday; exception days are serial numbers from 1899-12-30.
2. Nothing unstarted starts before the project's planned start, even when the
   data date is earlier (Expressway: 0 to 823 of 823).
3. As late as possible: the early dates take up the free float, from the last
   activity back so a chain of ALAP activities moves together (hotel: 4,206 to 4,212).
4. A finish milestone after a predecessor on a longer calendar snaps forward to
   the next working start; a zero-duration task's late finish snaps back to a
   period's end (hotel 4,216; example 404 of 404).
5. Completed activities stay in the network as zero-length nodes at the data
   date, pushed later only by unfinished predecessors (out of sequence); a
   finished predecessor still passes its lag, counted from its actual finish, to
   unfinished successors (a cure time still runs).
6. A started activity (or a completed node) with a start-to-start predecessor
   waits for that predecessor's remaining work to start: lag already spent if the
   predecessor has started, still running if not. The backward pass mirrors it.
   (CCA: 10,190 at first, then 11,006, 11,716, 11,888, 11,964, 12,385 and 12,582
   as rules 5-6 and the zero-duration snap landed.)

7. *(Second pass, same day.)* A start-to-start successor of a started
   predecessor whose remaining work P6 pushed past the data date (its own
   predecessors are unfinished) waits for that remaining work: its early start is
   the later of the predecessor's remaining start (no lag; it was spent) and the
   actual start plus lag. Before, the lag from the actual start fell before the
   data date and the successor started at the data date. (CCA 12,582 to 13,709.)
8. A start-to-start link from a finished activity that P6 placed out of
   sequence passes that node on, with no lag, to started and unstarted
   successors alike (13,709 to 13,727; rule 7's backward mirror, a started
   predecessor's late start bounded by its SS successor's remaining late start
   with no lag, 13,727 to 14,047; the same for a finished predecessor, 14,047 to 14,084).
9. Finished activities are zero-length nodes in the backward pass too: each
   gets a late date (the earliest its successors allow, FS and SS with no lag)
   and bounds its own predecessors (14,084 to 14,144; to 14,181 once a finished
   node's SS link to a started or unstarted successor also carries no lag back).
   The late dates of finished nodes now equal P6's stored ones on 1,175 of
   1,534 in CCA and 21 of 21 in the 24.12 file (each was a gap before).

Each rule is a `variant` switch in `cpm.mjs` (`ssActivePred`, `ssDoneNode`,
`bwSSActivePred`, `bwDoneNode`, `bwDoneSS`), so the run without it can be
repeated; none changed a match in the other five files.

**What is left.** 89 CCA activities: 59 with a different late finish (51
started, 8 not), and in the cases read by hand the root is a finished successor
whose own late date falls before the data date (negative float on a finished
node; P6's value is 12 to 16 days later than ours in those cases); 30 with a
different early finish (28 unstarted, 2 started), among them a started activity
whose actual start is after its remaining start and an unstarted one behind a
predecessor with no recomputed dates. 359 finished CCA nodes still differ
from P6's stored late dates. Free float differs on 43 activities of the 24.12 file (free float
is not used by any DCMA point). Not modelled at all: resource levelling,
expected finish dates, "make open-ended activities critical", multiple float
paths.

**Not checked.** No file here uses progress override, start or smallest float,
the successor or 24-hour lag calendar, or mandatory constraints; those paths are
covered by unit tests only. Six files from six sources is a small sample: a
seventh exporter could show a rule none of these does.
