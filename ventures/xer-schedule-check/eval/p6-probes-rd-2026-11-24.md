# Resource-dependent work on its crews' calendars, against P6 23.12, 2026-11-24

**Question.** The engine scheduled a resource-dependent activity
(`TT_Rsrc`) on its own calendar. P6 schedules it on its resources'
calendars. On the 338 public P6 23.12 probe files
(`eval/p6-probes-2026-11-24.md`), the engine matched P6 on all six values
for only 156 of 936 such rows, and their successors followed. How much of
that gap does a direct model of P6's rule close, and does anything else get
worse?

**Data.** The same probe set: danafitkowski/cpp-cpm-engine (MIT), commit
`f4554cb`, `validation/p6-probes/`, each file imported into Primavera P6
Professional 23.12.1 and scheduled once by its author, with P6's early and
late dates and total and free float read back per unfinished activity. Fetch:
`bash eval/corpus-fetch.sh DIR --probes`. Not committed.

## Two changes

**1. The scorer lays P6's import over each file.** Each probe folder also
holds `p6-imported-*.json`: what P6's database held after the import and
before F9. P6 re-sizes resource-dependent work when it imports it (remaining
and original durations, assignment units per hour, 1,667 TASK and TASKRSRC field changes in 228
of 294 records). The file P6 scheduled is therefore not the XER byte for byte.
`eval/p6-probes.mjs` now lays those values (activity durations; assignment
units, rates, lags, remaining start and finish) over the XER before
scheduling, as the probe author's own scorers do. `--no-import` scores the XER
as written. Laying the import with the old engine scores 2,928, not 2,953: the
resized durations are spans on the crews' calendars, which the old engine
then read on the activity calendar.

**2. The engine schedules `TT_Rsrc` work per assignment** (`cpm.mjs`,
`buildModel` collects the assignments, the forward and backward passes use
them; `variant: { rsrcDep: false }` restores the old reading):

- Each labour or nonlabour assignment (material does not drive) runs on its
  resource's calendar (the activity's calendar when the resource names none)
  for its remaining units over units per hour. With no units per hour, it
  runs the resource's working hours between its remaining start and finish
  (probe zero-units, rule ZW).
- Forward: an assignment starts at the activity's start plus its lag (lag on
  the resource's calendar). The activity runs from the earliest assignment
  start to the latest assignment finish. A finish-to-finish or
  start-to-finish requirement ends an assignment that would finish sooner at
  its resource's last close at or before the requirement, its work starting
  earlier; if no activity working time is left between that and the
  requirement, the activity finishes at the activity calendar's next opening
  (probe h9 RDSF, rule RQ).
- **The start must fall on the activity calendar.** The activity starts at
  its calendar's next opening; when the earliest assignment start lands off
  the activity calendar (a 06:00 crew on a 07:00 office calendar, or the
  crew's holiday), the remaining work moves to the activity calendar's next
  opening and every assignment runs again from there, up to two times (probe
  rd-underway: U1 restarts Tue 07:00 after a Monday crew holiday; U4, a
  weekend crew on a Monday-to-Thursday calendar, never lands, and P6 stops
  after two moves).
- Backward, the mirror: the late finish and any start bound snap to the
  activity calendar, each assignment finishes at its resource's last close at
  or before that, and the activity runs from its earliest assignment late
  start (less its lag) to its latest assignment late finish.
- Float stays on the activity calendar. On work under way, start float is
  finish float (probe h9 RDTF, rule RT).

These rules were read from the probe READMEs and fitted on the probe rows,
so the probe score is a fitted result, not a held-out test.

## Result

`node eval/p6-probes.mjs DIR/p6-probes --json eval/p6-probes-rd-2026-11-24.json` (0.6 s).

| | Rows | Before (XER as written) | After |
|---|---|---|---|
| All 337 files | 5,199 | 2,953 | **3,730** |
| Resource-dependent activities | 936 | 156 | **468** |
| In projects with resource assignments | 3,424 | 1,641 | **2,418** |
| In projects without | 1,775 | 1,312 | 1,312 |
| Touching an SF link | 300 | 147 | 230 |

Row by row against the old engine on the XERs as written: **799 rows fixed,
22 made worse** (10 zero-units, 5 h25-shapes, 4 duration-types, 1 each in
alap-rd, h23-shapes, round18). Most are assignments with no work beside ones
with work (probe zero-units' rule ZR, a late-date rule not modelled).

How the score grew, each step on top of the last:

| Step | All rows | `TT_Rsrc` rows |
|---|---|---|
| Old engine, P6's import laid | 2,928 | 170 |
| Assignments on their crews' calendars | 3,421 | 349 |
| A finish requirement with no activity time left: next opening | 3,447 | 363 |
| Start at the activity calendar's next opening | 3,513 | 389 |
| Late dates snapped to the activity calendar | 3,533 | 408 |
| Off-calendar start moves and reruns (up to two times) | 3,720 | 462 |
| No units per hour: the assignment's remaining start to finish | **3,730** | **468** |

Tried and rejected (each scored lower than the step it was tried on, so it stays off as a `variant`):

- Lag on the activity calendar, not the resource's: 3,498.
- Successors and the project finish following the *early* pair (the crews'
  unsnapped dates, which the rd-underway README says successors follow):
  3,526 with every successor, 3,693 for work under way only. The forward half
  of that is right on rd-underway (S1 starts at 18:00 in P6), but the
  backward pass then needs a matching early late pair the engine does not
  yet keep, so the late dates go wrong. This is the next item.
- Dropping no-work assignments from the dates: 3,718.

**The six real P6 files are unchanged**: `node eval/cpm-vs-p6.mjs DIR/xer`,
19,908 of 19,935 (their resource-dependent work shares one calendar with its
resources, so they do not exercise this).

## What is left

1,469 rows still differ, 468 of them on resource-dependent activities. In
order of size:

- The early pair for successors (above), with its backward mirror.
- Two or more assignments under a start bound (probe h9 rule RL: the latest
  finish any assignment gets is the activity's late finish) and an
  assignment with no work beside others in the backward pass (rule ZR).
- h23-shapes (146 early-start misses), h14 and key-activity, which stack
  these with As Late As Possible work and suspended activities.
- A real P6 file whose crews work other hours than the activity calendar:
  the probe files are synthetic, so the share on real files is not measured.
