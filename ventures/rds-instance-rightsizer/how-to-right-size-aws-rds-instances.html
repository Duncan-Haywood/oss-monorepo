How to right-size AWS RDS instances

Database instances are usually sized once, at launch, for a load that never arrived. Because an RDS instance bills every hour whether it is busy or not, the gap between the class you run and the class you need is one of the largest quiet line items on an AWS bill. Closing it is also riskier than most savings, since a resize restarts the database.

Collect four CloudWatch numbers

For each instance over a representative period (at least two weeks, including month-end or any batch window), take: CPUUtilization average and p95, the minimum FreeableMemory, and the maximum DatabaseConnections. Averages hide peaks; sizing from them is how a right-sized database falls over on the busiest day.

aws rds describe-db-instances > describe.json
node cli.mjs analyze describe.json metrics.csv --commands

Memory first, then CPU

Used memory is the class's RAM minus the minimum freeable memory. A smaller class must hold that plus headroom (20% by default). CPU is the second check: p95 usage divided by a target (60% by default) tells you how many vCPUs you need. The smallest size in the same family that satisfies both is the recommendation; the tool never changes family on its own, except for the Graviton swap below.

The other four savings

  • Graviton: db.m5/m6i to m6g, r5/r6i to r6g and t3 to t4g list lower at the same size. Supported by MySQL, PostgreSQL, MariaDB and Aurora; not Oracle or SQL Server.
  • io1 to gp3: provisioned IOPS are billed per IOPS; gp3 includes 3,000 IOPS (12,000 from 400 GiB). gp2 to gp3 is mostly a performance-baseline change at RDS list prices, so check the figure rather than assume.
  • Multi-AZ on non-prod: a standby doubles the instance and storage bill. For dev and staging, single-AZ is usually enough.
  • Idle instances: near-zero CPU and no connections. Snapshot, then stop or delete.

Under-provisioned is the other half

p95 CPU above 80% or freeable memory under 10% of RAM means the instance is at risk, not wasteful. The tool flags these as errors so a right-sizing pass never shrinks them.

Resize safely

A class change restarts the instance and fails over on Multi-AZ. Do it in a maintenance window, in non-prod first, with a snapshot behind you. aws rds modify-db-instance applies at the next maintenance window unless you pass --apply-immediately.

What this cannot see

A pasted snapshot is not your traffic. The price table is an editable list-price estimate: it ignores reserved instances, Savings Plans, region, licence-included engines and storage you cannot shrink, so the figure is an estimate, not a bill.

Common questions

When is an RDS instance over-provisioned?

When the busiest period you measured fits comfortably in a smaller class in the same family: p95 CPU well under the class's capacity and peak used memory (RAM minus minimum FreeableMemory) plus headroom under the smaller class's RAM.

Does moving to Graviton save money?

Usually yes: db.m6g, r6g and t4g list lower than db.m5/m6i, r5/r6i and t3 for the same vCPU and memory. Check your engine version supports Graviton, and test first.

Does resizing an RDS instance cause downtime?

Yes. A class change restarts the instance, with a failover on Multi-AZ, so schedule it in a maintenance window and verify in non-prod first.
