What a read-through catches reliably

A confusing sentence, a typo, a body section that contradicts itself or would not make sense to follow as written — anything that reads badly on its own terms is exactly what a careful reader is good at noticing. This tool does not replace that kind of reading.

The gap that matters most: the author is the wrong reader to judge trigger quality

This isn't a case of a reviewer missing something a careful enough read could have caught. The person best placed to write a skill's description is, by construction, the person worst placed to judge whether it gives a stranger enough to act on — they already know the trigger situation, so the description reads as complete to them whether or not it actually names it. An agent evaluating the description for the first time is in exactly the position the author cannot occupy while reading their own words. A structural check for a concrete trigger cue and real distinctive vocabulary asks a question the author's own read-through structurally cannot answer about itself, not a more careful version of the same question.

When to still read the file yourself

This tool only reports the structural patterns on its list: missing fields, vagueness heuristics, vocabulary overlap, a body-size caution. It does not understand what the instruction body actually tells the agent to do, does not judge whether the steps are correct or complete, and does not run the skill inside a real agent session to see whether it triggers. Judging the instructions themselves, and everything a structural pattern match cannot see, is still a job for reading the file yourself.

Common questions

What does a careful read-through of a SKILL.md catch reliably?

A read-through catches what reads badly: a confusing sentence, a typo, a body section that is out of order or contradicts itself, an instruction step that would not make sense to follow. Those are real defects and a careful reader finds them the same way they always have. This tool does not replace that kind of reading -- it checks a narrower, more mechanical set of things a read-through is not well positioned to catch.

Why can't the author reliably judge their own description's trigger quality?

Because the author already knows what the skill does before they read a single word of the description. Reading it back, their own knowledge fills in exactly the concrete detail -- the file type, the trigger phrase, the situation -- that a first-time reader, including an agent that has never seen the skill, does not have. The description can read as perfectly clear to the person who wrote it and still give an agent nothing concrete to match a real request against, because the two readers are not in the same position.

Why is a malformed frontmatter field hard to catch by eye?

YAML frontmatter is easy to skim as prose rather than parse as structured data -- a missing colon, a value that needed quoting and was not, or a description field that silently continued onto an indented line reads as ordinary-looking text to a human eye and can still fail to parse as the field the format expects.

Why can't a single read-through catch overlap with a sibling skill?

Because it requires holding a second file's distinctive vocabulary in mind while reading the first, across every skill in a bundle, which is not what reading one file at a time does. An agent that has several skills loaded still has to pick one per request; two descriptions that separately read fine can still share enough distinctive vocabulary to compete for the same request, and noticing that takes a direct word-by-word comparison, not a read-through of either file alone.

Does a clean result mean the skill will definitely trigger correctly?

No. This tool only reports the structural patterns on its list -- missing fields, vagueness heuristics, vocabulary overlap, a body-size caution. A skill with zero findings can still fail to trigger inside a real agent session, and a skill that trips a finding can still work fine. Every finding here is worth a look, not a verdict.
