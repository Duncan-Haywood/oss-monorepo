This checker vs. pasting the introspection query in by hand

The usual way to check whether a GraphQL endpoint has introspection enabled is to open your GraphQL IDE, an API client, or curl, paste in { __schema { types { name fields { name } } } }, and see whether a schema comes back. That answers the yes/no question fine. It works much less well the moment the schema is large enough that the useful next questions -- how much of this is write surface, and which of these hundreds of field names are worth a second look -- require reading every field by eye rather than getting a yes or no.

What each one is for

Pasting the query in by hand is free and needs no tool beyond whatever HTTP client you already have open. It works well as a quick sanity check on an endpoint you already half-expect to be misconfigured.

This checker sends the identical query, then classifies the result: it counts query, mutation, and subscription fields separately, flags a non-empty mutation surface as the higher-severity case, and scans field names for common sensitive-operation wording -- the bookkeeping a raw JSON read has to do silently, in your head, across however many fields the schema exposes.

Common questions

Isn't the introspection query itself the same either way?

Yes -- this checker sends the identical unauthenticated introspection query you would paste into your own GraphQL IDE or API client. What differs is what happens to the response. Reading raw JSON tells you introspection answered; it does not, by itself, count how many of those fields sit under mutationType versus queryType, or scan every field name against a list of common sensitive-operation wording.

Why does it matter whether a field is on the query type or the mutation type?

Because the risk is different. A queryable field that should not be readable is a data-exposure question; a mutation field is a write operation -- something a caller can invoke, not just read about. GraphQL's introspection JSON nests both under the same top-level __schema.types array with no visual separator, so noticing that the exposed schema includes mutation fields, not just query fields, means cross-referencing every field back to whichever root type it hangs off, by hand, across however many types the schema defines. This checker raises its introspection-enabled finding to danger severity specifically because a non-empty mutation surface was found, and notice otherwise.

Can I just search the JSON for words like "admin" or "delete"?

You can, and on a small schema that works. It stops scaling once the schema has hundreds of fields spread across dozens of types, because a text search finds the word wherever it appears -- in a type name, a description string, an argument -- not specifically in a field name on the query or mutation root, and it does not distinguish a hit that is more concerning (a mutation named resetUserPassword) from one that is merely worth a second look (a query named adminNotes). This checker runs its sensitive-word match only against query and mutation field names specifically, and reports the two lists with different severities.

Does this replace checking the schema by hand?

No -- a sensitive-sounding field name is a hint to review by hand, not proof of a missing access control, and this checker says so on its own results page. What it removes is the bookkeeping step of finding which fields deserve that closer look in the first place, out of however many the schema exposes.

Is anything I enter uploaded anywhere, either way?

Pasting a query into your own GraphQL IDE or API client sends it straight to the endpoint you name, through no third party. This checker's browser version does exactly the same -- the request goes from your tab straight to the endpoint -- and its CLI's request goes straight from your machine. Neither this page nor this site ever sees the endpoint, the query, or the response.

Evidence, not a determination. A sensitive-sounding field name, from either process, is a hint to review by hand, not proof of a missing access control.
