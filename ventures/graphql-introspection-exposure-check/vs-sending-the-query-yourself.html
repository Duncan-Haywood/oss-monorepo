GraphQL Introspection Exposure Checker vs. sending the query yourself

Pasting {"query":"{__schema{queryType{name}}}"} into curl, Postman, or a GraphQL client and reading what comes back is a real, fast way to answer the basic question: does this endpoint answer an unauthenticated introspection query at all. That single request genuinely settles the obvious case, and it is the method most developers reach for first. This page names no product or company being compared against — "sending the query yourself" is a generic manual habit, not a competing tool.

Two worked examples

The ambiguous-error case. An endpoint returns HTTP 200 with a body carrying {"errors":[{"message":"Introspection is not allowed"}]} and no data key. That is actually good news — a hardened server explicitly refusing the query — but it looks identical, at a glance, to a misconfigured proxy returning a generic JSON error for a URL that is not a GraphQL endpoint at all. This checker reads the error message text, matches the word "introspection", and reports a confirmed, deliberate block rather than lumping it in with "we don't know what this response means."

The buried mutation name. A schema with 340 query fields and 28 mutation fields answers in full. Somewhere in the 28 is adminResetUserPassword. A person who has already confirmed "yes, introspection is on" from the first screenful of query names has little reason to keep scrolling through the mutation list looking for anything unusual. This checker's word-list match against every mutation field name surfaces it as a danger-severity finding on every run, whether it is the first check or the fiftieth.

When to still just send the query yourself

If you only need a one-off sanity check on an endpoint you already suspect, and you already know to distinguish an "introspection disabled" error from a "this isn't GraphQL" error, sending the query yourself is fine — it costs nothing and you are already there. The gap this tool closes is correctness on the two cases above, consistent scanning of every field name rather than a first-screenful skim, and repeatability: the same classification, run again on every deploy, with an exit code a CI pipeline can act on.

Common questions

Isn't sending an introspection query with curl or Postman enough?

For the obvious case, yes: send {"query":"{__schema{queryType{name}}}"} and if you get real schema data back, introspection is enabled. That single request genuinely settles the yes/no question most of the time. Where it stops being enough is judging severity and reading an ambiguous response, both of which this checker does for you.

What does an ambiguous response look like, and why is it easy to misjudge by hand?

Some endpoints return HTTP 200 with a body carrying only an errors array and no data key at all -- which can mean "introspection is explicitly disabled" (a hardened GraphQL server) or "this URL isn't a GraphQL endpoint" (a generic API error, a proxy's JSON error page, a typo'd path). Both look like an error object to someone skimming the response. This checker distinguishes them: it pattern-matches the error message for the word "introspection" to report a real, deliberate block, and separately flags a response with neither a data nor an errors key as incomplete rather than silently calling it clean.

Why is scanning the returned schema for sensitive field names hard to do by hand?

A real production schema commonly returns hundreds of query and mutation field names in one response. Scrolling that JSON looking for anything that sounds like adminResetPassword or internalGrantRole among 300 other names is exactly the kind of task a person's attention skips fields on, especially the second or third time they run the check. This checker runs the same fixed word list against every field name on every run, so it never gets tired partway through the list.

Why does it matter whether mutations are called out separately from queries?

A schema dump doesn't visually separate "things that read data" from "things that write data" -- queryType and mutationType are just two more keys in the same JSON tree. Someone confirming "yes, introspection answered" can see that and stop reading, without registering that the same response also handed over the full list of mutation names -- the write surface. This checker raises a danger-severity finding specifically when mutationType is non-null, rather than treating every introspection response the same.

Evidence, not a determination. This checks one specific, well-documented exposure class — an unauthenticated introspection query answered by the one endpoint you give it. A clean report describes what that one request found, not a guarantee the API has no other access-control gaps.
