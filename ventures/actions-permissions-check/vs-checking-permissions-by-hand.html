Actions Permissions Check vs. checking permissions by hand

Reading a workflow file with the pattern already in mind -- a missing permissions: block, or an explicit write-all -- genuinely works, and it is the method most people already use. This page names no product or company being compared against: checking permissions by hand is a generic manual habit, not a competing tool.

The gap that matters most is not the obvious write-all grant -- most reviewers catch that one -- it is the job that inherits a permission nobody re-checked at the job level, in a file with more than one or two jobs.

Common questions

What does checking a workflow's permissions by hand actually catch?

A reviewer who knows to look can spot a top-level permissions: write-all grant, or a workflow with no permissions: block at all, on a short file with one job. That review genuinely works, and it is the method most people already use -- this tool checks the same two classifications, explicit and write-all, plus unspecified for a block that is simply missing.

Why is a job that inherits the workflow's grant easy to miss?

A job with no permissions: block of its own does not run with no permissions -- it inherits whatever the workflow-level block grants, or the repository's ambient default if the workflow has no block either. A reviewer has to hold the workflow-level grant in mind while reading every job below it and notice which ones never override it, and a workflow with several jobs makes that easy to lose track of partway through. This tool checks every job against the workflow-level grant it actually inherits, every time, and labels the inherited case explicitly rather than leaving it implicit.

Why is checking every job in a file, not just the first permissions: line, easy to under-do?

A workflow file with five jobs can carry a tight, explicit permissions: block on the first job and no block at all on the other four -- and a reviewer who confirms the first block looks right has a natural stopping point that is not actually the end of the file. This tool scans every job's own body for the shallowest permissions: key inside it, independently, so a block on job one has no bearing on whether job four gets checked.

Does this tool know my repository's actual default token permissions?

No, and neither can a reviewer looking only at the workflow file. There is no public GitHub API that reports a repository's or organization's default GITHUB_TOKEN permissions setting, so an unspecified finding here -- like an unspecified finding from a careful manual read -- is a prompt to check Settings -> Actions -> General yourself, not a claim that the ambient default is definitely too broad.

Does this replace deciding what scopes a job actually needs?

No. This tool only classifies each grant as explicit, write-all, or unspecified -- it has no opinion on whether an explicit contents: read grant is itself more than a given job needs. Deciding the minimum scope a job actually requires, the way GitHub's own token-permissions hardening guidance describes, is still a job for reading the workflow yourself.
