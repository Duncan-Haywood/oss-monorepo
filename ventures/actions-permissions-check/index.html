Common questions

Why does a missing permissions: block matter?

A workflow or job with no permissions: key runs with whatever your repository or organization's default GITHUB_TOKEN permissions are set to. Many repositories still default to read-write on every scope — it was GitHub's own default for repositories created before 2023-02-02. A workflow triggered by something an outside contributor can influence then runs with a token that can push commits or modify repository settings, even if the job only needed to read the checkout.

What is permissions: write-all and why is it risky?

write-all explicitly grants every scope write access, which is broader than almost any job actually needs. It replaces an ambient, hidden default with an explicit, but still overly broad, grant.

Does this tool know my repository's actual default token permissions?

No. There is no public API for that setting, and this tool makes no network calls of any kind. An unspecified finding means the workflow file itself does not make the permissions explicit — it does not mean your repository is definitely misconfigured, only that this file does not say.

Does a clean scan mean my workflow is secure?

No. This checks one specific, well-documented thing: whether a permissions block exists and is not write-all. It does not judge whether the scopes a workflow does declare are the minimum a job actually needs, and it makes no claim about your repository's overall security or compliance posture.

What should I put in a permissions: block?

GitHub's own guidance is to start from contents: read at the workflow level and add only the specific scope a job needs, such as pull-requests: write for a job that comments on PRs. This tool does not decide that for you — it only tells you where nothing has been decided yet.
