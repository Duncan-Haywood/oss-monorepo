Actions Permissions Check vs. auditing workflow permissions by hand

This checker's own README states the job it replaces: opening each workflow file by hand and checking whether permissions: was set on the workflow and on every one of its jobs. Below is a worked example -- 3 small workflow files, 5 jobs -- run through the checker's own code, showing exactly what that manual read has to track and the two ways it goes wrong.

What each approach does

Reading the files by hand means opening every workflow under .github/workflows/, checking whether it has a top-level permissions: key, then opening each job inside it and checking whether that job has its own permissions: key too -- because a job's grant can be absent (it inherits the workflow's, or the repository's ambient default if the workflow has none either), explicit, or wider than the workflow-level line above it. Nothing marks which case you are in except by comparing the job to the workflow yourself, file by file.

This checker runs the same classification -- explicit, write-all, or unspecified -- against every workflow and job you paste at once, and prints a file:line table instead of asking you to hold the workflow-level grant in memory while you read down through its jobs. It runs entirely in your browser; nothing you paste is uploaded, and it makes no network call of its own.

Where to answer each question.
QuestionWhere to answer it
Does this one workflow file set permissions:?Either -- reading one small file by eye is fast and this tool does not claim otherwise.
Does every job in a file with a workflow-level grant still need checking individually?Yes either way, but this checker does it for every job in every file you paste in one pass, instead of you re-reading each job against the workflow-level line above it.
Which jobs are silently inheriting write-all because they declare nothing of their own?This checker's file:line table marks these explicitly ("inherited from the workflow-level permissions"). By hand, an inheriting job looks identical to one inheriting a safe ambient default -- nothing is written on the job either way.
Which jobs re-declare broader permissions than the workflow-level block suggested?This checker lists every job-level grant on its own line, including ones that widen what the workflow declared. By hand this requires re-checking every job even after confirming the workflow-level block looks safe.
I need this to work on a private repository's workflow, or a file I have not pushed anywhere.This checker -- no token, no repository access, nothing leaves your browser.

A worked example: 3 files, 5 jobs

Three small, realistic workflow files. Pasting all three into the checker at once, or running check.py against a directory containing them, produces the same file:line table shown below -- computed by this venture's own classify.mjs, not typed in by hand.

ci.yml -- no permissions: anywhere in the file

name: CI
on: [push, pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm test
  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm run lint

Neither the workflow nor either job declares a permissions: key, so both jobs run with whatever the repository or organization's ambient default token permissions are -- 2 unspecified findings (job:test, job:lint). Nothing in the file itself says so; you would have to already know the repository's Settings → Actions → General default to know how much access that ambient grant actually is.

release.yml -- workflow-level write-all

name: Release
on:
  push:
    tags: ['v*']
permissions: write-all
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm run build
  publish:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      packages: write
    steps:
      - run: npm publish

The workflow-level grant is write-all -- every scope's write access. job:publish narrows its own grant to contents: read, packages: write, an explicit finding, exactly the fix you would want. But job:build declares nothing of its own, so it silently inherits write-all -- and on the page, a job with no permissions: block looks exactly like job:test above, even though one inherits an unknown ambient default and the other inherits every scope's write access. Reading the file top to bottom, it is easy to see publish narrowed correctly, credit the file as "fixed," and never notice build never got its own block.

deploy.yml -- workflow-level grant looks safe, a job widens it

name: Deploy
on:
  push:
    branches: [main]
permissions:
  contents: read
jobs:
  deploy:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      deployments: write
    steps:
      - run: ./deploy.sh

Here the workflow-level block reads as the safe case -- contents: read only, an explicit finding, and a reviewer checking just the top of the file has every reason to move on. But job:deploy re-declares its own permissions: block adding deployments: write -- also explicit, and not wrong on its own terms, but it is a real grant the workflow-level line never mentioned. A read that stops at the workflow-level block, which is the one place most eyes land first, misses it entirely.

A real repository with dozens of workflow files and several jobs each is the same read repeated dozens of times over, and it has to be redone by hand after every edit to any one of them.

Common questions

Why not just read the workflow files myself?

You can, and for one small file it is fast. The cost shows up as files and jobs multiply: this tool's own worked example is only 3 workflow files and 5 jobs, and answering the permissions question by hand there already means opening 3 files and checking a workflow-level block plus every one of 5 job-level blocks separately -- 8 separate places to read, cross-reference, and remember, before you have found a single risky grant. A repository with 20 workflow files averaging 3 jobs each is the same read done 60-plus times, and it has to be redone after every edit.

What does a manual read actually miss?

Two specific, opposite mistakes, both present in this page's own worked example. First, a job with no permissions block of its own looks identical on the page whether it is inheriting the repository's ambient default or inheriting an explicit workflow-level permissions: write-all -- nothing is written on the job either way, so a reviewer has to hold the workflow-level line in mind while reading every job below it, and a job added later, after the reviewer's eyes have moved on, inherits write-all with nothing on the job itself to flag it. Second, the reverse: a workflow-level permissions: contents: read reads as safe, and a reviewer who stops at the top of the file misses that one job further down re-declares its own broader permissions: block -- adding write access the workflow-level line never granted. Both mistakes are about permissions declared somewhere other than where the reviewer is currently looking, which is exactly what a single eyeball pass over one file at a time does not surface.

Are these findings invented for this page, or did the tool actually produce them?

They come from running this checker's own classify.mjs against the three workflow snippets shown below, the same module the browser page runs and that check.py mirrors line for line. Every count on this page -- 3 files, 5 jobs, 7 findings, 4 flagged as write-all or unspecified, 3 explicit -- is that function's real return value on that exact input, asserted in this venture's own test suite, not typed in by hand.

Does this replace reading the workflow file at all?

No. The checker tells you which workflow or job has no explicit permissions block, or has write-all, and where -- file and line. It does not know whether the scopes a job does declare are the minimum that job's steps actually need, and it does not replace understanding what a workflow does. What it removes is the part that does not need judgment: finding every place a grant is missing, ambient, or wider than the line above it suggested, across every file at once instead of one file, one job, at a time.
