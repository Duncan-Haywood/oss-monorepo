Prefer a CLI, or want this as a CI gate?

The CLI fetches the file over real HTTP, tries /.well-known/security.txt first and the legacy root copy second, and adds the two checks a paste cannot support — the served location and the media type: 

node check.mjs example.com
node check.mjs example.com --json
node check.mjs https://example.com/.well-known/security.txt --timeout 5000

Get check.mjs, engine.mjs and fetch-url.mjs from the repo — plain Node 18+, nothing to install. It only ever talks to the host you name; nothing goes through this site. Exit code 1 on a danger-severity finding or when no security.txt could be fetched at all, 0 otherwise.

This is the one check in this catalogue worth scheduling. Every other conformance rule here is stable once fixed — but Expires is a date, so a file that passes today fails on its own, with no commit and no deploy to blame. A monthly CI run is how you find out before a researcher does.

Common questions

What does an expired security.txt actually break?

RFC 9116 says data in an expired file must be considered stale and should not be used. So once the Expires date passes, a conforming researcher or automated tool treats your file as if it published no contact at all — even though the server is still serving it and it still looks fine to a human reading it. Nothing goes red, nothing 404s, and the file quietly stops doing its job. That is why Expires is the field this tool checks first.

Why does Contact have to be a URI?

RFC 9116 defines Contact as a URI field so that a consumer can act on it without guessing what kind of thing it is. security@example.com could be an address or a username; mailto:security@example.com cannot be anything else. Write a web form as https:, an email address as mailto:, and a phone number as tel:. A bare address is the single most common conformance failure after the expiry date.

Where does the file have to live?

At /.well-known/security.txt. A copy at the site root is tolerated by some tooling for historical reasons, but conforming consumers look under /.well-known/ and will not find a root-only copy. The browser tool here cannot see where your file is served from — you pasted the text, not the URL — so that check is one the CLI does.

Is this a security assessment?

No. It checks whether one text file conforms to the rules RFC 9116 states about that file. It does not test the site, scan for vulnerabilities, verify that anyone reads the address you publish, or confirm that the people behind it respond. A perfectly conforming security.txt on an unmaintained inbox passes every check here.
