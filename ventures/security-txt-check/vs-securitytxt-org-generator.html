This tool vs. securitytxt.org's generator and validator

securitytxt.org is the reference site for the format — it is where most people first meet security.txt, and it offers a form that generates a file and a validator that checks one. If you do not have a security.txt yet, start there: filling in a form is a better way to produce a first file than reading an RFC.

This tool is aimed at a different moment. Not "help me write one", but "the one we wrote eighteen months ago — is it still doing anything?" Those turn out to want different shapes.

The difference in one sentence

A generator is used once. Expires is a date, so conformance is not a one-time state — which means the useful tool is the one you can put on a schedule and forget, rather than the one you have to remember to revisit.

When securitytxt.org is the better answer

  • You are publishing for the first time. A form that emits a correct file beats a checker that tells you the file you do not have is missing.
  • You want the canonical reading of the spec. It is the format's own site; this is a third-party checker with no special authority.
  • You want to sign the file interactively. Nothing here generates or signs keys — this tool only reads what you already have.

When this one is

  • You want to find out before a researcher does. An expired file serves a 200, reads correctly, and publishes nothing to a conforming consumer. Only a deliberate check catches that.
  • You want it automated. One scheduled job, no account, no form:
node check.mjs example.com   # exit 1 once Expires has passed
  • You manage more than one domain. A form is per-file; a CLI is a loop.
  • You would rather not paste it into a website at all. The browser page here never uploads what you type, and the CLI talks only to the host you name.

Using both is the sensible answer

Generate the file at securitytxt.org, publish it at /.well-known/security.txt, then put node check.mjs yourdomain.com on a monthly schedule so the expiry date stops being something you have to hold in your head. The two tools are not really competing; they cover the start and the middle of the same job.

Common questions

Should I use this or securitytxt.org?

If you do not have a security.txt yet, start at securitytxt.org: filling in a form is a better way to produce a first file than reading an RFC. Come back here for the question that arrives later, which is whether the file you already published is still doing anything. The two cover the start and the middle of the same job, and using both is the sensible answer.

Why does a security.txt need re-checking at all?

Because Expires is a date. A generator is used once, but RFC 9116 makes the expiry field mandatory and time-bound, so conformance is not a one-time state — which means the useful tool is the one you can put on a schedule and forget, rather than the one you have to remember to revisit.
