CYCLEHOUND · CIRCULAR IMPORT CHECKER · RUST + WEBASSEMBLY · RUNS IN YOUR BROWSER

Which of your files import each other in a circle?

Pick a JavaScript or TypeScript project folder and cyclehound draws its import graph, then lists every loop in it: which files, and the file and line of each import that closes the loop. A loop works until the day a module uses something it imported while the files are still loading; this shows you the loops before that day.

Nothing is uploaded. Your files are read by this tab and given to a WebAssembly module from this site; the page makes no network requests of its own after it loads.

How it works

  1. Read the imports of every file with a small lexer that skips comments, strings, template literals and regular expressions, so "import x from './y'" inside a string is not an import. It finds import ... from, import "x", export ... from, import("x") and require("x"), each with its line number.
  2. Resolve each relative import the way bundlers and TypeScript do: the exact file, then each extension, then index in a folder, and ./x.js written for a file that is really x.ts. Package imports are left out.
  3. Group the files into strongly connected components (Tarjan's algorithm): sets in which every file can reach every other through imports. Every circular import lives inside one.
  4. List a shortest loop through each file of each component, with duplicates removed, so every file on a loop is shown and each loop is as short as it can be.

On the command line

git clone --depth 1 --filter=blob:none --sparse https://github.com/duncan-haywood/oss-monorepo
cd oss-monorepo && git sparse-checkout set ventures/cyclehound
cargo install --path ventures/cyclehound

cyclehound src/                                  # every loop; exit 1 if there is one (a CI gate)
cyclehound --no-type --no-dynamic src/           # only loops that run at load time
cyclehound --json src/ > cycles.json              # components, loops, edges with line numbers
cyclehound --graph --json src/ > graph.json       # the whole graph, in madge's --json shape
cyclehound --unresolved src/                     # relative imports that point at no file
cyclehound --orphans src/                        # files nothing imports

Needs a Rust toolchain (rustup). Respects .gitignore. cyclehound --help lists every option.

When to use something else

  • madge when you want a picture of the graph, or your imports go through webpack, Vite or TypeScript path aliases (@/lib/x): madge reads those settings and cyclehound does not.
  • dependency-cruiser when you want rules beyond cycles: which folders may import which, banned packages, orphans by pattern, and its many report formats.
  • Your linter's import rules (for example import/no-cycle in eslint-plugin-import) when you want the warning in your editor as you type.

Questions

Is my code uploaded?

No. The folder you pick is read by this browser tab and handed to a WebAssembly module loaded from this site. The page makes no network requests of its own after it loads.

Is a circular import a bug?

Not by itself. ES modules allow cycles, and code that only uses the imported names inside functions works. A cycle breaks when a module uses an imported value while the files are still loading, which depends on which file loads first, so it can pass every test and fail when someone adds a new entry point. Cycles are worth knowing about and usually worth removing.

How is this different from madge?

On 11,422 .mjs files madge 8.0.0 took 14 to 18 seconds and about 350 MB; cyclehound took 0.2 seconds and 20 MB and produced the same graph, edge for edge, once its require() edges were switched off. madge draws graph images, has many configuration options and reads webpack and TypeScript path aliases; cyclehound does not.

Why does it list fewer cycles than madge?

It groups files into components first: every file in a component can reach every other through imports. Then it lists a shortest cycle through each file. Every file on any cycle appears, but the list stays short; the number of distinct cycles in a tangled component can grow very fast.
