How AI coding plan pricing actually works

Every flat-rate AI coding plan — Claude Pro/Max, Cursor, GitHub Copilot, ChatGPT Plus — is really a bet the vendor is making about your usage against what the same work would cost billed per token. Whether that bet pays off for you depends on numbers neither pricing page shows side by side.

Why cache reads are the number that decides it

An agentic coding session does not send one prompt and get one reply. It resends the system prompt, the tool definitions, the files it has already read, and most of the prior conversation on nearly every turn, because the model has no memory between calls otherwise. Providers that support prompt caching bill that repeated, unchanged block at a small fraction of the fresh-input rate — often around a tenth — specifically because it costs the provider far less to serve a cache hit than to reprocess the same tokens from scratch.

Publicly reported breakdowns of heavy Claude Code usage put cache reads above 90% of total tokens processed, with fresh input and output together under a few percent. A calculator that multiplies "tokens" by one blended rate treats a cache read as if it cost as much as fresh input, which overstates the API-equivalent cost by a large factor for exactly the heavy users who are the ones actually asking "is my plan worth it?" That is why this calculator asks for fresh input, output, cache write, and cache read separately.

The two things a subscription is actually pricing

ModelWhat you're really buying
Flat-rate planA usage allowance (often soft, reset-based, or "fair use") at a fixed monthly price, regardless of your actual token mix. The vendor is pooling risk across many users' usage patterns.
Pay-per-token APIExactly what you use, at published per-token rates, with no allowance to hit or reset to wait out — but no ceiling either if usage spikes.

Neither is "correct" on its own — a light user well under a plan's allowance is very likely leaving money on the table by paying the flat rate; a heavy user who keeps hitting a five-hour usage reset is very likely leaving money on the table too, in the form of blocked time the API model would not have cost them. The calculator's break-even figure is the usage level where the two cross for your own numbers.

What happens after the allowance runs out

The comparison above quietly assumes the flat fee buys unlimited usage. For a light user it does. For the heavy agentic user actually asking this question it usually does not, and the error runs one way: treating a metered plan as unlimited always flatters the subscription, because it books the overflow at nothing.

Enter an allowance in the calculator's optional field and the plan side gets an honest total — the flat fee, plus whatever runs past the allowance priced at the same API rates as the other column. It also names the active day you exhaust it on, which is often the more useful number: "you run out on day 14" tells you something a monthly average hides.

That changes the shape of the break-even question, and the answer is not intuitive. Below the allowance, growing usage pushes the API column up while the plan stays flat, so the two cross somewhere — that is the usual break-even. Above it, both columns grow at exactly the same per-token rate, so the gap between them stops moving. It settles at the value of your allowance at those rates, minus what you pay for it. Past that point more usage does not change the answer at all: the only things that move it are the rates and the size of the allowance.

One consequence worth naming, because it is the whole decision for a heavy user: if your allowance is worth less at API rates than the fee you pay for it, no amount of extra usage will ever make the plan win. The usual advice to "use it more to get your money's worth" is only true up to the ceiling.

The calculator ships no default allowance for any named plan, on purpose. Vendors publish these limits in messages, "premium requests", or rolling five-hour windows — not in tokens — so there is no sourced figure to pre-fill, and a made-up one would be worse than an empty field. Your own estimate, from your own usage, is the number that belongs there.

Seats change the comparison, not just the total

Business and team subscription tiers are priced per seat, and the API-equivalent side scales with actual usage, not headcount — a team where three of five seats are light users is a very different comparison from one where all five run agentic loops most of the day. Enter the seat count that matches your plan and let the usage fields reflect a typical member, or run the calculator once per usage band if your team is uneven.

Questions

Why do cache reads matter so much more than input or output tokens?

An agentic coding session resends the system prompt, the tool definitions, the files it has already read, and most of the prior conversation on nearly every turn, because the model has no memory between calls otherwise. Providers that support prompt caching bill that repeated, unchanged block at a small fraction of the fresh-input rate, and publicly reported breakdowns of heavy Claude Code usage put cache reads above 90% of total tokens processed.

Is a subscription always cheaper for a heavy user?

Not automatically. It depends on the plan price, the model's API rates, and how many of your tokens are cheap cache reads versus expensive fresh input and output. A heavy user whose sessions are mostly cache reads can still come out ahead on the API for some models and plans, which is why the calculator asks for your own numbers rather than assuming a verdict.

Do seats change which option is cheaper?

Yes. Business and team subscription tiers are priced per seat, and the API-equivalent side scales with actual usage, not headcount, so a team with uneven usage across seats is a different comparison from a single heavy user.
