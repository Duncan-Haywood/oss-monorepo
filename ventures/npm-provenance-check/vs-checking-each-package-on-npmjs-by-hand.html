npm Provenance Check vs. checking each package on npmjs.com by hand

Opening one package's npmjs.com page and checking its provenance badge works fine for a single dependency you're curious about. It does not scale to a package-lock.json with dozens or hundreds of packages, each needing the right resolved version's page found, checked, and the result written down — which is what this free, no-upload checker does in one pass from a pasted file.

Where checking it yourself stops being enough

Anyone curious about one specific dependency already does this: open its page on npmjs.com, switch to the version you actually have installed, and look for the provenance badge. For a single package that's a minute of clicking. The problem is a real dependency tree is rarely one package — it's a package-lock.json with dozens of direct and transitive entries, and the manual version of this check does not get easier per-package as the list grows.

Common questions

Can't I just look up each package on npmjs.com myself?

For one package, yes -- open its npmjs.com page, find the version you actually installed, and check whether that version's page shows a provenance badge. What doesn't scale is doing that for every package in a package-lock.json: each one needs its own page found, the specific resolved version located among however many versions that project has published, and the result written down somewhere before you move to the next package. This tool resolves and checks every package in a pasted file in one pass.

Why is matching the right resolved version easy to get wrong by hand?

A package-lock.json records the exact resolved version npm installed for every direct and transitive dependency, but npmjs.com's package page shows the badge for whichever version you land on -- by default the latest, not necessarily the one your lockfile pins. Finding the one version page that matches what your lockfile actually resolved, for every package in the file, is the kind of lookup that is reliable when a tool does it the same way every time and error-prone when it depends on remembering to change the version dropdown before reading the badge.

Why is it easy to lose track partway through a long dependency list?

A typical project's package-lock.json runs to dozens or hundreds of direct and transitive dependencies. Checking each one by hand means repeating the same several clicks -- find the package, switch to the resolved version, look for the provenance badge, note the result -- over and over, with no running tally except what you remember or type into a separate note. It is the same kind of repetitive, easy-to-drop-a-row task a mechanical pass through a pasted lockfile does exactly the same way every time.

What do I get from a manual check that this tool doesn't produce?

Nothing extra -- both read the same registry facts. What a manual pass through npmjs.com doesn't produce on its own is a single list of which packages in your file lack an attestation, in a form you can hand to a teammate, paste into a migration tracker, or feed to another script. This tool's CLI emits that list as JSON in one run; a manual check produces only whatever you wrote down yourself.

Is this page making a live comparison against a tool or company?

No. This page describes a manual habit any maintainer or reviewer already has -- opening a package's npmjs.com page and checking its provenance badge before trusting it. It names no competing product or company. This tool makes only read-only requests to the public npm registry, the same facts a manual page visit would show.
