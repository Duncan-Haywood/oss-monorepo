This checker vs. eslint-plugin-obsidianmd

Different setups, and one check neither tool shares: eslint-plugin-obsidianmd is Obsidian's own official ESLint plugin -- install, configure a TypeScript project, and run it as part of your normal lint pass. This tool needs no install at all, and it is the one that cross-checks manifest.json's version against versions.json.

What each tool is for

eslint-plugin-obsidianmd (obsidianmd/eslint-plugin on GitHub, published to npm) is Obsidian's own official linting plugin. Its documented setup is an npm install of ESLint and the plugin, then a flat-config eslint.config.js with a required parserOptions block -- its own README states this block is needed because the recommended config includes type-checked rules that read your actual TypeScript project. In exchange for that setup it covers a lot: 40+ rules across manifest-structure validation, forbidden-element and style-assignment XSS prevention, banned Node.js module imports, unchecked type casts, view-reference memory-leak patterns, and UI sentence-case conventions.

This tool does none of that setup and none of that rule breadth. It is a static page you open (or a Node CLI with no dependencies) that reads three inputs -- manifest.json, versions.json, and your source files -- and reports six specific, narrow checks: missing required manifest fields, leftover sample-plugin template placeholders, a manifest version with no matching versions.json entry, unsafe innerHTML/outerHTML/insertAdjacentHTML usage, direct global listeners, and leftover console.log calls. The versions.json check is the one this comparison turns on: eslint-plugin-obsidianmd's published rule list validates manifest.json's own structure but its docs do not describe a rule that reads versions.json at all -- that file governs which installed Obsidian versions can see a release, a release-mechanism question a source linter has no reason to touch.

Common questions

Does eslint-plugin-obsidianmd already check versions.json?

Its own README and rule list, as published on GitHub, describe validating manifest.json's structure and dozens of source-level rules (forbidden elements, style-assignment XSS risks, Node.js imports, unchecked type casts, view-reference memory leaks, UI sentence case), but do not describe a rule that reads versions.json or cross-checks it against the current manifest version. This tool's versions.json check is the one thing in this comparison it does not cover.

Should I use this tool or eslint-plugin-obsidianmd?

Different jobs and different moments: eslint-plugin-obsidianmd is an ESLint plugin -- install it, add it to your flat config with a parserOptions.projectService block pointed at a real TypeScript project, and its 40+ rules run as part of your normal lint pass, catching far more than this tool's three source-level checks (unsafe innerHTML/outerHTML/insertAdjacentHTML, direct global listeners, leftover console.log). This tool needs no npm install, no TypeScript project, and no config file -- open the page or run one CLI script -- and it is the one that reads manifest.json against versions.json, the release-mechanism check neither tool's docs credit the other with. A plugin team can reasonably run both: the lint plugin in day-to-day development, this tool as a fast pre-submission pass or CI gate that needs no project setup.
