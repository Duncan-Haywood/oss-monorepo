Where copying and editing stops being enough

Anyone building a new Claude Skill already does this: open a sibling skill's SKILL.md, copy its frontmatter, and edit the fields for the new skill. For an obviously missing name or description, that catches it. The problem is the other checks below are exactly the kind of mistake that survives editing someone else's file, because the starting point was written in a different voice for a different skill.

Common questions

Can't I just copy an existing skill's frontmatter and edit it?

For catching an obviously missing name or description field, yes -- that stands out on a read. What copying and editing an existing file does not reliably catch is a first-person opening left over from the source skill's own voice, a description that reads fine but carries no concrete trigger condition, YAML indentation or quoting that looks plausible but parses wrong, and a folder layout that no longer matches the scripts, references, or assets the body actually names once you've added or removed one. Those need the same fixed template and checks applied every time, not edited by hand from a starting point written for a different skill.

Why is first-person phrasing easy to miss when you write it yourself?

Because a description written while thinking through what the skill does naturally slips into the skill's own voice -- "I help with..." reads as ordinary and even friendly to the person writing it. Claude's own documentation asks for third person specifically because the description is matched against a request, not read as the skill introducing itself, and that mismatch is invisible to the author precisely because it sounds fine out loud.

Why does forgetting a trigger cue happen so easily?

Because a description that explains what a skill does -- "formats a CSV into a PDF form" -- already feels complete to the person who just built it; the missing half is when Claude should reach for it, which requires deliberately writing out the condition rather than the capability. Skipping that step produces a description that reads as informative and still fails to trigger reliably.

What about the folder layout?

A SKILL.md written by hand and a folder built separately are two artifacts kept in sync by memory. Add a reference file after the frontmatter is already written, and it is easy to update one and forget the other -- the file exists but the SKILL.md never mentions it, or the body promises a script that was never added to the folder.
