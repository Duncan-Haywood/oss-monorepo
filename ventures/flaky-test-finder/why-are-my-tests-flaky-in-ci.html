Why are my tests flaky in CI?

"Flaky" means a test fails sometimes and passes other times with no code change in between. It is different from a broken test, which fails every time — see the first question below for why that distinction matters before you start debugging anything.

Common questions

Why does a test pass locally but fail intermittently in CI?

CI runners are usually slower and more resource-constrained than a laptop, and often run tests in parallel across more workers. That surfaces timing assumptions (a fixed sleep instead of an actual wait condition), shared state between tests running concurrently, and real network or filesystem calls that a local run's warm cache or already-open connection was hiding.

What's the difference between a flaky test and a broken test?

A broken test fails every time under the same conditions — that is a real regression in the code or the test. A flaky test fails sometimes and passes other times with no code change in between — the test or its environment is nondeterministic. Treating a broken test as flaky (retrying until green) ships a real bug; treating a flaky test as broken (blaming the last commit) wastes time bisecting a change that did nothing.

Should I just retry flaky tests until they pass?

As a short-term unblock for a release, sometimes. As a permanent policy, no — a suite where flaky tests are silently retried stops being a signal at all, since a real regression that also happens to race can pass on retry too. Track which tests are flaky and fix the highest-value ones; a rerun-until-green CI step should be a visible, counted exception, not silent default behavior.

How do I find out which of my tests are actually flaky before I start debugging?

Run the suite (or the reruns your CI already does) at least twice and compare pass/fail per test — a test that flips is flaky, a test that fails every time is a real bug. The four causes that account for most flaky tests

1. Timing and race conditions

A fixed sleep(1) instead of waiting for an actual condition (an element to appear, a job to finish, a lock to release) works on a fast machine and fails on a loaded CI runner. Look for hardcoded delays and replace them with a poll-until-true or an explicit wait on the real event.

2. Shared or leaked state between tests

A global variable, a database row, or a file on disk that one test writes and does not clean up can make a later test pass or fail depending on execution order or whether tests run in parallel. This is the most common cause when a test only fails when run alongside the full suite, never in isolation.

3. Real network or filesystem calls

A test that hits a real API, a real DNS lookup, or a real disk write inherits that dependency's own reliability — a slow upstream service, a rate limit, or a transient DNS failure will show up as an intermittent test failure that has nothing to do with your code. Mock the boundary in unit tests; keep real calls to a smaller, explicitly-flagged integration suite.

4. Test order and parallelism assumptions

A test suite that assumes it always runs in file order, or that test IDs are assigned sequentially, breaks the moment a test runner shards or randomizes execution — which most CI systems now do by default to cut wall-clock time. Randomize test order locally on purpose to surface this before CI does.
