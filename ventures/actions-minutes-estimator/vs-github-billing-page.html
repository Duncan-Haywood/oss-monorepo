This tool vs. your GitHub Actions billing page

GitHub's billing page is the real number: minutes actually metered against your plan's allowance, aggregated across every workflow in every repository on the account. It is the only place the true figure lives, and nothing here changes that. What it does not do is say which workflow spent them, or what a workflow sitting in an open pull request is about to cost once it merges -- both questions billing can only answer after the fact, once for the whole account at once.

This tool reads the workflow YAML you paste (or point the CLI at) and projects monthly billable minutes and dollar cost forward, per workflow and per job, against GitHub's own published rates -- naming the specific patterns responsible: the macOS 10× multiplier, per-job rounding on a wide matrix, a missing timeout-minutes, and push + pull_request with no branch filter building the same commit twice. It does not read your account, your billing page, or your real spend -- it models one workflow file forward from a stated set of assumptions, all of them shown on screen.

QuestionWhere to answer it
What has this account actually spent this billing period? Your GitHub billing page -- that is the real, metered number and this tool does not have it.
Which workflow or job is responsible for the spend? This tool -- billing aggregates by account, not by workflow, and the run-timing API often reports 0 on private repos.
What will the workflow in my open pull request cost once it merges? This tool -- nothing about a workflow that has not run yet exists on a billing page.
I want this checked automatically before a costly workflow merges. The CLI's --max-allowance-percent gate -- exits non-zero when a change pushes projected usage past a share of your allowance, wireable into CI itself.

Neither replaces the other. Billing is where you go to find out what actually happened; this tool is where you go before it happens, so the workflow that would have doubled your spend gets a named reason attached to it in review instead of a bigger number a month later.

Common questions

Should I use this tool instead of GitHub's own billing page?

Different jobs, and most people who use this tool still check their billing page too. GitHub's billing page is the source of truth for what an account has already spent -- real, metered, and aggregated across every workflow in every repository on the account. It does not attribute a single minute to a single workflow or job, and it has nothing to say about a workflow you have not merged yet. This tool reads the workflow YAML you paste and projects forward from GitHub's own published rates, so you get a before-you-merge estimate the billing page structurally cannot produce.

Why can't the billing page just show cost per workflow?

It aggregates by account and plan, not by workflow file, and the run-timing API that looks like it might close the gap (/actions/runs/<id>/timing) reports a billable total_ms of 0 on private repositories often enough that no reliable per-workflow attribution can be built on it. That gap is exactly what this tool exists to fill by modelling cost from the workflow definition itself rather than from a runtime API that does not expose it.

Does this tool read my account's actual usage or billing data?

No, and it cannot -- it has no access to your GitHub account at all. You paste workflow YAML into the browser tool, or point the CLI at a directory of workflow files on your own machine; either way it reads only the text of those files plus assumptions you set (how often you push, how many PRs you open) and projects a monthly total from GitHub's published list rates. It is an estimate from a model, not a read of your real spend, and both surfaces say so.

Is my workflow file or any account information uploaded anywhere?

No. The browser tool parses and costs everything client-side and sends nothing anywhere -- there is no account, no login, and no analytics vendor. The CLI reads local files and makes no network call at all. Neither surface could read your billing page even if it wanted to; you would need to check that yourself, separately, on github.com.
