This estimator vs. your GitHub billing page

Settings → Billing → Plans and usage shows how many Actions minutes an account has already spent this cycle, added up across every workflow. It is real, and it is the number GitHub will actually charge you against. What it will not do is tell you which workflow spent them, or what a workflow sitting in an open pull request is about to cost once it starts running on every push. This free tool reads the workflow files themselves and does that arithmetic forward.

What each one actually answers

GitHub's billing page is a ledger, not a diagnosis. It totals minutes already consumed for the current cycle against your plan's allowance, and it is the figure that determines whether you get billed for overage. It has no per-workflow or per-job breakdown, and it cannot look forward — a workflow you have not merged yet has spent nothing, so it has nothing to show you about it.

This estimator never touches your account or GitHub's API at all — it parses the workflow YAML you paste, entirely in your browser, and projects a monthly cost from it: per workflow, per job, with the runner multiplier, matrix expansion, cron frequency, and rounding rules GitHub actually bills by. It can do that before a single run has happened, which is the one thing the billing page structurally cannot do.

Common questions

Doesn't GitHub's billing page already show me this?

It shows total minutes spent for the billing period, added up across every workflow in the account. It does not break that total down by workflow or job, and it only reports minutes that have already been spent — it cannot tell you what a workflow currently sitting in a pull request will cost once it starts running on every push. This tool reads the workflow YAML itself and projects the cost forward, before any of it has run.

So is the billing page useless?

No — it is the only place that shows real, already-billed spend and your actual remaining allowance for the current cycle, and it is the figure GitHub will actually charge you against. This tool produces an estimate from assumptions you set (how often you push, how many pull requests run); the billing page is ground truth. Check a number here against it before making a decision that depends on being exact.

Why would I need per-workflow attribution at all?

Because a repository with more than a handful of workflows makes the billing page's account-wide total nearly useless for deciding what to fix. A macOS matrix job, a */20 * * * * cron, and a workflow that fires on both push and pull_request with no branch filter can each be spending thousands of allowance minutes a month, and the billing page reports one number for all of them combined. Attribution is what turns 'we are over budget' into 'this one workflow is the reason.'

Is anything I paste here sent to GitHub or anyone else?

No. This tool never talks to GitHub's API or anywhere else — it only parses the YAML you paste, entirely in your browser. It has no way to read your actual billing page or your account's real spend; it can only project from the files and the assumptions you give it. That is a real limit, not an oversight — see the question above about the billing page being ground truth.
