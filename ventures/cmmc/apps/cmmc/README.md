# CMMC Workspace (`apps/cmmc`)

Helps small defense/aerospace machine shops **prepare** CMMC Level 1 and Level 2 self-assessment documents:
per-requirement implementation status, owners, notes and evidence; a System Security Plan (SSP); a POA&M with due
dates; and the DoD Assessment Methodology score to enter in SPRS. Same stack and conventions as `apps/grants`
(Cloudflare Worker + Hono + D1/Drizzle + R2 + React SPA, Better Auth, `ctx.llm` with FakeLlm).

## What it is not

- **Not a certification, not a C3PAO, not government-endorsed.** It produces self-assessment *working documents*.
  The organization's affirming official makes the self-assessment and affirmation in SPRS; the app never submits
  anything and never determines a CMMC status. Every page and generated document says so.
- **Not a CUI enclave.** Do not store Controlled Unclassified Information here. Evidence uploads require the
  uploader to attest the file contains no CUI. Upload policies, procedures and redacted screenshots.
- **Not a substitute for reading the sources.** The control library was checked word for word against NIST
  SP 800-171 Rev. 2, SP 800-171A, FAR 52.204-21 and 32 CFR 170.24 on 2026-11-25, and a unit test keeps it equal
  to them ([docs/SOURCES.md](docs/SOURCES.md)), but the regulations govern, not this app.
- **Not on sale yet.** Plans, checkout and limits exist but ship dark until the owner sets the Paddle
  secrets ([docs/BILLING.md](docs/BILLING.md)).

## Features

| Area | What it does |
| --- | --- |
| Control library | Level 1: 15 requirements of FAR 52.204-21(b)(1). Level 2: 110 NIST SP 800-171 Rev. 2 requirements with all 320 SP 800-171A objectives and DoD point values — static data in `src/shared/controls/`. |
| Per control | Status (not assessed / not implemented / partially / implemented / N/A), partial credit for 3.5.3 and 3.13.11, owner, notes, per-objective met/not met, accepted implementation statement. |
| Spreadsheet import | "Import spreadsheet" on the Controls page: an existing self-assessment workbook (.xlsx, read in the browser, the tab with requirement ids picked for you) or the sheet saved as CSV. Requirement ids found by contents (AC.L2-3.1.1, 3.1.1, AC.L1-b.1.i, (b)(1)(i)); status, owner e-mail, notes and implementation statement by header. Preview first, then apply; blank cells never overwrite, unreadable rows are listed by line. Applying Level 2 needs the Level 2 plan. |
| Evidence | Uploads to R2 at `orgs/{orgId}/evidence/{id}`; 25 MB, PDF/image/text/CSV/DOCX/XLSX only; SHA-256 recorded; downloads are `attachment` with a sandbox CSP. |
| Score | 110 minus 5/3/1 per unmet requirement (range 110 to −203); no score without an SSP (3.12.4). Level 1 is pass/fail. |
| POA&M | Items with due dates, overdue flag, and live eligibility under 32 CFR 170.21 (score ≥ 88, 1-point items only, the six excluded requirements, 180-day closeout). CSV export with formula-injection guard. "Import spreadsheet" on the POA&M page reads an existing POA&M (.xlsx in the browser, or CSV): requirement id by contents; weakness, scheduled completion, remediation, milestones, responsible and status (open/closed) by header. Dates in unambiguous forms (ISO, month names, Excel date numbers) or numeric in one order for the whole sheet: month/day/year by default, day/month/year (31/12/2026, 31.12.2026) when picked or when the sheet's own dates can only be day first, never swapped cell by cell; a row with the same requirement and weakness as an item already here updates it, so re-importing changes nothing. Preview shows each row new or updated and whether 32 CFR 170.21 allows it; applying Level 2 items needs the Level 2 plan. |
| SPRS affirmations | A record of each affirmation the affirming official enters in SPRS (32 CFR 170.22): level, why (after a self-assessment, annual, after a POA&M closeout), Final or Conditional status and its date, the score entered beside the score the workspace computed that day, and the official's name, title and contact. The Affirmations tab and the dashboard show when the next annual affirmation, the next self-assessment (Level 1 yearly, Level 2 every three years, § 170.15/170.16) and a Conditional status's 180-day closeout fall due, amber within 60 days and red when past. Admins and owners get a reminder email 60 and 7 days before each date and one notice if it passes, with a one-click stop link. Admins record and delete; Level 2 records need the Level 2 plan. Nothing is submitted to SPRS. Rules quoted in `src/shared/affirmation.ts`. |
| ISO 9001 checklist | The 47 requirement clauses of ISO 9001:2015 (4.1 to 10.3), each with status (not assessed / gap / partly in place / in place / not applicable), owner, notes and evidence. Evidence is shared, not re-uploaded: files on a related CMMC requirement (a training record on AT.L2-3.2.2 for 7.2, an internal audit on CA.L2-3.12.1 for 9.2) show under the clause, and any file the org holds can be linked to a clause. Not applicable needs a reason (the scope statement must give one). Readiness by section, clauses marked in place with no file, open clauses nobody owns, a dashboard card, and a Markdown gap report with an Owner column. Clause numbers and headings only, no ISO text; prompts are the app's own wording. Every member reads it; recording needs Level 2 + Quality. `src/shared/quality/`. |
| Document control | The Documents tab is the ISO 9001 master list (clause 7.5): each procedure, work instruction, form and customer drawing with its number, revision in force, approver and date, owner, where the controlled copy is kept and its review date. Release, start the next revision (the released one stays in force until then), record a review, or withdraw it (kept, with its history; never deleted once released). History per document, master list CSV, and checks (never released, review overdue or due soon, no approver, owner or location). Review dates go in the calendar file and the subscribable link as a count of documents per date (never titles), and the "ISO 9001 dates" dashboard card lists reviews overdue or due within 60 days. No ISO text. Every member reads it; recording needs Level 2 + Quality. `src/shared/document-control.ts`. |
| Internal audits and corrective actions | The Audits tab is the ISO 9001 audit programme (clause 9.2) and corrective-action log (10.2). Each audit has a title, the clauses or process in scope, a planned date and an auditor (a member, or an outside auditor by name); mark it done with a date and summary, or cancel it (kept). Findings per audit (major or minor nonconformity, observation, opportunity for improvement, each with a clause and what was seen); "Open a corrective action" turns a finding into CA-0001, CA-0002 … with its source, clause and text. Each corrective action records the nonconformity, the correction made at once, root cause, action, owner, due and done dates, and the effectiveness check: "worked" closes it on the check's date, "did not work" keeps it open and the next action starts a new check (the earlier one stays in the notes). Checks: audits overdue or due within 30 days, an auditor who owns a clause in scope on the ISO 9001 checklist, nonconformities with no corrective action, applicable clauses (not-applicable ones left out) not audited in 12 months and not planned (the standard sets no interval; 12 months is the app's choice), actions or checks overdue, a check that found the action did not work, no owner. Corrective-action log CSV with a formula guard. Audits whose findings opened actions, findings with an action and closed actions are kept, never deleted. Planned audit dates and each open action's due or effectiveness-check date go in the calendar file and the subscribable link as a count per kind and date (never titles or the nonconformity's text), and the "ISO 9001 dates" dashboard card lists audits and actions overdue or due soon. No ISO text. Every member reads it; recording needs Level 2 + Quality. `src/shared/internal-audits.ts`. |
| Asset inventory | The Assets tab lists every asset by the five Level 2 scoping categories of 32 CFR 170.19(c) (CUI, Security Protection, Contractor Risk Managed, Specialized, Out-of-Scope); specialized assets name their kind in the rule's words (IoT, IIoT, OT such as CNC controllers, GFE, Restricted Information Systems, Test Equipment). Each asset has a type, location, provider (an external service provider), owner and notes. Checks flag a list with no CUI or security protection asset, and CRMA, specialized or out-of-scope assets with no note on how they are managed or why they cannot hold CUI. A network diagram of the assessment scope (table 3 asks, for every in-scope category: "Document in the network diagram of the CMMC Assessment Scope.") is one of the org's evidence files, picked or uploaded on the Assets tab; the check flags an inventory with in-scope assets and no diagram, deleting the file unlinks it, and the SSP names it by title, file name and SHA-256 prefix. Printed in the Level 2 SSP under the system boundary; CSV export with a formula guard. Readable on every plan; recording needs the Level 2 plan. Each category quotes the rule's description (table 3, read on eCFR 2026-11-25) above the app's own plain-language note. `src/shared/assets.ts`. "Import spreadsheet" on the Assets tab reads an existing asset list (.xlsx in the browser, the sheet with the most readable rows picked, or CSV), this inventory's own export, the CSV the free CMMC scoping worksheet exports, or the worksheet's saved file (JSON: its answers, each asset given the category the worksheet's own Level 2 rules give them, ported in `src/shared/scope-worksheet.ts` and checked against the worksheet's results on all 456 answer combinations; a "Not resolved" asset is listed with its open question, an IoT / IIoT kind is listed rather than picked): name and category by header, the category only from its own cell (this app's labels, the worksheet's, or CUI/SPA/CRMA/OOS; never inferred from a device type), a specialized asset's kind from its column or a worksheet kind that names one kind; the worksheet's policy and separation columns go into the notes. Same name updates in place (blank cells keep), so re-importing changes nothing; unreadable rows and the worksheet's "Not resolved" ones are listed by line. `src/shared/assets-import.ts`. |
| External service providers | The Providers tab scopes each cloud service, MSP or other outside provider by table 4 to 32 CFR 170.19(c)(2)(i): what it processes, stores or transmits (CUI, Security Protection Data, or neither) and whether it is a cloud service provider, with the rule's own cell quoted (read on eCFR 2026-11-26). Each records its services, the FedRAMP basis a cloud provider holding CUI needs (DFARS 252.204-7012), and its service description and customer responsibility matrix (CRM) (paragraph (c)(2)(ii)), each picked from the org's evidence files, uploaded right there on the form (after "Fill from the matrix" the matrix just read is offered as the CRM file), or typed as where it is kept (a deleted file unlinks itself), plus the Level 2 requirements the CRM assigns to it or shares. Checks flag a missing FedRAMP basis, services, service description or CRM, a CRM with no requirements marked, and a non-ESP with no reason or with requirements on it. The Level 2 SSP prints the provider table under the system boundary (a linked file by title and SHA-256 prefix) and, on each requirement, which providers carry or share it; the Controls list and each requirement's page show the same line. Same plan gate as the assets. `src/shared/service-providers.ts`. "Fill from the matrix" on the form reads the provider's CRM (.xlsx in the browser or CSV) into those marks: a responsibility column (Customer, Provider, Shared, Inherited, the provider's name) or a column per party marked with an X; objectives (3.1.1[a]) count for their requirement and a split one is marked shared with the reason; a Rev. 3 matrix is refused; unreadable rows are listed and left out; nothing is sent until the provider is saved. `src/shared/crm-import.ts`. |
| Personnel and training | The People tab is the record an assessor asks for under Awareness and Training (3.2.1 to 3.2.3) and Personnel Security (3.9.1, 3.9.2): each person's job title, whether they have access to systems containing CUI and whether they carry security duties (and which), when and how they were screened (the method, never the result), when access was granted, the date of their last security awareness, role-based (people with security duties only) and insider threat training, and, when they leave or transfer, when their access and credentials were removed. Each training's next due date comes from the organization's refresher interval (6, 12, 24 or 36 months, an admin setting, 12 by default; the page says NIST SP 800-171 Rev. 2 sets no interval, so it is the policy's choice). Checks name each gap with its requirement: training missing or past due, screening missing or dated after access was granted, duties not written down, nobody carrying security duties, a departure with no access-removal date. Per requirement, the page counts how many people the records cover and quotes the requirement from the control library; the counts are not an assessment result and set no status. Future dates are refused. CSV export with next due dates and a formula guard. Import a roster or a training provider's completion report (CSV or .xlsx): matched by email or name, blank cells keep, training dates only move forward, and each course counts only for the trainings you tick for it. Refresher dates go in the calendar file and the subscribable link as a count of people per training and date (never names), and a Level 2 dashboard card lists overdue, due-soon and missing training. Readable on every plan; recording needs the Level 2 plan. `src/shared/personnel.ts`, `src/shared/personnel-import.ts`. |
| Subcontractors and suppliers | The Suppliers tab is the flow-down list a prime asks for under DFARS 252.204-7021(d)(4) and (f): each supplier, what the order sends it (CUI, FCI only or neither), whether it is for off-the-shelf (COTS) items, the CMMC level you flow down, its CMMC status (the seven in the clause's definition), status date, latest affirmation and CMMC UIDs, whether the PO carries the clause, and when you checked the status and awarded the order. Checks quote the clause: status at the level flowed down or higher, still "current" as paragraph (a) defines it (Conditional 180 days, Final Level 1 one year, Final Level 2 or 3 three years, affirmation one year; amber 60 days ahead), CUI sent at Level 1, the clause missing from the PO (not needed for COTS or orders with no FCI or CUI), no status check, or one after award. The form suggests the minimum level 32 CFR 170.23(a) sets, quoting the paragraph it applies: Level 1 (Self) for FCI only, Level 2 (Self) for CUI, Level 2 (C3PAO) for CUI when the prime contract requires Level 2 (C3PAO) or Level 3 (DIBCAC); one click fills it in, and you still choose (docs/SOURCES.md, "Suppliers"). CSV export with each supplier's "current through" date. Those dates go in the calendar file and the subscribable link as a count of suppliers per date and part (status or affirmation, never names), and a dashboard card lists suppliers not current, running out within 60 days, or missing a status or date. FCI-only Level 1 flow-down records on every plan; CUI or a Level 2 or 3 requirement needs the Level 2 plan. `src/shared/suppliers.ts`. |
| Security policies | The Policies tab keeps one written policy per NIST SP 800-171 Rev. 2 family (the 14 Level 2 domains). Each starts from a template: purpose, scope, roles, a "Policy" section that restates every requirement of the family in its official wording from the control library, a "Procedures" section with the org's **accepted** implementation statements copied in (never an AI draft; a requirement without one gets a prompt to write it), exceptions, enforcement and review. The org edits it, an admin approves it (the exact text approved is kept), and editing an approved policy starts the next version as a draft while the approved one stays in force. A policy owner (a member), a review interval (6, 12, 24 or 36 months; NIST sets none, and the template says so), "Reviewed, no changes" to move the review date, a history of approvals and reviews, amber within 60 days and red when overdue. Download one policy, any approved version, or all of them as one Markdown manual; the SSP prints section 8 with the version in force, its approval date and next review. Readable on every plan; writing and approving need the Level 2 plan; approving, reviewing and deleting are for admins. `src/shared/security-policies.ts`. |
| SSP | Markdown generated from the system profile, the asset inventory, the security policies table and **accepted** statements only. On Level 2, each of 3.2.1-3.2.3 and 3.9.1-3.9.2 also carries the People tab's count that day ("2 of 3 current people have up-to-date security awareness training"), the refresher interval for the trainings and how many gaps the People tab lists: counts only, never a name. |
| AI drafting | `POST /controls/:id/draft` via `ctx.llm` (purpose `cmmc.implementation_statement`). Uses only the org's notes and profile; unknowns become `[CONFIRM: …]`; numbers not in the inputs are flagged. Saved as an unreviewed draft that a person must edit/accept before it reaches the SSP. Policy procedures too: `POST /policies/:family/procedures/:controlId/draft` (purpose `cmmc.policy_procedure`) writes numbered steps for one requirement from its notes, accepted statement, evidence titles and service providers (never a person's name), stored in `policy_procedure_draft` beside the policy, never in its text; the Policies tab's "Put in the policy and save" (enabled once every `[CONFIRM: …]` is resolved) puts it under the requirement's `### 3.x.y` heading, saves, and discards the draft, and the policy still needs an admin's approval. Both kinds count against the plan's AI drafts a month. |
| Billing | Level 1 free; Level 2 $249 and Level 2 + Quality $399 a month through Paddle (dark). Limits: Level 2 recording, seats, AI drafts a month, evidence storage; reading and downloads never limited. On the free plan the Controls page shows Level 2 read only (requirements, objectives, anything already recorded) with a "See Level 2 plans" button for admins, instead of forms that fail with a 402. [docs/BILLING.md](docs/BILLING.md). |
| Legal | Terms, Privacy, Refund and Acceptable Use drafts (`docs/legal/`, counsel review pending) at `/legal/:key`; every user accepts the current version before the workspace opens, and creating an org is refused until then. |
| Tenancy | Every org route behind `requireOrg()` (404 for non-members), every query filtered by `tenant.orgId`, roles owner/admin/editor/viewer, audit log. |

Model: `claude-haiku-5-5` by default (`LLM_MODEL` in `wrangler.jsonc`), per the repo rule to use the cheapest
model that does the job; move `cmmc.implementation_statement` up only when an eval shows Haiku gets it wrong.

## Commands (from `apps/cmmc`)

```
pnpm typecheck · pnpm test:unit · pnpm test:worker · pnpm build
cp .dev.vars.example .dev.vars && pnpm db:migrate:local && pnpm dev   # offline, FakeLlm
node --test scripts/provision.test.mjs                                  # deploy provisioning
```

Deploy: the `cmmc-deploy` workflow (`.github/workflows/priv-cmmc-deploy.yml`), by hand only from `main`, provisions D1 and R2, migrates, syncs the Paddle
catalog and smoke-tests `/api/health` ([docs/DEPLOY.md](docs/DEPLOY.md)). It has not run yet.

## API (all JSON; `/api/orgs/:orgId/*` is tenant-scoped)

- `GET /api/health` (`billing`, `email`), `ALL /api/auth/*` (Better Auth email+password, email verification and password reset: [docs/EMAIL.md](docs/EMAIL.md)), `GET /api/me` (with `legal`), `POST /api/me/legal/accept {version}`, `GET|POST /api/orgs` (POST needs the current legal version accepted)
- Public: `GET /api/legal`, `GET /api/legal/:key` (terms, privacy, refunds, acceptable-use)
- `GET /` (org, role, profile and the plan whose limits apply) · `PATCH /profile` (admin)
- `GET /members` · `POST /members {email, role}` · `PATCH|DELETE /members/:memberId` (admin)
- `GET /controls?level=1|2` · `GET /controls/:controlId` · `PATCH /controls/:controlId` (editor)
- `POST /controls/import {level, csv, apply}` (editor; preview when `apply` is false, Level 2 apply needs the Level 2 plan)
- `POST /poam/import {level, csv, apply}` (editor; same preview/apply split; one `poam.import` audit entry)
- `POST /controls/:controlId/draft` · `POST /controls/:controlId/draft/accept {statement?}` (editor)
- `GET /evidence?controlId=` · `POST /evidence` multipart `file, title?, controlId?, noCui=true` · `GET /evidence/:id/download` · `DELETE /evidence/:id`
