This checker vs. checking canonicals by eye in DevTools

View-source or DevTools' Elements panel shows the exact <link rel="canonical"> markup a page shipped with, for free, with nothing to install. For a page you already have open, it is the fastest way there is to see what the tag says. What it does not do is resolve a relative href against the page's own address, fetch that resolved URL, and tell you what came back -- a 404, a redirect, a page that is itself marked noindex, or a clean 200. Reading the tag and knowing whether it actually resolves cleanly are two different jobs, and only the first one is visible in the markup.

This tool sends the request(s) needed to check both halves: it fetches the page you name, reads its canonical tag(s), and -- when there is exactly one -- follows it and fetches that too, then classifies the combined evidence into eight named, well-documented canonicalization patterns. It does not replace view-source -- for a page open in your browser right now, glancing at the markup is still the quickest way to see what tag is there at all. It automates the second step: actually following the tag and checking what it leads to.

A worked example

A product page at https://shop.example.com/products/kids-rain-boots carries <link rel="canonical" href="/products/rain-boots-kids-old-name">. Viewed by eye in DevTools, that line looks entirely ordinary: a relative path, which is common and not itself an error to notice. Resolving it in your head against the page's own address gives https://shop.example.com/products/rain-boots-kids-old-name -- and only fetching that URL shows it now 404s, left behind by a rename that updated the page's own path but not the canonical pointing at the old one. This checker fetches both pages in one run and reports two findings: a relative canonical URL (notice) and a canonical target that does not return a usable page (danger, since the tag is telling search engines to index a URL that no longer exists). Confirming the second finding by eye means copying the href, resolving it yourself, opening a second tab, and checking the response -- for every page you check this way.

QuestionWhere to answer it
I have a page open and want to see what its canonical tag actually says. View-source or DevTools' Elements panel -- that quick raw look is exactly its job.
I want to know whether the canonical target actually resolves, or is dead, redirects, or is itself noindexed. This checker -- it fetches the target and reports what came back, instead of leaving you to open a second tab yourself.
I have two canonical tags in the same head and want to know if they conflict. This checker -- it compares every canonical link tag found and flags distinct targets, rather than relying on you to notice a second one further down the markup.
I want this checked automatically on every deploy, with a non-zero exit code on a real problem. This checker's CLI -- node cli/check.mjs <url> --json exits non-zero on a danger-severity finding. View-source has no CLI to wire into CI.

Neither replaces the other, and in practice most people use both: view-source or DevTools for a fast look at the markup on one page you're already looking at, this tool for the recurring, automatable question of whether the tag it names actually holds up once followed.

Common questions

Should I use this tool instead of view-source or DevTools?

Different jobs, and most people who use this tool still open view-source or DevTools first. The Elements panel (or a plain view-source) shows you the exact canonical tag markup a page shipped with -- free, already installed, and often the fastest way to glance at one page you're already looking at. What it does not do is resolve a relative href against the page's own URL, fetch that resolved URL for real, and tell you whether the target actually returns a usable page, or is itself marked noindex, or contradicts a second canonical tag elsewhere in the same head. Reading the raw tag and knowing whether it actually resolves cleanly are two different jobs.

Why would I need more than view-source if I can already read the tag?

Reading the tag tells you what it says. It does not tell you what happens when a crawler follows it: whether a relative href resolves to a URL that 404s, whether the canonical points cross-domain, or whether the destination page itself carries a noindex directive that contradicts the canonical's own instruction to index it. Confirming any of those by eye means copying the href, resolving it against the page's own address in your head, opening it in a second tab, and checking what comes back -- for every page you check. This tool does that in one request and states which named pattern, if any, the evidence matches.

Does this tool see anything view-source or DevTools can't?

It sees the same canonical tag markup view-source already shows, plus one thing neither shows on its own: the response from actually following the canonical to its target. View-source and DevTools show you what a page's head element contains; they do not fetch a second URL on your behalf and report back what it returned.

Is my target URL or its response uploaded anywhere?

No. The CLI's requests go directly from your machine to the URL(s) it needs, exactly like the requests your browser already makes. The browser report viewer only parses JSON you paste into it yourself, locally in your browser -- nothing about the target or the results is sent anywhere. The only thing stored is an anonymous local count of which features were used, with no target URLs in it.
