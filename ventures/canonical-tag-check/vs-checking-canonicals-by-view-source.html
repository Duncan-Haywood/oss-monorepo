Canonical Tag Checker vs. checking canonicals by view-source

View-source needs no tool beyond what is already open: right-click, view page source (or the Elements panel), and read the <head>. It is exact about the one page you have open -- whether a canonical tag exists, whether its href is absolute, whether it points at the right domain. It tells you nothing about the page that tag points at, because checking that means fetching a second URL, and view-source only ever shows you the page you already loaded.

Viewed in view-source, /old-guide/'s canonical tag has nothing wrong with it: one tag, absolute URL, same domain, same protocol. Every check you could run against that markup alone passes. This tool fetches /guide/ too — the page the canonical actually names — and reads what it says about itself. In the worked example below, /guide/ carries a noindex meta robots tag. The canonical on /old-guide/ is the instruction "index /guide/ instead of me"; the target page is saying "do not index me." Neither page, read alone, shows that contradiction — the practical effect is usually that neither page ends up indexed at all.

Common questions

What does checking a canonical tag by view-source get wrong?

View-source (or a browser's Elements panel) shows you the one page you already have open. It is exact about that page's own markup: whether there is a canonical tag, whether its href is absolute, whether it points at the right domain. It tells you nothing about the page the canonical points at, because that is a different URL you have not fetched -- and a canonical tag is only doing its job if the page it names is actually indexable.

Can you give a concrete example?

A migrated blog post at /old-guide/ carries one canonical tag, absolute, same domain, same protocol, naming https://example.com/guide/. Viewed in view-source, that tag has nothing wrong with it. Fetching /guide/ as well -- what this tool does automatically -- shows that page carries a noindex meta robots directive. The canonical on /old-guide/ is telling search engines "index /guide/ instead of me," and /guide/ is telling them "do not index me." Neither page, read alone, shows the contradiction.

Isn't view-source already exact about what a page contains?

About the one page you opened, yes -- it will not miss a malformed tag or a typo in the href. What it cannot do is follow a link and check what is on the other end, because that is a second HTTP request to a second URL, and a browser's view-source has no reason to make one. This tool makes that second request itself, reads the target's own meta robots and status code, and reports back whether the canonical actually resolves to something indexable.

Does this replace looking at the page at all?

No. You still choose which URL to check, and you still decide what to do about a finding -- this does not edit anything. What it removes is the step of manually opening a second tab, fetching the canonical target yourself, and reading its meta robots or status code by eye, for every page whose canonical you want to trust.

Verified against this tool's own worked example (a canonical whose target carries a noindex directive): the finding it reports is "Canonical target is itself marked noindex."
