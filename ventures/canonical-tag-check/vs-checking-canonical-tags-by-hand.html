Common questions

What's wrong with just viewing page source and reading the canonical tag?

Nothing, for reading the tag's text -- view-source or DevTools shows you exactly what the canonical tag says. What it can't show you is whether that target is actually a good canonical: whether it resolves, whether it redirects somewhere else first, or whether the page it points at is itself marked noindex. Those all require a second, real request to the canonical URL, which a manual read never makes.

Why does the canonical target need to be fetched at all?

Because a canonical tag is a claim, not a guarantee -- it tells a search engine "index this URL instead," but says nothing about whether that URL is reachable or usable. A canonical pointing at a URL that 404s, redirects through several hops, or carries its own noindex directive quietly tells search engines to index nothing at all. That only shows up by actually requesting the target, the same way a search engine would.

How would I miss a second, conflicting canonical tag by eye?

Two canonical tags naming different URLs commonly come from two systems writing one each -- a CMS plugin and a hand-written template tag, say -- and both can be buried well down a long head section among dozens of other tags. Skimming source for "the" canonical tag finds the first one and stops; it's easy to miss that a second one exists and disagrees. A tool that parses every canonical tag in the document catches this by construction.

Can DevTools show me if the canonical target redirects or 404s?

Not directly. DevTools' Network tab shows requests the current page actually made -- and a browser loading a page does not fetch that page's own canonical URL as part of rendering it. Seeing what the canonical target itself returns means opening it as a separate request and checking the result, which is exactly the second fetch this tool makes and reports on.
