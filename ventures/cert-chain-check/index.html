CERTIFICATE CHAIN CHECK · RUNS IN YOUR BROWSER

Will clients accept this certificate chain?

A server has to send its own certificate and the intermediates that issued it, in order. Browsers often paper over a missing intermediate, so the site looks fine in Chrome while curl, Java, Python and every API client fail with unable to get local issuer certificate. Paste the chain and see what each client will see.

Paste certificates

PEM text (-----BEGIN CERTIFICATE-----), a whole fullchain.pem or CA bundle, or the output of openssl s_client -connect example.com:443 -servername example.com -showcerts. Or open .pem, .crt, .cer or .der files. Never paste a private key: the page ignores one, and warns you.

Nothing is uploaded: the certificates are read and their signatures checked in this page.

      The chain in the right order

      Server certificate first, then each intermediate, no root and nothing unrelated. Save it as the file your server's ssl_certificate (nginx), SSLCertificateFile (Apache 2.4.8+) or load balancer reads.

      What it checks

      • Order and completeness: builds the chain from the server certificate up, by issuer name and key identifier, and checks every signature with your browser's Web Crypto (RSA, RSA-PSS, ECDSA P-256/384/521, Ed25519). It names a missing intermediate, a wrong one with the same name (a re-keyed or cross-signed CA), certificates in the wrong order, duplicates, strays and an included root.
      • What clients refuse: expired or not yet valid certificates, an intermediate that expires before the server certificate, an issuer that is not a CA or may not sign certificates, a path length constraint exceeded, no subjectAltName (browsers ignore the CN), a host the names do not cover, partial wildcards, no serverAuth, a keyUsage without digitalSignature, RSA keys under 2048 bits, SHA-1 and MD5 signatures, unusual curves and DSA keys, Certificate Transparency precertificates.
      • Rules with dates: the longest validity a public CA may issue: 398 days, then 200 days from 15 March 2026, 100 days from 15 March 2027 and 47 days from 15 March 2029 (CA/Browser Forum ballot SC-081v3).

      Every finding is explained, with the fix, in certificate chain errors explained. The reading was checked against OpenSSL 3.0: field for field on 37 generated certificates and all 120 roots in Ubuntu's CA bundle, and fault for fault against openssl verify on 30 chains (source and parity tests).

      From the command line

      The same checks as a zero-dependency Node 18+ script, for a CI step or a server:

      node check.mjs fullchain.pem --host www.example.com
openssl s_client -connect example.com:443 -servername example.com -showcerts </dev/null | node check.mjs - --host example.com
node check.mjs cert.pem chain.pem --fix > fullchain.pem
node check.mjs fullchain.pem --warn-days 21 --fail-on-risk     # exit 2 on an error, high or medium finding

      Questions

      Why does my site work in Chrome but curl says unable to get local issuer certificate?

      The server sends only its own certificate, without the intermediate that issued it. Browsers often hide this: they cache intermediates from other sites or download the missing one from the URL in the certificate. curl, Python, Java, Go, Node and most API clients do not, so they cannot reach a trusted root. Serve the server certificate followed by the intermediate (fullchain.pem from an ACME client, or cat cert.pem intermediate.pem).

      What order should the certificates be in?

      The server's own certificate first, then the certificate that issued it, then the one that issued that, and so on. Leave out the root: clients use their own copy. TLS 1.3 lets clients accept other orders, but TLS 1.2 requires this one and older or embedded clients still enforce it.

      Does a wildcard certificate cover the bare domain or two levels?

      No to both. *.example.com matches www.example.com and api.example.com, one whole label to the left. It does not match example.com itself or a.b.example.com. List example.com separately, and add *.b.example.com for the second level. A partial wildcard such as w*.example.com matches nothing in browsers.

      Is the common name (CN) still used to match the hostname?

      Not by browsers. Chrome stopped reading the CN in version 58 (2017), and Firefox, Safari and Go also check only the subjectAltName. OpenSSL's own check still falls back to the CN when there is no DNS name, so a certificate can pass openssl and still fail in every browser.

      Does a clean result mean my TLS setup is secure?

      No. It reads the certificates you paste. It cannot see which roots each client trusts, whether a certificate has been revoked, the protocol versions and cipher suites the server allows, or which certificate the server actually sends for each name. Test the live server too, and have a qualified person review anything that protects valuable data.
