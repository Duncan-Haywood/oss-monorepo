Certificate chain errors explained

A TLS client trusts a server certificate only if it can build a path from it, certificate by certificate, to a root in its own trust store, and every step passes: names chain, signatures verify, every issuer is allowed to issue, nothing has expired and the name the client asked for is covered. The server's job is to send everything on that path except the root. Most chain problems are one of the cases below. The type in each heading is what the checker reports.

Is the chain complete and in order?

missing-intermediate

Only the server certificate was sent. Public CAs never sign server certificates straight from a root (the CA/Browser Forum Baseline Requirements, section 6.1.7, forbid it), so an intermediate is always needed. Browsers often cope anyway: Chrome and Safari fetch the missing certificate from the URL in its Authority Information Access field, and Firefox ships a list of known intermediates. That is why a site looks fine in a browser while curl, Python's requests, Java, Go, Node and mobile apps fail with unable to get local issuer certificate or PKIX path building failed. Fix: serve the full chain (nginx ssl_certificate takes the leaf followed by intermediates; Apache 2.4.8+ reads the chain from SSLCertificateFile).

key-id-mismatch

An intermediate with the right name is present, but it is a different certificate with a different key: the server certificate's authority key identifier does not match its subject key identifier. CAs renew and re-key intermediates under the same name and publish cross-signed versions, and a bundle downloaded at a different time can hold the wrong one. Clients that select by key identifier skip it and fail as if it were missing. Fix: use the intermediate the CA returned with your certificate, or the one at the certificate's AIA CA Issuers URL.

wrong-order

TLS 1.2 (RFC 5246, 7.4.2) says the sender's certificate comes first and each following certificate certifies the one before it. TLS 1.3 relaxes this for clients, but servers and load balancers often take the first certificate in the file as theirs, and Java, older Android and many embedded TLS stacks do not reorder. Fix: leaf first, then its issuer, and so on. The checker prints the corrected file.

unrelated-certificate, duplicate-certificate, root-included

Certificates that are not on the path, appear twice, or are the root itself. A root in the chain is harmless to most clients (they use their own copy) but adds bytes to every handshake; extra unrelated certificates can confuse clients that build in order. Fix: send only the leaf and its intermediates.

Does every link hold?

bad-signature

The names chain but the issuer's public key does not verify the signature. The certificate was edited, or the issuer is a same-named certificate with another key. Fix: fetch the correct intermediate from the CA.

signature-unchecked

The algorithm is outside what Web Crypto offers (for example Ed448, RSA-PSS with mixed hashes, or the secp256k1 curve), so the checker could not verify it. Names and key identifiers were still compared. Confirm with openssl verify -untrusted chain.pem leaf.pem.

issuer-not-ca, issuer-no-keycertsign, path-length-exceeded

RFC 5280, 6.1.4: a certificate that issues others must say basicConstraints CA:TRUE, its keyUsage (if present) must include keyCertSign, and a pathlen limits how many intermediate CAs may sit below it. A private CA built by hand with openssl req -x509 plus a second openssl x509 -req step without an extensions file often gets these wrong. Fix: reissue the intermediate with the CA extensions.

Is it valid now?

expired, not-yet-valid, expires-soon

Each certificate's notBefore and notAfter, compared with the check time. Not yet valid for a fresh certificate usually means a client or server clock is wrong. Expires soon is reported within 30 days by default (--warn-days).

chain-expires-first

An intermediate expires before the server certificate. On that date the chain breaks even though the server certificate is still valid, unless the CA's replacement intermediate is installed. The checker reports the date the whole chain stops working.

validity-too-long

The CA/Browser Forum caps how long a publicly trusted TLS certificate may be valid, by the date it was issued: 398 days from 1 September 2020, then 200 days from 15 March 2026, 100 days from 15 March 2027 and 47 days from 15 March 2029 (ballot SC-081v3). The period counts both ends, so it is notAfter − notBefore + 1 second. A private CA may issue longer certificates; browsers apply the cap only to publicly trusted ones.

Does it cover the name?

hostname-mismatch

Browsers follow RFC 6125, 6.4.3 strictly: names compare case-insensitively, a * is allowed only as the whole left-most label and matches exactly one label, and an IP address must be listed as an IP entry, not a DNS name. So *.example.com covers www.example.com but not example.com or a.b.example.com.

no-san

No subjectAltName at all. Chrome since version 58, Firefox, Safari and Go ignore the subject common name, so the certificate is valid for no name. OpenSSL's -checkhost still falls back to the CN, which is why such a certificate can pass an openssl test and fail in every browser.

partial-wildcard

A name such as w*.example.com. OpenSSL accepts it by default; browsers match nothing with it.

Is it a server certificate?

no-server-auth

The extendedKeyUsage list lacks serverAuth (TLS Web Server Authentication). Typical when a client certificate or a code-signing certificate is installed on a server by mistake.

key-usage-mismatch

A keyUsage that does not include digitalSignature. An ECDSA certificate cannot be used at all without it. An RSA certificate with only keyEncipherment works only for the old RSA key exchange, which TLS 1.3 removed, so strict clients refuse it.

leaf-is-ca, self-signed-leaf

A CA certificate in the server position usually means files were swapped. A self-signed server certificate is accepted only by clients told to trust exactly it.

precertificate, no-embedded-sct

A Certificate Transparency precertificate carries a poison extension so that no client accepts it; it is what the CA logs before issuing. Download the final certificate. Chrome and Safari also require proof of logging (signed certificate timestamps) for public certificates, usually embedded in the certificate; a server can send them instead in the handshake or a stapled OCSP response.

must-staple

The TLS Feature extension asks clients to insist on a stapled OCSP response. Firefox enforces it, so the server must have OCSP stapling on.

Is the cryptography acceptable?

weak-rsa-key, weak-curve, dsa-key

RSA keys under 2048 bits, curves other than P-256, P-384 and P-521, and DSA keys are refused by current browsers and by OpenSSL at its default security level in most distributions.

weak-signature-hash

A SHA-1 or MD5 signature on anything except the root's own self-signature. Browsers stopped accepting SHA-1 certificates in 2017.

v1-certificate, negative-serial, duplicate-extension, signature-alg-mismatch, trailing-data

Malformed or old-style certificates: X.509 version 1 (no extensions, so no names and no CA flag), a negative serial number, an extension that appears twice, an inner and outer signature algorithm that differ, or bytes after the certificate. Each one is refused by some libraries.

What was pasted?

private-key-pasted

A PRIVATE KEY block. The checker skips it without reading it. If that text went anywhere else (a ticket, a chat, a log), treat the key as exposed: make a new key and reissue the certificate.

unreadable-block, not-a-certificate, no-certificates

Text that is not a readable certificate: a cut-off copy, a CSR (send that to the CA, install what comes back), PKCS#7 (convert with openssl pkcs7 -print_certs) or nothing at all.

What this check cannot see

It reads the certificates you give it. It does not know which roots a given client trusts, whether a certificate was revoked, which certificate a server actually sends for each name (SNI), or the server's protocols and ciphers. Check the live server too: openssl s_client -connect host:443 -servername host -showcerts shows what is sent, and its output pastes straight into the checker.

How it reads certificates: DER per ITU-T X.690 and the certificate profile in RFC 5280, re-implemented; signatures checked with the browser's Web Crypto API. Checked against OpenSSL 3.0.13 on generated chains and the Ubuntu CA bundle; see the source and parity tests.
