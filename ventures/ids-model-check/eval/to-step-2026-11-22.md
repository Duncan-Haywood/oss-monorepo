# ifcXML, ifcJSON and IFC5 models written as STEP (2026-11-22)

**What changed.** `step-writer.mjs` writes any model the checker reads (ifcXML,
ifcJSON, IFC5 `.ifcx`, or STEP itself) as an ISO 10303-21 `.ifc` file, from
the parsed entities, in the schema's attribute order. Before this, the model
fill (`model-fill.mjs`, 2026-11-21) refused anything but STEP ("only STEP
(.ifc) models are written"), because it edits a STEP file's text line by line.
Now a non-STEP model is written as STEP first and that copy is filled, on the
page and with `cli.mjs --fill`. The page also offers *Download as .ifc* for a
non-STEP model, and the CLI has `--to-step MODEL -o OUT.ifc`.

Choices the writer makes, each because the formats differ:

- **INTEGER or REAL from the schema.** ifcXML, ifcJSON and IFC5 do not keep
  `1` and `1.` apart, so each number is written by its attribute's (or typed
  value's) declared type: a REAL always with a point, as the shortest text
  that reads back as the same double (`1.E-7`, `0.30000000000000004`).
- **BINARY.** xs:hexBinary (ifcXML, most ifcJSON) is whole bytes; STEP's form
  starts with the count of unused bits, so `"0"` goes in front of an even
  count of hex digits. An odd count already carries it (IFC.JAVA's ifcJSON
  writes the STEP form).
- **ifcJSON list items wrapped as `{"type": "IfcPositiveInteger", "value": 28}`**
  (IFC.JAVA's tessellation samples) are unwrapped to the bare value, or a
  typed value where the attribute is a select.
- **Nothing is made up.** A required attribute the source left out is written
  `$`, as read, and counted in the writer's notes by class and attribute; a
  reference to an entity the model does not hold is written and noted.

One reader fix came out of the IfcOpenShell comparison below: IFC.JAVA writes
an `IfcCompoundPlaneAngleMeasure` as `{degrees, minutes, seconds,
microSeconds}`, and `ifcjson.mjs` kept only the degrees (IfcSite's
RefLatitude 49 where the STEP twin says (49,5,44,124)). It now reads the
fields as the list, in order.

## How it was checked

Inputs (fetched, not committed; pinned commits in each script):
`eval/fetch-ifcxml-twins.sh` (43 ifcXML files: buildingSMART's IFC4 ADD2 TC1
Annex E and two GeometryGym examples), `eval/fetch-ifcjson-twins.sh` (97
ifcJSON files, buildingSMART/ifcJSON), `eval/fetch-ifcx-twins.sh` (47 IFC5
files, buildingSMART/IFC5-development), and `eval/fetch-audit-corpus.sh` (65
public IDS files).

### 1. Read back and checked the same (`eval/to-step-twins.mjs`)

```
node eval/to-step-twins.mjs --ids-dir eval/corpus/real --out OUT --list LIST \
  eval/twins/bs eval/twins/gg eval/twins/ifcjson/Samples eval/twins/ifc5/examples
```

Each model is read, written as STEP, and the written file read again by the
STEP reader. The two are compared id for id (class and every argument;
numbers at 12 significant digits), and the 3 starter IDS plus the 65 public
IDS are checked on both (status, applicable count and failing GlobalIds per
specification).

| format | files | entities | read back the same | IDS checks the same |
| --- | --- | --- | --- | --- |
| ifcXML | 43 | 5,134 | 5,134 | 2,924 of 2,924 |
| ifcJSON | 97 | 54,416 | 54,416 | 6,596 of 6,596 |
| IFC5 (.ifcx) | 47 | 18,793 | 18,793 | 3,196 of 3,196 |
| **all** | **187** | **78,343** | **78,343** | **12,716 of 12,716** |

0 files with parse errors; 169.5 MB in, 8.4 MB of STEP out (ifcJSON and
ifcXML are verbose); 35 s for all 187 files and 12,716 checks. Before the
binary and wrapped-item handling, the first run read back 78,332 of 78,343
(10 IfcTriangulatedFaceSets with wrapped indices, 1 IfcPixelTexture).

The writer's notes on these files (required attributes the source left out,
written `$`): 34 notes of 18 kinds, all in the sources, e.g. IfcGeometricRepresentation-
SubContext.ParentContext (14 files), IfcIndexedTriangleTextureMap.Maps (3),
IfcFaceOuterBound.Orientation (1 ifcJSON file, 163 faces, `.T.` in its STEP
twin: the converter dropped it).

### 2. A second, independent reader (`eval/to-step-ifcopenshell.py`)

IfcOpenShell 0.9.0.post1 (pip) opens every written file and runs its schema
validation (`ifcopenshell.validate`). Where the source has a STEP twin from the
same exporter, the twin is validated too and the issues compared by kind.

- **187 of 187 written files open**; 149 have no validation issue.
- On the 145 files with a STEP twin, 326 issues are not in the twin. Every
  kind traced to the source file, not the writer: IfcFaceOuterBound.Orientation
  (163, the ifcJSON leaves it out), IfcPropertySet.HasProperties empty (79, the
  Duplex ifcJSON writes `"hasProperties": []`), IfcAlignmentSegment.DesignParameters
  (26, IFC5's composition does not carry it), ParentContext (20), and inverse
  counts on nested ifcXML/ifcJSON where an entity is not used (placements,
  material layers). After the compound-angle fix the IfcSite RefLatitude/
  RefLongitude issues (3 + 3) are gone and the count is 320.
- The 102 "On instance" findings in files with no twin are one IFC5 example
  (ACCA's) whose GlobalIds hold a character outside IFC's GUID alphabet.

### 3. Fill on the converted model (`eval/to-step-fill.mjs`)

```
node eval/to-step-fill.mjs --ids-dir eval/corpus/real \
  eval/twins/bs/IFC/RELEASE/IFC4/ADD2_TC1/HTML/annex/annex-e \
  eval/twins/gg/ConsoleCreateSurfaceMember eval/twins/gg/ConsoleParametricFooting
```

For each ifcXML file with a STEP twin and each of the 65 public IDS, fill runs
on the ifcXML (converted) and on the twin: **2,795 of 2,795 fills write the
same values** (by GlobalId, set, property and value: 351 values in 112 fills,
on both) and move the failing count by as much. In 47 of them the failing
counts already differ before the fill, between the two source files: the same
counts-only difference eval/ifcxml-twins-2026-11-18.md reports for a
specification that applies to every entity (a STEP twin holds unreferenced
entities a tree-shaped ifcXML file has no place for).

### 4. The ifcJSON reader change

`node eval/ifcxml-twins.mjs --ext .json --deep --ids-dir eval/corpus/real
eval/twins/ifcjson/Samples` before and after the compound-angle fix: IDS
verdicts 6,485 of 6,596 both times (as eval/ifcjson-twins-2026-11-21.md),
GlobalId-paired attribute values 29,790 to 29,794 identical (RefLatitude and
RefLongitude on two sites).

### 5. Page

Headless Chromium on the page served locally: `samples/tiny-house.ifcxml` with
the starter IDS, *Download as .ifc* downloads `tiny-house.ifc` (49 entities),
the fill panel appears for the ifcXML model and its status says the model was
written as STEP first; no console errors.

## Limits

- The written file keeps the source's ids and its entities only: a STEP twin's
  unreferenced extras are not recreated, and what a converter dropped stays
  dropped (listed in the notes when the schema requires it).
- The header is the writer's own (FILE_NAME names `ids-model-check
  step-writer.mjs`; the original author and organisation are not carried).
- Strings outside printable ASCII are written as `\X2\` (UTF-16, as
  model-fill.mjs writes them); characters beyond U+FFFF go as surrogate pairs.
- Not measured: a real authoring tool opening a written file (IfcOpenShell is
  the only second reader run here).
