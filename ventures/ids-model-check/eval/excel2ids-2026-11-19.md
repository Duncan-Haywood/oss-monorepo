# Excel2IDS workbooks read as IDS, and IDS written as one (2026-11-19)

**Question.** buildingSMART-community's
[Excel2IDS](https://github.com/buildingsmart-community/Excel2IDS) (GPL-3.0,
Artur Tomczak, 2024) is a workbook template that BIM managers fill in to
agree information requirements: asset categories in columns (name,
cardinality, IFC entity, property, classification, attribute, material,
purpose), one requirement per row, and a matrix where an `X` (or a value for
the row's `REPLACEME` cell) says which category needs which requirement. Its
tool is a Windows `.exe` that writes one IDS per purpose and cannot read an
IDS back. Can this venture read the filled template as it stands, in a browser,
and write an existing IDS into the template, without changing what any
requirement asks for?

**What was built.** `excel2ids.mjs`, MIT, with no code from Excel2IDS:
the layout is found from the template's labels ("Specification name",
"Toggle on/off", the requirement headings, "METADATA"), not fixed cells,
so a workbook with rows or columns added still reads; the rules are the ones
the template's own instructions state. Each switched-on category column
becomes a specification in one IDS per purpose (and per phase with
`--by-phase`); values in "double quotes" become patterns, values with commas,
semicolons or line breaks become lists; data types are trimmed and upper-cased;
a class typed `IfcWall` is written `IFCWALL` with a warning (a pattern is left
as written). The reverse, `idsToExcel2Ids`, lays an IDS out as the template
(categories from column R, requirements from row 19, the same requirement
shared by several categories written once with an `X` in each column) and
lists every specification it leaves out with the reason. Page: drop the
workbook where the IDS goes ("Check MEP" / "Download" per purpose); after an
audit, *as an Excel2IDS workbook*. CLI: `cli.mjs --from-sheet book.xlsx -o
out.ids [--by-phase]` writes `out_<purpose>.ids`; `cli.mjs --to-excel2ids
spec.ids -o book.xlsx`.

**Method.** `node eval/excel2ids-roundtrip.mjs --checker` (after
`eval/fetch-audit-corpus.sh` and `eval/fetch-testcases.sh`). Each IDS is
repaired as the page repairs it (`fix.mjs`), written into the template,
saved as `.xlsx`, read back by `xlsxToRows` and `excel2idsToIds`, and each
kept specification compared with the original by `canonicalIds`, with only
what the template writes out by its own rule counted as the same:
applicability occurs read as the checker reads them (no `minOccurs` is
required), a requirement facet with no cardinality as `required`, an empty
`description`/`instructions` attribute as none, the same facet twice in one
`<requirements>` as once, facet order inside a part, version order in
`ifcVersion`, a one-item string list as its value, and an entity name in
upper case. On buildingSMART's test pairs, the checker's verdict on the
round-tripped IDS is compared with its verdict on the original.

**Results** (`eval/excel2ids-roundtrip.txt`).

| files | specifications that fit the template | come back the same | files whole | requirement rows / facets |
| --- | ---: | ---: | ---: | ---: |
| public IDS files on GitHub (`eval/real-ids-files.txt`, 64 readable) | 309 of 507 | 309 of 309 | 12 of 64 | 438 / 600 |
| IDS-Audit-tool test files (75 readable) | 334 of 807 | 334 of 334 | 26 of 75 | 571 / 847 |
| buildingSMART IDS test pairs (suite `870f9c4`) | 256 of 334 | 256 of 256 | 256 of 334 | 257 / 257 |

- Checker verdicts on the round-tripped test pairs equal the originals 255 of
  256. The one that differs is `invalid-entities_must_be_specified_as_uppercase_strings`:
  the template reader writes its `IfcWall` as `IFCWALL`, so the file the
  suite expects to fail now passes. That is the reader's intended repair, and
  the warning names it; 7 entity names across the three sets were upper-cased.
- In the public files, sharing a requirement row between categories turns 600
  requirement facets into 438 rows, which is the point of the matrix.
- Why specifications do not fit (counts of specifications, top reasons):
  a `partOf` requirement (92, plus 6 with another reason), a material
  requirement with no material named (78: the template builds a material
  facet only from a non-empty cell), a range, length or typed restriction
  (52 + 17 + 8 + ...; the template's instructions say ranges are not
  supported), a specification with no requirements that is not prohibited
  (44: the template writes such a column nowhere), two property facets in one
  applicability (12). A comma in an info `purpose` or `milestone` (3) would be
  read as several purposes or phases, so that field is left out and named.
  Nothing is changed silently: every loss is a note.

**Where Excel2IDS's own tool and this reader differ.** Running Excel2IDS's
Python tool here was refused by the session's sandbox (it is third-party code
fetched for the test), so there is no side-by-side output in this
measurement. The differences below are read from the tool's source at
commit `4eb7575` (`Excel2IDS.py`), not measured:

- A `TRUE`/`FALSE` value cell is written by the tool as `True`/`False`; IDS
  booleans are `true`/`false` (the audit here flags `TRUE`), and this reader
  writes `true`.
- For a `REPLACEME` in the property-set or property-name column, the tool
  assigns the row's value and URI to a variable from an earlier row
  (`property.value = ...` where the facet is `facet`), so they are dropped
  from the facet; this reader keeps them. The same branch reads the row's
  instructions from whichever `X` row came before it.
- The tool writes every IDS with `<milestone>LOD400</milestone>`
  (`MILESTONE = 'LOD400' #TODO TEMP`); this reader writes no milestone unless
  `--by-phase` splits by the template's "Milestone (phase)" column, which the
  template's instructions describe and the tool does not yet implement.
- A category with no purpose stops the tool (`re.split` on an empty cell);
  this reader writes it to a file with no `<purpose>`.
- An IFC version other than `IFC2X3`, `IFC4` or `IFC4X3_ADD2` becomes
  `IFC4X3_ADD2` in both, but here with a warning; `IFC4X3` is read as
  `IFC4X3_ADD2` and several versions in the cell are kept.
- The tool checks the toggle with Python truth, so a toggle typed as the text
  `FALSE` counts as on; here `false`, `0`, `no` and empty are off.

**The template's own sample.** Read by these rules, Excel2IDS's sample
workbook gives an MEP and an STR IDS; the audit passes 3 of the 4 MEP
specifications and flags the fourth: its "External doors" column carries a
row (`prohibited`, `IFCWALL` `PARTITIONING`, attribute `Name` matching
`.*[Ee]xternal.*`) whose entity cell becomes a requirement that every door be
an `IFCWALL`, which no door can be. In the template a row builds one facet
per filled facet column, and an entity facet takes no cardinality, so
"prohibited" reaches only the attribute. The sample is not committed here.

**Not measured.** A requirement workbook filled in by a BIM manager for a
real project (the only public Excel2IDS workbook is the template's sample),
the tool's own output on the same workbooks (see above), and workbooks saved
from Excel by a person (the round trip reads workbooks written by
`sheetsToXlsx`; `xlsxToRows` itself was measured on 321 Apache POI workbooks,
eval/excel-workbooks-2026-11-19.md).
