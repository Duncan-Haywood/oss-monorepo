# Qto_ sets written as property sets: Tekla 2026 and Allplan exports (2026-11-23)

**Question.** The model fill's `--from-geometry` measured a missing `Qto_`
value only when the element held that set as an `IfcElementQuantity`, or held
no set of that name. Tekla Structures writes every `Qto_` set as an
`IfcPropertySet` of `IfcPropertySingleValue`s, so on a Tekla export a missing
`Qto_ColumnBaseQuantities.NetVolume` went to the to-fill table for a person to
type, even though the body was there to measure. How often does that happen
on real exports, does the geometry reading agree with what Tekla stores in
those sets, and what happens when the fill measures for them?

Every Tekla file holds its `Qto_` sets as property sets. The two Allplan 2024
test exports do too, and with German names no `Qto_` template defines
(`Länge`, `Dicke`, `Höhe`, the last 0 on every wall): an IDS asking for
`Qto_WallBaseQuantities.Length` fails on them, rightly. Allplan 2025 writes
proper quantity sets.

IDS 1.0 property facets read both kinds of set, and so do this checker and
IfcTester 0.9.0: a check is not wrong on these files. Only the fill was
missing them.

## Does the geometry reading agree with what Tekla stores?

`node eval/qto-psets.mjs <files> --json eval/qto-psets-2026-11-23.json`
(output `eval/qto-psets-2026-11-23.txt`): for each value in a `Qto_` property
set, converted to SI from the project's units (Tekla's lengths are mm), the
value `measureModel` (what `--from-geometry` writes) gives for the same
element and name.

| File | values stored | geometry gives one | within 2% |
| --- | ---: | ---: | ---: |
| test-2026-2x3.ifc | 243 | 183 | 165 |
| test-2026-4.ifc | 325 | 151 | 150 |
| test-2026-4.3.ifc | 320 | 147 | 140 |
| Tekla-Export.ifc, side areas left out | 207 | 102 | 96 |
| **Tekla total** | | **583** | **551 (94.5%)** |

- The one model in three schemas: the IFC4 export agrees on 150 of 151; the
  IFC2X3 export's beams on 51 of 68 and the IFC4X3 export's on 61 of 68.
  The same beams agree in the IFC4 file, so the difference is in how those
  exports write the bodies, not in the measuring.
- **Wall side areas are Tekla's own convention.** `Tekla-Export.ifc` stores
  `NetSideArea` on 16 walls at 1/0.489 of the one face the `Qto_` definition
  names (203.04 m² on a 28.64 m x 3.6 m wall): both faces, and still 2.2% off
  twice the measured face. No rule found reproduces it, so the fill does not
  measure side areas into a Tekla-style set (below).
- Allplan 2025 (`test-allplan.ifc`, proper quantity sets, read by
  `eval/qto-from-geometry.mjs`): walls 6 of 6 on every name, beams 61 of 61
  gross volume and 27 of 27 net, columns 8 of 8, piles 15 of 15, the slab's
  volume 1 of 1; the slab's GrossArea and the two coverings' NetArea disagree
  (3 values). The first Allplan reading this venture has had.

## What changed (`model-fill.mjs`)

When the element holds the requested `Qto_` set as an `IfcPropertySet` and
the facet's data type is a quantity measure, the value can now come from the
element's other quantity sets (as for a quantity) and from its geometry, and
is written into that property set as an `IfcPropertySingleValue` of the
measure, converted to the project's units and rounded to six significant
figures (a mm model would otherwise get `2500.0000000000005`). No second set
of the same name is created beside it. Side areas are not measured into such
a set (the Tekla convention above); they stay in the to-fill table.

## Result

`node cli.mjs --fill MODEL eval/qto-from-geometry/base-quantities.ids.xml -o OUT --from-geometry`
(walls' NetSideArea, NetVolume, Width; slabs' areas and volume; columns' and
beams' NetVolume):

| File | failing before the fill | after, old fill | after, new fill | IfcTester after |
| --- | ---: | ---: | ---: | ---: |
| test-2026-2x3.ifc | 97 | 29 | **17** | 17 |
| test-2026-4.ifc | 117 | 49 | **37** | 37 |
| test-2026-4.3.ifc | 116 | 48 | **36** | 36 |

25 more values per file written into Tekla's own sets; every written value
reads back as passing the facet that failed (93 of 93 each), and IfcTester
counts the same failures as this checker on all six files. What is left: the
walls' NetSideArea (held back), and bodies the takeoff cannot read.

Tests: `model-fill.test.mjs`, "a Qto_ set held as a property set (Tekla's
way) takes geometry and other quantity sets' values, in project units".
