# The CI runner at scale: parse once, cap the failure lists, end on truncated files (2026-11-17)

`ci-action-2026-11-17.md` ran `ci-cli.mjs` on four real exports against the
two starter IDS files and left one item open: each model was parsed once per
IDS file, so N models by M IDS files cost N x M parses. This run fixes that
and then runs the four exports against public IDS files written by other
people, which turned up two more faults a CI job cannot live with.

## Setup

The same four exports from `opensourceBIM/IFC-files` at `cb96c50` (HHS Office
`MEP.ifc` 39.6 MB / 665,224 entities, `architect.ifc` 13.1 MB,
`construction.ifc` 3.9 MB, OpeningDesign's `Schultz_Residence.ifc` 22.5 MB;
fetch steps in `model-attr-codes-2026-11-17.md`), symlinked into `models/`.
IDS sets: the two starter files in `samples/`, and the first 16 (by file
name) of the public IDS files `eval/fetch-audit-corpus.sh` fetches from
`eval/real-ids-files.txt`. Node 22.23.4, 4 vCPU, 16 GB, this container; main
at `76d819e8f` against this branch, one process at a time; peak memory from
`process.resourceUsage().maxRSS` printed at exit.

```
node ci-cli.mjs --models "models/*.ifc" --ids "req/*.ids.xml" --fail-on never --json r.json --annotations
```

## 1. Parse each model once

`ci-cli.mjs` now reads and parses a model once and checks it against every IDS
it is paired with (`pairUp` yields a model's pairs together, so one parsed
model is in memory at a time), and parses each IDS file once. `node.mjs`
exports `parseModel` and `parseIds`; `checkIds` already took a parsed model.
The first pair of a model carries the read and parse time in its JUnit
`time`, so the times still sum to the run.

| 4 models x 2 starter IDS (8 pairs) | main | this branch |
|---|---:|---:|
| Wall time, three runs | 8.37, 8.72, 8.42 s | 4.76, 4.49, 4.65 s |
| Wall time, two more runs (one process alone) | 8.65, 8.21 s | 4.37, 4.55, 4.34, 4.43 s |
| Peak memory | 1,084-1,115 MB | 991-997 MB |
| stdout, annotations included | | identical |
| `--json` results, `seconds` removed | | identical |

The saving is (M - 1) parses per model, so it grows with the number of IDS
files: with two it is about half the run.

With more IDS files the saving grows. The 14 public IDS files below, i.e. the
first 16 minus the two from `CedricDriesen92/RulebookProcessing` that section
2 is about, against the same four models (56 pairs, 264 specification checks):

|---|---:|---:|

| Peak memory | 1,546-1,561 MB | 845-852 MB |

## 2. One specification can fail every entity

With all 16 public files, both main and this branch (before the cap) died
after about 40-50 s: `FATAL ERROR: Ineffective mark-compacts near heap limit
... JavaScript heap out of memory` at Node's default ~2 GB heap.

The cause is
`CedricDriesen92/RulebookProcessing ids_output/section_0_2_1_shapes_ids.ids`.
Its specifications have no entity facet, only property facets
(`Pset_BuildingCommon`, `Pset_BuildingUse`), so they apply to every entity in
the model: on the MEP export, all 665,224 of them, Cartesian points and
property values included. Every one fails, and the report kept each failure
with its reason text. Three of its specifications on that one model:

| Specification | Optionality | Applicable | Failing | Characters of reasons |
|---|---|---:|---:|---:|
| BuildingExtension | required | 665,224 | 665,224 | 133,710,053 |
| LowHeightBuilding | optional | 665,224 | 665,223 | 63,861,408 |
| IndustrialActivity | optional | 665,224 | 665,224 | 242,141,536 |

The heap reached 2.9 GB after that one file (in a script with a larger heap);
`JSON.stringify` of its report threw "Invalid string length".

Whether such a specification should apply to every entity is IDS's question,
not CI's: IDS 1.0 allows an applicability with no entity facet. The runner's job is not to fall over.
`checkIds` takes `maxFailed`: a specification keeps its first N failing
elements and puts the full count in `failedCount` (set only when some were
dropped); `failCount` in `ci.mjs` reads it, so JUnit, the summary, the
annotations, `elements-failed` and the tally stay exact. `ci-cli.mjs` passes
`--max-failures` (default 1,000; Action input `max-failures`). The page does
not pass it, so the browser report is unchanged.

| 4 models x 16 public IDS (64 pairs) | main | this branch |
|---|---:|---:|
| Result | out of memory at 50.0 s | 44.8 s, peak 1,461 MB |
| Outputs | none | JSON 15.6 MB, JUnit 1.2 MB, BCF 22 MB |
| Specifications capped | | 16, the largest count 665,224 |


## 3. A truncated file looped forever

While testing an unreadable IDS, `parseXml("<ids><not closed")` never
returned. Every "find the end of this construct" in `xml.mjs` (comment, CDATA,
processing instruction, declaration, end tag, start tag) used `indexOf` and
added the closer's length to the result, so a missing closer sent the cursor
back to the start of the file and the loop re-read it, appending to the tree,
until the process ran out of memory. `step.mjs` had the same shape: an
enumeration, binary or `#` reference cut off mid-entity left the reader at
position 0, and `parseStep` set its scan back to it.

On main, with a 200 MB heap and a 5 s limit: the IDS `<ids><not closed`
aborted out of memory; `samples/tiny-house.ifc` cut after
`#2=IFCSIUNIT(*,.LENGTHUNIT.` (569 characters) was still running at 5 s. The
same functions run in the browser page and the editor, so a truncated upload
froze the tab, and in CI a half-committed file hung the job until the
runner's timeout.

Now each construct throws `unterminated <what> at character N` (`xml.mjs`), a
cut-off value is one bad entity (`step.mjs`: "unterminated enumeration",
"'#' with no number") and `parseStep` never moves its scan backwards. Checked
by test: every one of the 3,876 prefixes of `samples/tiny-house.ifc` ends
(3,634 parse with entity errors, the rest have no DATA section yet); every
proper prefix of a small IDS throws; every third prefix of
`samples/tiny-house.ifcxml` (3,941) throws, in 317 ms in all. In `ci-cli.mjs`
a broken model or IDS now fails only its own pairs (`ci.test.mjs`).
