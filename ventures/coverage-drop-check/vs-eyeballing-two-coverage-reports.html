Coverage Drop Check vs. eyeballing two coverage reports

Eyeballing two coverage reports is the default method, because every coverage tool already prints the number needed: the overall line-coverage percentage, in the terminal summary or at the top of the HTML report. It works when the two numbers clearly differ or a floor like --cov-fail-under=80 is crossed. It stops working the moment the overall number stays above the floor while one file underneath it does not, because the overall percentage is a weighted average across every file and does not say which file moved.

payments.py52 / 60 — 86.67%41 / 60 — 68.33%−18.33 points
Overall92 / 100 — 92.00%81 / 100 — 81.00%−11.00 points

Eyeballing the two summary numbers — 92.00% → 81.00% — both still clear a common 80% floor, so the natural read is "this PR is fine." Pasted into this tool, the same two reports come back with the fact the summary line cannot show: payments.py alone dropped 18.33 points, from 86.67% to 68.33%, while checkout.py did not move at all. The overall 11.00 point drop is entirely one file's doing, and the 80% floor never said so.

QuestionWhere to answer it
I have a baseline report and this PR's report — did the overall percentage cross my floor? Either method works here: the top-line number in your terminal or HTML report already answers this.
The overall percentage barely moved, or stayed above my floor — is a specific file still worse? Coverage Drop Check — paste both reports and the per-file breakdown names the file and the exact point drop, sorted to the top.
I have dozens or hundreds of files and want to know which ones changed without opening each one. Coverage Drop Check — it computes the delta for every file present in either report in one pass; eyeballing an HTML report has no sort-by-delta view.
I want to know why a specific file's coverage dropped, not just that it did. Neither method — that needs reading the diff itself. This tool only narrows which file to read.

Neither method is wrong on a small, single-file change: one file, an obvious drop, a glance at either report catches it. The gap opens exactly where an overall percentage is built to hide it — a large codebase where one file's real regression is diluted into a top-line number that still clears the floor. That is precisely the shape of the 92% → 81% example above, and the shape this tool exists to catch without reading every file by hand.

Common questions

What does eyeballing two coverage reports get wrong?

It usually stops at the one number every coverage tool prints in bold: the overall line-coverage percentage. A PR that takes a repo from 92.00% to 81.00% still clears a common 80% floor, so a glance at two summary numbers reads as fine. That summary is a weighted average across every file, so it cannot say which file changed or by how much — a hundred-file repo could have one file collapse or ten files each drop a little, and the top-line percentage looks the same either way.

Can you give a concrete example?

A baseline report covers 92 of 100 total lines (92.00%): checkout.py at 40 of 40 lines, payments.py at 52 of 60. The current report for this PR covers 81 of 100 (81.00%): checkout.py unchanged at 40 of 40, payments.py down to 41 of 60. Eyeballing the two summary percentages, 92% to 81%, both still above an 80% floor, reads as a PR that is fine. Pasted into this tool, the per-file breakdown says payments.py alone dropped from 86.67% to 68.33% — an 18.33 point drop in that one file — while checkout.py did not move.

Is finding the dropped file not just a matter of opening the HTML coverage report?

It is, in principle — most coverage tools can render an HTML report with a page per file. The gap is scale: an HTML report for a codebase of dozens or hundreds of files has no sort-by-delta view built in, so finding the one file that moved means opening files one at a time, or remembering which files looked different from the last time you checked. This tool computes the delta for every file that appears in either report and sorts the ones that got worse to the top, which is the same fact the HTML report contains but not a view it presents.

Does this replace reading the coverage report at all?

No. It replaces the specific step of scanning every file in two reports to find which ones changed and by how much. You still decide whether the file that dropped matters and what, if anything, to do about it — this tool only removes the manual search for which file to look at.
