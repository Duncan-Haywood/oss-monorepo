Social Preview Checker vs. Facebook Sharing Debugger

Different shapes: Facebook Sharing Debugger checks and refreshes Facebook's own cached view of one page, from Facebook's servers, and needs a Facebook login. This checker reads Open Graph and Twitter Card tags together, reads the preview image's real pixel dimensions, and needs no account -- as a browser report viewer or a matching CLI.

Check your page's tags →

Facebook Sharing Debugger, at developers.facebook.com/tools/debug, is Meta's own tool for checking how a URL will look when someone shares it on Facebook. You sign in with a Facebook account, paste a URL, and its own crawler fetches the page from Facebook's servers -- not from your browser -- then shows you the Open Graph tags that crawler read, a preview of the resulting share card, and a "Scrape Again" action that forces Facebook to re-fetch the page and refresh what it has cached for that URL. It is the tool Meta itself documents for diagnosing why a link looks wrong specifically on Facebook.

This checker does a broader, differently-shaped job. A CLI you run yourself (node cli/check.mjs <url> --json) sends one request to the page and its preview image, and the report covers both Open Graph and Twitter Card tags in one pass, applying the twitter:image/twitter:title/ twitter:description → og:* fallback chain platforms document rather than flagging a missing twitter:image as a problem on its own. It reads the preview image's real pixel dimensions straight out of the image file's own header -- not a cached crawler's account of them -- and a standalone tool on this page checks any image URL's real size with no CLI at all. No sign-in, no Facebook account, nothing uploaded to this site.

Common questions

Should I use this checker or Facebook Sharing Debugger?

They overlap on one thing -- reading a page's Open Graph tags -- and differ in scope and how they get there. Facebook Sharing Debugger, at developers.facebook.com/tools/debug/, is Meta's own tool for checking how a URL will look when shared on Facebook: you sign in with a Facebook account, its own crawler fetches the page from Facebook's servers, and it shows the Open Graph tags that crawler read along with a preview card and a button to force Facebook to re-scrape the page and refresh its cache. This checker does a broader, differently-shaped job: a CLI you run yourself sends one request to the page and its preview image, reads Open Graph and Twitter Card tags together, applies the twitter:image to og:image fallback chain, and reads the image file's real pixel dimensions directly from its header rather than trusting a cached crawler's read -- with no Facebook account and no sign-in. Use Facebook Sharing Debugger when you specifically need to see or refresh Facebook's own cached preview of a page; use this checker when you want one report covering Open Graph and Twitter Card together, or a check you can wire into your own CI with no account involved.

Facebook Sharing Debugger is free too -- what does this add?

Being free is not the difference. Facebook Sharing Debugger requires signing in with a Facebook account before it will run at all, and what it shows you is scoped to Facebook's own crawler and Facebook's own cache of the page -- it does not check Twitter/X's card tags or fallback rules, and it reports the image dimensions its own crawler resolved rather than independently reading the image file's real pixel header. This checker needs no account of any kind, checks Open Graph and Twitter Card tags in the same report, applies the twitter:image/title/description to og:image/title/description fallback chain platforms document, and includes a standalone tool that reads any image URL's actual pixel dimensions straight from the file, with no crawler or cache in between. It also ships as a CLI, so the same check can run unattended in your own build pipeline.

Why does this need a CLI instead of one paste-a-URL box like Facebook Sharing Debugger?

Facebook Sharing Debugger can fetch an arbitrary URL because the fetch happens on Facebook's own servers, where cross-origin restrictions do not apply. A browser tab has no such privilege: fetching a third-party page's HTML from inside a page you're visiting is blocked by CORS unless that site opts in, which almost none do. A small local CLI, run from your own machine, does not have that restriction. The one piece that genuinely can run in any browser with no CLI is checking an image URL's real pixel dimensions, since loading an image via an img tag -- unlike fetching its bytes -- is not subject to CORS, which is what this page's standalone image-size tool uses.
