This checker vs. manually checking each exports target by eye

Names no specific product or company — the comparison is against reading an exports map yourself, a habit every package.json author already has. Manually checking needs no tool: open the exports map, and for each subpath and condition, confirm the file it names actually exists. It works for a map with one or two subpaths. It stops working at the scale a real package's exports field actually reaches, because a present target and a missing one read identically as JSON — nothing about the text says whether the file is there.

What each method is

Manually checking means opening package.json, finding the exports field, and for every subpath and every nested condition (import/require/types/…) confirming the target file is really there — usually by clicking through a file tree or running ls against each path in turn. It costs nothing and needs no tool, and for a small map it is completely reliable: a person who checks two files correctly checks two files correctly, every time.

This tool does the same check mechanically, from two pasted text blocks: a package.json and a listing of the files you actually publish. It flattens every subpath, every nested condition, and every position in a fallback array into one flat list of literal targets, then reports the exact ones missing from the listing — with no install, no publish, and no network call either way.

Common questions

What does eyeballing an exports map get wrong?

Every literal target in an exports map reads the same on the page: a quoted relative path next to a subpath and a condition name. Nothing about the text itself says whether the file at the end of that path actually exists — that's a fact about the filesystem, not about the JSON. A small map (one or two subpaths) is realistic to check by opening each file yourself. A real package's map nests import/require/types conditions and fallback arrays across a dozen or more subpaths, and reading all of them correctly, every time, is exactly the kind of bookkeeping that slips under time pressure — especially for a condition like require that a maintainer who only tests the import path never personally exercises.

Can you give a concrete example?

A package.json declares five subpaths — ".", "./button", "./modal", "./theme", "./package.json" — totalling eleven literal targets once every import/require/types condition is flattened. The files actually published are missing exactly one of them: cjs/modal.js, the require condition inside "./modal". Every other target exists. Pasted into this tool, the package.json and the file listing resolve to one finding: 10 export target(s) exist, 1 export target(s) named in package.json do not exist — and it names cjs/modal.js specifically. Eyeballing the same eleven lines, nothing distinguishes the missing one from the other ten; a maintainer who tests only through the ESM import path (the common case in a codebase and its own tests) would never notice modal's require target was broken until a CommonJS consumer's require() call failed.

Is this tool just automating something obvious?

Reading whether one target file exists is obvious once you already know which line to check. What manual review gets wrong is coverage across the whole map: a deeply nested exports field mixes conditions a maintainer actively exercises (typically the one their own build and tests use) with ones they don't (often require, if the project itself only imports its own code with ESM). This tool doesn't know which condition matters more to any given consumer — it checks every literal target in the map, every subpath, every condition, every fallback-array position, the same way, so coverage doesn't depend on which paths a maintainer happens to run.

Does this replace testing the package after publish?

No. It replaces the step of manually re-reading the exports map to decide whether every target it names is present on disk. A clean result means every literal target you pasted a file listing for exists at that path — it is not a guarantee the package installs or imports cleanly, and it does not resolve wildcard targets or bare-specifier re-exports at all. Verify with npm publish --dry-run and a real install, exactly as this tool's own front page and footer already say.
