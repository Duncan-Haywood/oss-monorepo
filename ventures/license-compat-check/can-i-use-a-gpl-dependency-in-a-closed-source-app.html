Can I use a GPL dependency in a closed-source app?

It depends on how you ship, not only on what you depend on. The same library can be fine in a hosted service, a problem in a downloadable app, and impossible in an MIT-licensed library. This page is the short version; the tool checks a whole dependency tree against your situation.

Ways out of a conflict

  • Replace the dependency with a permissively licensed one.
  • Run it as a separate program and talk to it over a pipe, socket or HTTP, which is generally treated as arm's length.
  • Buy a commercial license from the copyright holder, which many dual-licensed projects sell.
  • Use a community fork under an OSI license, such as OpenSearch for Elasticsearch or Valkey for Redis.
  • Relicense your own project, if it is yours to relicense.

Common questions

Can I use a GPL library in a closed-source app?

If you distribute the app, no: GPL requires the combined work to be released under the GPL. If you only run it on your own servers, the distribution trigger is not met, and a separate program you call over a socket or a pipe is generally treated as a separate work.

Is LGPL safe for a proprietary app?

Usually yes if you link dynamically and let users replace the library, ship the license text, and offer the library's source. Static linking means you must let users relink with a modified version.

What does AGPL change for a web service?

Its network clause says that if you modify the software and let users interact with it over a network, you must offer them the corresponding source. Running it unmodified is generally fine.

Is Apache-2.0 compatible with GPL?

With GPL-3.0 and GPL-2.0-or-later, yes. The FSF treats Apache-2.0 as incompatible with GPL-2.0-only because of its patent terms.
