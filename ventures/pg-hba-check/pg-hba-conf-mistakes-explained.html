pg_hba.conf mistakes explained

pg_hba.conf decides who may connect to a PostgreSQL server, from where, to which database, and how they prove who they are. It reads like a firewall rule list, but three of its rules surprise almost everyone, and most of the mistakes below follow from them. The behaviour described here is PostgreSQL 16's, from src/backend/libpq/hba.c and the pg_hba.conf chapter of the manual, and each point was checked against a real PostgreSQL 16.15 server (the parity run). This guide is not affiliated with the PostgreSQL Global Development Group.

Rule 1: the first matching line decides

For each connection PostgreSQL reads the rules from the top, with an included file's lines standing where its include line is, and stops at the first line whose connection type, client address, database and user all match. It then uses that line's method. It does not look for the most specific line, and if the password is wrong it does not try the next line. A connection no line matches is refused.

Rule 2: one bad line and the whole file is refused

If any line fails to parse, or an included file cannot be opened, PostgreSQL rejects the file as a whole. At start-up the server will not start. On a reload (pg_ctl reload, SELECT pg_reload_conf(), systemctl reload) it logs the error and carries on with the previous rules, so your change has no effect and nothing on the screen says so. SELECT * FROM pg_hba_file_rules WHERE error IS NOT NULL; reads the file on disk and shows the errors before you reload.

Rule 3: keywords only count unquoted, and all is not everything

all, sameuser, samerole, replication, samehost and samenet are keywords only without quotes; "all" is a database or role named all. The database all does not match physical replication connections (pg_basebackup, streaming standbys): those match only lines that say replication. A +group matches members of the role, and a superuser is not counted as a member unless it was granted the role.

A worked example

This file is a composite of patterns that are common in real deployments:

# pg_hba.conf on an app database, edited over the years
local   all             postgres                                peer
local   all             all                                     trust
host    all             all             127.0.0.1/32            trust
host    all             all             0.0.0.0/0               md5
host    all             postgres        0.0.0.0/0               reject
host    reporting       /analyst        10.20.0.0/16            password
hostssl all             all             192.168.10.5/24         scram-sha-256
host    all             backup          010.0.0.7/32            scram-sha-256

  host    all             all             127.0.0.1/32            trust

Every finding

parse-error (error)
PostgreSQL rejects the line, with the error text it would log. Common ones: a bare address such as 10.1 or 192.168.1.0 without /bits makes the next field the netmask, so the method is read as a mask (invalid IP mask "md5"); scram instead of scram-sha-256; peer on a host line; cert or clientcert on a line that is not hostssl; a host name with /24; an option without =; a comma inside an option value (ldapsuffix=,dc=example) that splits it into two options unless the value is quoted. Because of rule 2, one of these refuses the whole file.
include-missing (error)
An include, include_dir or @file names something that is not among the files given. A relative path is taken from the directory of the file that names it. If it is missing on the server too, the whole file is refused. include_if_exists is the form for an optional file.
no-entries (error)
The file has no rules at all; PostgreSQL refuses it, since nobody could connect.
hostssl-without-ssl (medium, only when you say the server runs with ssl = off)
A hostssl line on a server without SSL is accepted with a warning (the view shows an error) but never matches, so TLS clients fall through to the rules below.
trust-remote (high), trust-loopback (medium), trust-local (medium)
trust lets the connection in as the role it names, with no password. From a network range that is anyone who can reach the port. On 127.0.0.1 or samehost it is every process on the server, including other users, containers sharing the network namespace and a web app tricked into making requests (SSRF). On the local socket it is anyone with a shell. initdb writes trust lines unless given -A, and container images often keep them.
ident-over-tcp (high, medium on loopback)
Over TCP, ident asks the client machine's ident service (port 113) who owns the connection and believes the answer. Whoever controls the client machine chooses the answer. (On the local socket ident silently becomes peer, which is fine.)
cleartext-password-no-tls (high)
password, ldap, pam, radius and bsd have the client send the password itself. On a host line from a remote range the connection may be unencrypted, so the password crosses the network in clear. Make the line hostssl.
password-method (low)
password where the transport is protected (a hostssl line, loopback, the socket): the server still receives the password rather than a SCRAM proof. Prefer scram-sha-256.
md5-method (low)
MD5 password hashes are deprecated, and PostgreSQL 18 warns about them. An md5 line already authenticates with SCRAM for roles whose stored password is a SCRAM verifier, so migrate the stored passwords (password_encryption = scram-sha-256, then set each password again) and then change the line.
no-tls-required (medium)
A remote host, hostnossl or hostnogssenc line with scram-sha-256, md5 or gss: the login itself does not reveal the password, but the session that follows can be unencrypted. A common layout is hostnossl all all 0.0.0.0/0 reject first, then hostssl lines.
any-address (low)
all, 0.0.0.0/0 or ::/0 with a password method: anyone who can reach the port can try passwords. Narrow the range and keep the port off the public internet.
secret-in-file (medium)
ldapbindpasswd= or radiussecrets= keeps a secret in pg_hba.conf, and pg_hba_file_rules shows it to anyone allowed to read that view.
unanchored-regex (medium)
A database or user starting with / is a regular expression, and it is searched for anywhere in the name: /admin matches notadmin and admin_readonly. Write /^admin$.
shadowed-rule (low; medium for a reject)
An earlier line matches every connection this one would, so by rule 1 this line never decides anything. It is worst for a reject written to block one user or network under a line that lets everyone in: the block never happens. The check is conservative: it only reports a line when the earlier one certainly covers its type (a host line covers hostssl and hostnossl), address range, databases and users.
quoted-keyword (low)
"all", "replication", "samehost" and the other keywords in quotes mean a name, not the keyword (rule 3). A quoted address keyword is read as a host name.
ipv4-shorthand (medium)
PostgreSQL parses IPv4 with the C library's numeric rules, which accept shorthand: a leading zero is octal (010.0.0.1 is 8.0.0.1), 0x is hex, and missing parts are filled from the last one (10.1 is 10.0.0.1). Write four decimal parts.
address-is-hostname (medium when it looks like an IP, else low)
Anything that is not a valid numeric address is treated as a host name, silently. 10.0.0.300 becomes a host name that almost certainly never matches. Real host names make PostgreSQL do a reverse lookup of each client and check that it resolves back, so slow DNS delays logins and whoever controls that DNS decides who matches.
host-bits-set (low)
192.168.10.5/24 matches all of 192.168.10.0/24, not one host. Write /32 for a single address.
include-dir-file-ignored (low)
include_dir reads only names that end in .conf, do not start with a dot and are at least six characters long, in byte order; 20-ops.conf.bak is skipped.

How the checker was tested

The parser is an independent implementation in JavaScript, not PostgreSQL code. 600 generated files of odd but plausible lines (quotes, commas, continuations, includes, bad masks, shorthand addresses, every method and many options) were written to a PostgreSQL 16.15 server's data directory and its pg_hba_file_rules view read back; the checker agrees with every row: the type, databases, users, address, netmask, method, options and error text (for regular expressions PostgreSQL's own engine words its errors differently, so there only the failure is compared). Then 160 files of valid rules were loaded one at a time and 36 real connections made against each, over the socket and TCP with and without TLS, as three roles to three databases and as physical replication; for every one of the 5,760 connections the checker names the same line PostgreSQL logged as the one that authenticated, or the same refusal. The cases, the runner and the recorded output are in the repository.

Limits: regular expressions are evaluated with JavaScript's engine, which agrees with PostgreSQL's for common syntax; host names, samehost and samenet from outside addresses, and group membership you have not given are reported as undecided rather than guessed; pg_ident.conf maps are not read.
