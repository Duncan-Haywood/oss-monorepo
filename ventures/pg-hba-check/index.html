Who can really connect to your PostgreSQL?

PostgreSQL uses the first line of pg_hba.conf that matches a connection, not the most specific one, and it never tries a second line. A reject for postgres written under host all all 0.0.0.0/0 scram-sha-256 never fires.

And one bad line makes PostgreSQL refuse the whole file: on a reload it quietly keeps the old rules, so the fix you just made does nothing. Paste pg_hba.conf and the files it includes below: this page reads them the way PostgreSQL 16 does and shows the lines that will not load, the rules that can never match, the line that decides each kind of connection, and the rules that let people in more easily than they look.

Nothing is uploaded. What you paste is read in this browser and never leaves your device, and the tool makes no network calls. It is a static read of the files you give it, not a security audit and not a connection test against your server.

      What it checks

      Lines PostgreSQL 16 rejects, with its own error text (invalid IP mask "md5" when 10.1 has no /, scram instead of scram-sha-256, peer on a host line, a clientcert on a non-hostssl line); includes it cannot open; rules an earlier line always beats; trust over the network, on loopback and on the socket; password, ldap, pam and radius on lines that also accept connections without TLS; ident over TCP; md5; remote password lines that do not require TLS; 0.0.0.0/0 and all; ldapbindpasswd and radiussecrets stored in the file; regexes such as /admin that match anywhere in a name; quoted keywords such as "all", which mean a role or database literally named all; IPv4 shorthand (010.0.0.1 is 8.0.0.1, 10.1 is 10.0.0.1); an address that is not a valid IP and is silently read as a host name; host bits in a CIDR; and files include_dir skips.

      Common questions

      Which pg_hba.conf line does PostgreSQL use?

      The first one, reading from the top (with included files read where their include line stands), whose connection type, address, database and user all match. It does not look for the most specific line and it does not try the next line if authentication fails. So a reject line for one user placed under a line that allows all users never fires.

      Why did my pg_hba.conf change do nothing after a reload?

      If any line has an error, PostgreSQL refuses the whole file. On a reload it logs the error and keeps using the old rules, so your edit silently has no effect; at start-up the server will not start. Run SELECT * FROM pg_hba_file_rules WHERE error IS NOT NULL; to see the errors before reloading.

      Does the all database match replication connections?

      No. A physical replication connection (pg_basebackup, a streaming standby) only matches lines whose database field is the keyword replication. Logical replication connections name a real database and match like ordinary connections.

      Is md5 still safe to use in pg_hba.conf?

      MD5 password hashes are deprecated (PostgreSQL 18 warns about them). An md5 line already uses SCRAM for any role whose stored password is a SCRAM verifier, so the practical step is password_encryption = scram-sha-256, then re-set each password, then change the lines to scram-sha-256.

      Does a clean result mean my database is secure?

      No. It reads only the patterns listed on this page, from the files you paste. It does not see listen_addresses, your firewall, role passwords, pg_ident.conf maps, which roles are superusers or group members, or your network. Confirm on the server with the pg_hba_file_rules view, and have a qualified person review anything that protects valuable data.
