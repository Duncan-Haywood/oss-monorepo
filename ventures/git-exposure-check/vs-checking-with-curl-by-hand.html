Git Exposure Checker vs. checking with curl by hand

curl -I https://example.com/.git/HEAD is the quick check every developer already reaches for, and it is not wrong to run -- a 200 there is genuinely worth investigating. What it cannot do on its own is tell a real exposure apart from a webserver answering every unknown path with its own 200-status error page. Both look identical to a status-only read.

A status-only read cannot tell them apart, which means every site behind a soft-404 server gets a false-positive "exposed" verdict from status alone -- or every soft-404 site has to be manually re-checked by eye, which does not scale past the one site you happen to be looking at right now. This checker reads the response body against the exact shape a real .git/HEAD or .git/config file has, so the soft-404 case resolves automatically instead of needing a second manual look.

Common questions

Isn't curl -I on .git/HEAD enough to check for exposure?

It tells you the status code, and a 200 there is genuinely worth investigating -- but status code alone cannot distinguish a real exposure from a webserver or CDN configured to answer every unknown path with a 200-status custom error page (a "soft 404"). Both return 200 on .git/HEAD. This checker instead reads the response body and confirms it is real git-internal content -- a "ref: refs/heads/..." line or a bare 40-character commit SHA -- before calling it exposed.

What does a soft-404 site actually return on a curl -I check?

The same 200 status a real exposure returns. A soft-404 server is deliberately configured to answer every unmatched path with its own 200-status error page rather than a real 404, precisely so broken links render something instead of a blank browser error -- which means a status-only check flags every site behind such a server as exposed, whether or not .git is actually reachable.

So does curl -I ever give a wrong answer on a real exposure or a genuinely protected site?

No -- a real 404 (genuinely protected) and a real exposure both show their true status through curl -I; the ambiguity is specific to the soft-404 pattern. That is exactly the gap this checker closes: it agrees with curl -I everywhere curl -I is already unambiguous, and adds the one case -- 200 on a soft-404 page -- that a status-only read cannot resolve on its own.

Is this page making a live comparison against curl?

No. This is a static page describing a manual method every developer already has access to -- running curl by hand and reading the status code. It names no competing product or company. The checker's own CLI requests go straight from your machine to the site you name, never through this site.

Open the Git Exposure Checker and run it against your own site.

Evidence, not a determination. This checks one specific, well-documented exposure class -- a publicly readable .git directory at the one path you give it. It does not check other source-control or backup exposures, does not crawl the rest of the site, and cannot see a pattern it doesn't check for. A clean report describes what these two requests found, not a guarantee the site has no exposed secrets.
