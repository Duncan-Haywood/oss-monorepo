Are your Dockerfile base images pinned to a digest?

A base image referenced by a tag (node:18) or nothing at all (node, which resolves to :latest) trusts whatever bytes that tag points to right now — and its publisher can push a new build to that same tag tomorrow, silently, with no version bump to review. Paste your Dockerfile below and this page finds every FROM line that isn't pinned to a content digest, with the exact command to look up the digest yourself.

Common questions

Why is a tag like node:18 a risk if it looks like a specific version?

A tag — even a specific-looking one like :18 — is a name someone attached to an image, and the publisher can push a new build to that same tag at any time. The next time you run docker build, you pull whatever bytes that tag now points to, with no version bump to review and no diff to notice. A content digest (@sha256:...) addresses one exact set of bytes and cannot be silently repointed, which is why Docker's own base-image guidance and the SLSA framework's build-provenance requirements both recommend pinning to it.

Does this tool fetch or pull anything for me?

No. It makes no network calls at all — nothing here can, because nothing here talks to a registry. For every mutable reference it finds, it prints the exact docker buildx imagetools inspect command you can run yourself to look up the digest that tag currently resolves to. The lookup, and the decision to pin, stay entirely yours.

Does a clean scan mean my build is supply-chain safe?

No. This checks one specific, well-documented thing: whether a FROM line references its base image by content digest. It is not a security audit, and it makes no claim about your build's overall supply-chain security or the safety of the code inside a pinned image.

What about multi-stage builds and FROM scratch?

A FROM line that names an earlier build stage (FROM builder, after a prior FROM ... AS builder) is not a registry pull and is skipped, as is FROM scratch, Docker's empty virtual base image that cannot be repointed. A FROM line containing a build-arg substitution like ${BASE_IMAGE} is also skipped, since the actual image cannot be determined from the Dockerfile text alone — resolve the build argument's value and re-run.

Digest-pinning a base image doesn't catch every container supply-chain risk: Pinned Actions Check asks the same "mutable tag vs. immutable reference" question for the GitHub Actions uses: lines that build and push that image, and npm Lifecycle Script Check flags install-time scripts in the dependency tree the image's own RUN npm install pulls in — two more slices of a hardened build pipeline. Docker Build Secrets Check asks a third question of the same Dockerfile: whether an ENV, ARG, or copied file bakes a credential into the image this tool never looks for, and Docker Cache Order Check asks a fourth: whether the same Dockerfile's instruction order busts the build cache. And pinning is not the same as supported: a reference can be pinned to an exact digest and still be built from a release line nobody patches anymore — Docker Base Image EOL Check asks that question of the same FROM line. Once the image is pinned and built, Kubernetes Rollout Safety Check asks the next question down the same pipeline: whether deploying it drops live requests. Already generate an SBOM for that image? SBOM Diff Check shows exactly which packages changed between two builds.
