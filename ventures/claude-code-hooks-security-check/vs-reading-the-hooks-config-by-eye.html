Claude Code Hooks Security Check vs. reading the hooks config by eye

Reading a short hooks config with one obvious curl-to-shell download catches that download. It reliably misses a credential read and network send split across a pipe, an environment dump piped to curl, a base64-decoded payload piped to a shell, and a broad rm -rf buried inside a longer chain of statements — which is what this free, no-upload checker computes exactly, in one pass.

Where reading it yourself stops being enough

Anyone about to trust a hooks configuration already does this: open settings.json, read each hook's command string, and decide whether it looks right before letting it fire automatically and unattended. For a single hook with an obviously broad curl | bash, that read catches it. The problem is the other ten checks below are not the kind of thing a skim of a rendered command string reliably surfaces, especially once a config carries several hooks across several events.

A quick read is still the fastest way to catch an obviously dangerous command in a short config, and this checker is not doing anything a careful line-by-line audit couldn't — it is reading the same command strings a careful audit would, just checking every one against eleven fixed shapes automatically instead of leaving the comparison to be remembered by hand across however many hooks the config has.

Common questions

Can't I just read the hooks config myself?

For a short config with one hook and an obvious curl-piped-to-bash download, yes -- that case is visible on a single read. What reading does not reliably catch is a credential file read and a network send that live in different parts of the same command line, an environment-variable dump piped to curl, a base64-decoded payload piped to a shell, or a broad rm -rf buried inside a longer chain of && and ; separated statements. Those need the whole command line checked against eleven separate shapes the same mechanical way every time, not remembered while skimming a settings.json with a dozen hooks in it.

Why is credential exfiltration easy to miss on a read-through?

Because the read of a sensitive path like ~/.ssh/id_rsa or ~/.aws/credentials and the curl -d or scp that sends it out can sit on opposite ends of a long piped or chained command, with ordinary-looking steps in between. A reviewer's eye catches either half in isolation easily; confirming both halves are present in the same command line, for every command in the config, is the kind of pairing a mechanical check does the same way every time and a skim does not.

Why is a base64-decoded payload piped to a shell hard to spot?

Because the dangerous part -- what actually runs -- is hidden inside an encoded blob, not written out as a readable command. The visible text is just "base64 -d | bash" or similar, which looks unremarkable next to a curl-to-shell download unless you already know to treat any decode-then-execute pipe as the same risk shape. This tool flags the pipe shape itself, without needing to decode or run the payload.

What about a broad rm -rf buried in a longer command?

A hook command chained with && or ; can run several statements in sequence, and an unguarded rm -rf ~ or rm -rf $HOME sitting third or fourth in that chain is easy to skim past while reading left to right for the command's obvious purpose. Splitting every command on its statement separators and checking each part for a broad, unguarded recursive delete is a mechanical pass through every clause, not a read of the parts that look load-bearing.
