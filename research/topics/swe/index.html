Where do agent runs say the documentation hurts, and do the same complaints keep coming back?

research/swe-friction · 5 tests

Where do agent runs say the documentation hurts? 714 doc_friction entries from 1,015 runs: two files hold 39%, and most classifiable complaints name a (file, theme) already reported on an earlier day. Preliminary.

Abstract

A stdlib analysis of the doc_friction field in 1,015 dated run records (1 to 18 October 2026): 575 runs (57%) report at least one problem, 714 entries in all. They concentrate: CLAUDE.md and research/PROJECTS.md hold 39% of entries and the top ten files 70% (Gini 0.75 over 115 files). Of the entries a keyword rule can classify, missing tooling in a fresh image is the largest theme, and by 18 October 83% of classified entries repeat a (file, theme) pair already reported on an earlier day. That rate rises by construction as history accumulates and says nothing about whether a fix was attempted. Keyword themes, self-reported field, 18 days. Preliminary.

Which test input should you use to calibrate a mass-spring-damper twin?

research/free-excitation · 8 tests

Which test input should you use to calibrate a mass-spring-damper twin? A resonant sine gives the lowest held-out prediction error (3.1e-4 vs 1.1e-3 for a step) yet the worst Fisher condition number (527 vs 56 to 114); fitted spreads sit within 0.83 to 1.09 of the Cramér-Rao bounds. Stylised, preliminary.

Abstract

Fitting mass, damping and stiffness of a lightly damped oscillator (ζ = 0.1) from one 10 s noisy trace under four equal-energy inputs, with Cramér-Rao bounds and 100 Gauss-Newton fits each. A sine at the natural frequency gives the lowest held-out prediction error (mean RMSE 3.1×10−4 against 1.1×10−3 for a step and 2.8×10−3 for an off-resonance sine) although it has the worst Fisher condition number (527 against 56 to 114), so conditioning ranks the inputs backwards. The step estimates damping 4.5× less precisely. Fitted spreads are within 0.83 to 1.09 of the bounds. Stylised: one plant, one noise level, truth inside the model class. Preliminary.

What does an agent run cost, and which runs cost the most?

research/swe-runcost · 5 tests

What does an agent run cost, and which cost the most? 355 priced runs (14 to 18 October): median $0.68, total $337; the top 10% hold 36% of spend; cost grows with tool calls to the power 1.18 (preliminary; API-equivalent estimates).

Abstract

A stdlib analysis of the 355 run records (14 to 18 October 2026) that carry an API-equivalent cost_usd. The median run costs $0.68 (95% bootstrap $0.64 to $0.72) and the 355 together $337; the top 10% of runs hold 36% of spend. Research runs are 47% of spend with the highest median ($0.82), process runs 24% on 14% of runs because of a long tail. Cost scales with tool calls with exponent 1.18 (1.11 to 1.25) and input tokens with 1.37, consistent with context re-read at each step. Preliminary: five days, one model, estimates not invoices, and cost is not scored against value.

What do agent runs record going wrong? 17% of 1,027 runs record an error (24.5% of research runs); environment 28%, own mistakes 21%, collisions 17%; runs with an error end partial twice as often (12.6% vs 6.0%) and cost about twice as much. Preliminary: keyword classifier, self-reported.

Abstract

Reads the free-text errors field of 1,027 run records: 175 runs (17.0%, Wilson 14.9–19.5%) record at least one, 24.5% of research runs against 12.4% of ventures runs. Keyword rules put 28% of the 222 entries in environment and tooling, 21% in the run's own mistake, 17% in collisions with a parallel run and 7% in timeouts; 24% match no rule. Do the swe-errors keyword rules sort run-record errors correctly?

research/swe-errlabel · 5 tests

Do the swe-errors keyword rules sort run-record errors correctly? On a 60-entry blind hand-labelled sample they agree on 40 (66.7%, Wilson 54.1% to 77.3%; kappa 0.59); the ci-or-tooling rule never wins and own-mistake recall is 55%, so the earlier shares are a lower bound for those two. Preliminary: one labeller.

Abstract

A 60-entry blind sample of the run records’ reported errors, hand-labelled once and compared with swe-errors’ keyword rules: they agree on 40 of 60 entries (66.7%, Wilson 95% 54.1–77.3%; Cohen’s κ 0.59). The ci-or-tooling rule never wins (9 hand-labelled, 0 assigned), the run’s-own-mistake class is found with recall 55%, and environment, timeout and collision hold up (recall 92–100%). So the earlier error shares are a lower bound for tooling and own mistakes. Preliminary: one labeller, the same kind of model that wrote the records, and 60 entries.

How well does a run's tool-call count predict what it costs?

research/swe-callcost · 8 tests

How well does a run's tool-call count predict its cost? On 882 priced run records cost is about $0.03 per call, a log-log fit has R² 0.91 and a held-out median error of 9%; the pooled slope 1.22 is partly group mixing (1.10 within Sonnet). Preliminary.

Abstract

Of 1,638 run records, 882 carry both a cost and a tool-call count. Cost per call is almost constant (median $0.031, 10th to 90th percentile $0.026 to $0.038); a log-log fit has R2 0.91 and misses held-out runs by a median of 9% (90th percentile 25%), no better than a flat cost-per-call multiplier. The pooled slope of 1.22 (1.18 to 1.26) is partly group mixing: it is 1.10 within Sonnet runs and 0.96 within Opus runs (wide interval). Cost is API-equivalent and derived from the same transcript as the call count, so the fit checks the measurement, not agent behaviour. Preliminary.

Where does an agent run's cost go, and why does it grow faster than its tool calls?

research/swe-cachecost · 5 tests

Where does a run's cost go? On 893 run records with per-token-kind usage, cache reads are a median 45% of the API-equivalent cost and 1-hour cache writes 41%, output only 13%; the starting context (about 60,000 tokens) is re-read on every request, which makes cost grow faster than linearly in tool calls (preliminary).

Abstract

Of 1,659 run records, 893 carry per-token-kind usage as well as cost and tool calls. At API-equivalent list prices, cache reads are a median 45% of a run's cost, 1-hour cache writes 41% and output 13%; fresh input is about zero. A linear context model fits the cache-read tokens per request as about 60,000 tokens at the start plus about 1,900 tokens more per request (bootstrap 95% interval 1,500 to 2,200), so at the median run (20 requests) the starting context is 76% of what each request re-reads. That fixed part, written once and re-read throughout, is why cost rises with a log-log slope of 1.16 against requests and 1.22 against tool calls rather than 2. Limitations: API-equivalent dollars from list prices, not a bill; the context model explains only 31% of the per-request variance; descriptive, from one repository's runs.

Abstract

Can two independent passes agree on what a portfolio project is worth?

research/swe-value · 8 tests

Can two passes agree on what a project is worth? A three-level value rubric scored two automated ways over 408 projects agrees at chance (kappa 0.07, 95% 0.01 to 0.13), partly from a name-family flaw fixed after the fact (0.25); a blind 30-project hand sample agrees better (0.45 to 0.57, wide intervals). Preliminary, track 10 milestone 3; no correctness term.

Abstract

A three-level value rubric (follow-up, new question, listed milestone) scored over all 408 research/ projects by two automated passes, one from names and order and one from README text, plus a blind 30-project hand sample. The two automated passes agree at chance level (linear Cohen’s kappa 0.07, 95% bootstrap 0.01 to 0.13); a flaw in the name pass (108 *-twin projects counted as one follow-up chain) explains part, and fixing it after the fact lifts kappa to 0.25. Against the hand sample the text pass reaches 0.45 (0.24 to 0.65) and the fixed name pass 0.57 (0.24 to 0.81), n = 30, scored by the rubric’s author. Follow-ups add about as many lines as new projects (median 318 vs 328), so by the rubric they return less per line, a ratio that is largely built in. Preliminary and negative on the automated passes; no correctness term.

How many runs does a prompt experiment need, and is it safe to peek at it?

research/swe-prompt · 7 tests

When can a prompt experiment stop? Fixed-n, peek-every-pair and a mixture SPRT simulated on ledger-shaped outcomes: peeking declares an identical brief different in 21% (success rate) to 40% (value) of experiments, the mixture test stays under 5% but needs far more runs than a 97% success rate allows. Stylised, no candidate brief run; track 10 milestone 6, partial.

Abstract

Three stopping rules for a champion-versus-candidate brief experiment were simulated on outcome distributions drawn from the run ledger (success rate 237/244) and from swe-value’s project values: one look at the end, a look after every pair, and a mixture sequential probability ratio test. Looking after every pair declared an identical brief different in 21% of 2,000 experiments on success rate and 40% on value (nominal 5%); the mixture test stayed at 0.4% and 3.9%, at the price of power (92% against 99% at a +0.2 shift in value, stopping after 181 of 400 pairs on average). At a 97% success rate a fixed test needs about 2,200 runs to see a 0.971 to 0.991 change, so success rate is a poor primary metric. Stylised and preliminary: all 244 ledger rows are the same prompt, effects are hypothetical, and the value scores are weak; no candidate brief has been run.

Which track should the next run work on, and does a smarter pick beat a uniform one?

research/swe-allocate · 6 tests

Which track should the next run work on? Four allocation policies (uniform, greedy, bootstrap Thompson, knapsack-UCB) replayed offline on 7 tracks' scored projects: greedy and Thompson reach about 80% of the best-arm oracle against 60% for the current uniform pick, but value per line falls with order in 4 of 7 tracks, so the stationary replay overstates the gain. Stylised, offline only, no live trial; track 10 milestone 4, partial.

Abstract

Four track-allocation policies (uniform, greedy value per line, bootstrap Thompson sampling, and a knapsack-style UCB) were replayed offline on 7 tracks, using the 408-project scores from swe-value (value 1 to 3, cost in lines added) under a 20,000-line budget and 300 seeds. Greedy and Thompson reach about 79–83% (pass A) and 75–79% (pass B) of the best-single-track oracle, against 58–60% for the current uniform pick; the UCB variant explores too much to help (62–66%). This is a stylised, preliminary result: arms are assumed stationary, yet value per line falls with order in 4 of 7 tracks (Spearman −0.36 to −0.57), the value scores themselves agree only weakly, lines are a poor proxy for tokens, and no live trial was run, so no policy is adopted.
