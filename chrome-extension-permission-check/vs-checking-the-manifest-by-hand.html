Chrome Extension Permission Checker vs. checking the manifest by hand

Reading manifest.json alongside your source and searching for each declared permission's API calls genuinely works, and it is the method most extension developers already use before a submission. This page names no product or company being compared against: "checking the manifest by hand" is a generic manual habit, not a competing tool.

The gap that matters most: more than one code shape per permission

Not every permission has a single, unambiguous API call to search for. clipboardRead is unlocked by either the modern navigator.clipboard.readText() or the older document.execCommand('paste'), and a codebase can use either. A developer who searches for only one and comes up empty will report the permission unused -- the wrong conclusion if the other pattern is what the code actually uses. This tool checks every known signature for a permission, not just the one a developer happened to think of first.

The gap that matters second: a host pattern hiding among API permissions

Manifest V2 extensions often list broad site-access patterns directly inside the permissions array next to ordinary API permissions like storage and tabs, with nothing to visually distinguish them. A skim for suspicious chrome.* usage has no reason to single out an entry that is not an API permission at all. This tool checks every host-shaped entry it finds, in either array, against the same fixed broad-pattern list every time.

When to still read the manifest yourself

This tool answers whether a permission's code signature is present or absent in the source you point it at -- it has no opinion on whether the feature behind that signature is worth the scrutiny a broad permission invites in review, and Chrome Web Store review ultimately judges justification, not just presence. Deciding whether a permission is actually needed, and writing the justification review will ask for, is still a job for you.

Common questions

What does checking the manifest by hand actually catch?

A developer who remembers to look can spot an obviously unused permission -- a leftover storage entry from a feature that got removed, say -- by scanning the source for chrome.storage. and not finding it. That review genuinely works for a small codebase with permissions whose API surface is a single, obvious pattern, which is most of them.

Why does a permission like clipboardRead slip past a manual search?

clipboardRead has two unrelated code shapes that both use it: the modern navigator.clipboard.readText() call, and the older document.execCommand('paste'). A developer searching the source for one pattern and not finding it will conclude the permission is unused, when the code actually uses the other pattern. This tool checks both signatures for every permission that has more than one, so which one a codebase happens to use never matters.

Why is telling a host pattern apart from an API permission easy to get wrong by eye?

Manifest V2 extensions commonly list host patterns like *://*.example.com/* directly inside the permissions array, alongside ordinary API permissions like storage and tabs -- there is no separate host_permissions array to signal which entries are which. A developer skimming the array for chrome.* API misuse has no visual cue that one entry is a broad site-access grant rather than an API permission, and might not think to check it against the broad-pattern list at all. This tool reads a host pattern wherever it appears -- in permissions or the newer host_permissions array -- and checks it against the same fixed broad-pattern set every time.

Why is re-checking the whole source tree easy to skip?

A used-but-undeclared permission -- code calling a chrome.* API whose permission was never added to the manifest -- fails at runtime, independent of review, and catching it means diffing every file against the manifest again after every change. That is easy to skip on a routine feature addition, especially right before a submission deadline when a developer is focused on the one file they just edited. This tool re-scans every file it is given every time, so a permission gap introduced anywhere in the tree is caught the same way regardless of which file changed.

Does this replace deciding whether a permission is actually justified?

No. This tool answers whether a permission's code signature is present or absent -- it has no opinion on whether the feature that signature supports is worth the review scrutiny a broad permission invites. Chrome Web Store review ultimately judges justification, not just presence, and that judgment call is still yours.

Evidence, not a determination. This is pattern-matching against known chrome.* API signatures in the source you point it at. A clean report describes what that scan found, not a guarantee a Chrome Web Store review will pass.
