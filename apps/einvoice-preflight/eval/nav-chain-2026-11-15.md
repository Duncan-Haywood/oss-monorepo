Follows `nav-annex1-head-lines-2026-11-15.md`, whose "Not done" list said section I.5
(inconsistent modification data) had not been re-read, and whose skipped list named five
I.1/I.2 warnings (342, 11400, 11401, 632, 1030) as "against the stored base invoice".

Source: nav-gov-hu/Online-Invoice (MIT), `docs/API docs/en/EN_Online Invoice System 3.0
Interface Specification (2026.02.12.).pdf`, read with `pdftotext -layout`: Annex I I.5
(page 360, IDs 1140, 1200, 1210, 1220, 1230), Annex I 342 (page 263), 11400 and 11401
(pages 264-265), 632 and 1030 (I.2, pages 298-299), Annex II (page 365: INFO 10311, 10082,

## What I.5 holds

The earlier note said "1140, 1200-1230 are in". They were not: nothing in `hungary-nav.mjs`
checked them, and none can be checked from one file. All five compare a modifying document with
the base invoice and the modifications NAV already holds. The PDF's "10311, 10082 untitled"
are Annex II INFO messages that start on the page after I.5, not part of it.

## What the chain checks, and how "earlier" is read

`hungary-nav-chain.mjs` takes every NAV file in a batch (InvoiceData, or each operation of a
manageInvoice request; batchInvoice entries one by one), finds each modification's base invoice
by originalInvoiceNumber, and walks the chain in modificationIndex order, carrying the line
numbers created so far, the running net / VAT / HUF VAT / gross, the last delivery date, any
cancellation and any mergedItemIndicator true.

| Code | Kind | Read as |
|---|---|---|
| 6 INVOICE_TYPE_MISMATCH | error | invoiceCategory differs from the base's (modifyWithoutMaster false) |
| 7 INVOICE_LINE_ALREADY_EXISTS | error | a CREATE line's lineNumberReference is the base's or an earlier modification's |
| 16 MODIFICATION_INDEX_NOT_UNIQUE | error | the index is another file's in the same chain |
| 20 MODIFY_WITHOUT_MASTER_MISMATCH | error | modifyWithoutMaster true while the base invoice is among the files (NAV: "the referenced invoice is marked as valid in the system") |
| 342 | warning | issue date before the base's |
| 11400 | warning | MODIFY: delivery date equals its own issue date, in another calendar month than the last delivery date, and the document has a line or changed customer data |
| 11401 | warning | STORNO: delivery date equals its own issue date and differs from the last delivery date |
| 632 | warning | mergedItemIndicator false after a true earlier in the chain |
| 1030 | warning | a MODIFY line whose lineNumberReference no earlier document in the chain has |
| 1140 | warning | any document after a STORNO |
| 1200 / 1220 | warning | STORNO, NORMAL or AGGREGATE, complete chain: net / VAT plus the chain's is not zero, 1 unit |
| 1210 | warning | STORNO, SIMPLIFIED, complete chain: gross (summaryGrossData) plus the chain's, 1 unit |
| 1230 | warning | STORNO, complete chain: HUF VAT, 1 HUF or 0.01 of the currency, whichever is greater |
| 11250 | information | the indices so far, with this one, are not 1..n |
| 10082 | information | the customer's taxpayerId differs from the base's |

NAV reads "received earlier" against what it holds; here it is "earlier in modificationIndex
order among the files given", and each message says "among these files". A chain with a gap
gets 11250 and its cancellation's zero sums are listed as skipped (NAV runs them only on a
complete chain). A bare InvoiceData file does not say whether it is sent as MODIFY or STORNO;
it is checked as MODIFY and the skipped list says the cancellation checks did not run. Two files
with the same base invoice number: the chain is not guessed. Legal-predecessor chains
(JOGELOD_POTLAS) are not followed.

The six chains are the ones NAV's sample folder publishes: five scenarios on base invoice
ZZZ000001 ("Modositas es ervenytelenites" 1-2, "Teves termek helyesbitese" 20-21, "Teves
termek helyesbitese", "Tobbszoros modositas" 1-2, "Teteladatok modositasa") and the batch
modification "Tobb szamla modositasa egy okirattal" of SZ00001-3. The second document of
"Modositas es ervenytelenites" (modification and cancellation) brings net 5,500,000 -
2,200,000 - 3,300,000 and VAT 1,485,000 - 594,000 - 891,000 to exactly zero, so read as STORNO
it passes 1200, 1220 and 1230 with nothing to spare.

Dropped all at once, the 30 samples form four chains and give 6 MODIFICATION_INDEX_NOT_UNIQUE
and 10 INVOICE_LINE_ALREADY_EXISTS: the five ZZZ000001 scenarios are alternatives, each
starting at index 1 and line 6, so together they collide. That is what NAV would say if all five
were sent, and why the eval runs each scenario on its own.

The one miss in the first run was the harness: the delivery-date mutant on the cancellation was
expected as 11400 and came out as 11401, which is the code Annex I gives a STORNO.

Also landed: Annex II INFO 10311 (INCORRECT_DATE_INVOICE_ISSUE_DATE_EARLY), a CREATE invoice
issued more than 10 days before the day of reporting, as an "information" finding on HU-034.
On the page the day of reporting is today in Budapest, so an old sample now carries it.
